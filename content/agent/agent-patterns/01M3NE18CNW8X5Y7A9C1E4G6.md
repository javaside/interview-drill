**先泼冷水：多智能体不是更高级，是更贵**——token 翻倍、调试翻倍、失败模式翻倍。**上它的唯一理由**：子任务需要**不同的工具集与上下文**，塞进一个上下文会互相稀释。

两种主流拓扑：

- **编排者-执行者（orchestrator-workers）**：主 Agent 只做「拆解与收敛」——把任务分成几路、每路带着专属工具与指令交给子 Agent，收回结果做汇总。像项目经理带专项小组；
- **接力交接（handoff）**：客服 Agent 聊到退款政策，把**整个会话现场**交给退款专精 Agent——后者带着完整上下文继续，用户无感。

**核心收益是上下文隔离**：单 Agent 塞进代码工具+文档工具+数据工具+全部历史——注意力四散、每步都拖全部包袱；拆成三个子 Agent，各自的窗口只有自己的工具与相关历史——**窄上下文 = 高信噪比 = 少幻觉**。

**通信的现实**：子 Agent 间不直接对话——**编排者中转**（结果作为消息回填）或**共享状态存储**（文件/数据库，各自读写）。

**术语速查**：编排者=只拆活与收敛|交接=连现场一起移交|窄上下文=多 Agent 的真正红利

并行 fan-out（独立子任务并发执行——总延迟取最慢一路）。子 Agent 的输出契约（结构化交付物——主 Agent 好消化）。Swarm 式路由（无固定编排者，Agent 间互相 handoff——对话即接力）。
