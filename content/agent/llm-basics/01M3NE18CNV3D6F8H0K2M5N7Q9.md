**上下文窗口 = 这一次请求能带的全部 token**：system prompt + 对话历史 + 检索的文档 + 即将生成的回复，全部算在内。窗口从 4K 涨到 200K+，但「塞得下」≠「用得好」：

- **截断是必然**：历史超过窗口，服务端/客户端策略是丢最旧或摘要压缩——用户感觉「它忘了之前说的」，其实是上下文工程没做好；
- **迷失中间（lost in the middle）**：长文**首尾**召回好、**中段**显著掉——把关键信息埋在 50 页文档第 23 页，等于抽奖。绕法：重要信息放头尾、结构化分段、或干脆用检索只喂相关段；
- **成本与延迟随长度线性走**：token 计费 × 长度，KV 缓存占显存，长 prompt 的 prefill 也慢——「每次带全部文档」是最贵且常常最差的做法；
- **长窗 vs RAG 不是二选一**：长窗适合**整体理解**（整本书总结）；RAG 适合**精准问答**（万个文档里找那三段）——生产系统常是「检索精选 + 长窗兜底」。

**术语速查**：窗口=一次能带的家当|迷失中间=中段记忆洼地|塞满=最贵且未必最好
