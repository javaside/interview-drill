抢券是**秒杀的变体**（秒杀详卡见分布式大类），但多了**核销**这一段生命周期：

```
领取段（高并发峰值）：
  流量漏斗：前端防抖/按钮置灰 → 网关限流 → 排队
  库存：Redis lua 原子「查+扣」——扣成功才发号，天然防超发
  落库：发券记录异步入库（MQ 削峰）——DB 只承接收敛后的量
  一人一张：领券表 (券id, userId) 唯一约束——Redis 挡量，DB 兜底

核销段（低并发但要防错）：
  状态机：未使用 → 锁定（下单占用）→ 已使用
  锁定超时未支付 → 自动回滚为未使用（订单取消券要回来）
  已使用是终态——防重复核销靠状态机单向流转
```

**Redis 与 DB 的一致性**：以 **Redis 预扣为准做超发判断**（快且原子），DB 记录异步补——极端情况（Redis 扣成功、MQ 丢失）用**对账补偿**：活动后 Redis 剩余 + DB 发放数 = 总量，不平则按 DB 修正 Redis。**宁少发不多发**：少发可补发（客诉可解），超发核销时才发现就是资损（不可逆）——所以 Redis 扣减的 lua 要「先查后扣」原子执行。

**术语速查**：领取与核销分段治|原子查扣=防超发的核心|锁定回滚=券的生命周期闭环
