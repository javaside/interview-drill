IM 的骨架四件套：

```
客户端 ←长连接→ 网关集群 ←→ 路由服务（谁在哪台网关） ←→ 消息服务 → 存储
                                              ↓
                                          离线收件箱/推送
```

- **接入层**：长连接（WebSocket/私有 TCP 协议）网关集群百万级连接——网关只管收发与心跳，**无状态化靠路由层**：连接建立时在 Redis 登记 `userId → gateway节点`，发消息先查路由再转投；
- **可靠性（不丢不重）**：发送链 `客户端 → 服务端落库（持久化成功才回 ack）→ 推送接收方`；接收方**客户端去重**（消息 id 幂等）+ **按序补拉**（上线/断连时按最大消息 id 拉增量）——推送丢了有拉取兜底，推送重复有去重兜底，两层防御；
- **在线/离线双路径**：在线→网关直推；离线→写收件箱（未读队列），上线拉取后清；移动端还有厂商推送通道兜底（进程被杀时）；
- **单聊 vs 群聊的分治**（最容易答崩的点）：单聊**写扩散**（一条消息写两份收件箱，量小无所谓）；群聊小群仍写扩散、**大 V 群读扩散**（消息只写一份到群时间线，成员读时各自拉取+各自维护已读位）——万人群若写扩散，一条消息=一万次写，必然风暴。

**术语速查**：路由表=找人的通讯录|落库再 ack=不丢的底线|大群读扩散=防写风暴的开关

消息序与因果一致性（单聊用发送方 seq，群聊用会话向量/混合逻辑时钟）。已读回执的写放大（读状态不上行广播——聚合上报）。多端同步（同一账号多设备的消息游标独立）。
