## 结论先行

§5 不是"有几个边界没想清楚"。它有一个结构性问题：**§5.2 想让每张卡的最后一遍落在面试前，§5.4 只允许把卡往前挪。这两条在任何满载场景下都不可能同时成立**，而文档把两者都写成了硬性保证。§5.5 的超载判据用的是全局求和，检测不到 §5.4 真正会崩的那种失败，连文档自己给的收窄建议都救不回来（下面有实算）。

叠加上"每次提交都重跑 schedule()"（§8），整个引擎没有稳定不动点：同一张卡的复习计划每次都被重算，次数单调发散。

## 致命

### F1. 同一批新卡拿到完全相同的 `d[]`，排期不是"铺满窗口"而是 4 个尖峰

**章节**：§5.2 + §4.4

`n` 的唯一输入是 `s`，而 §4.4 规定"未刷过的卡 `s = 0`"。于是第 0 天**全部 150 张卡的 `s` 都等于 0 → `n` 都等于 4 → `d[]` 逐字节相同**。公式里没有任何按卡 id 的抖动、错峰或分批。

失败输入：150 张全新卡，`R=21`，`dailyCapacity=30`。
实算：`buffer=1, E=20, n=4, d=[1,4,9,20]`，对全部 150 张卡都一样。

每日负载：

```
day1: 150   day4: 150   day9: 150   day20: 150
其余 17 天: 0
```

窗口有 20 天、容量 600 个槽位，而算法只用了其中 4 天。"按 1:2:4:8 递增比例**铺满窗口**"（§5.2 标题句）这个说法是错的——它铺的是 4 个 δ 尖峰。§5.2 的整套设计隐含假设卡片已经彼此错开，而这只在用了几天之后才成立；**第 0 天，也就是 §12 ① 的激活流程刚把用户送进来的那一刻，退化程度最大**。

F2、F3 都是这条的直接后果。

**建议修法**：`d_i` 加入按 `cardId` 的确定性抖动（如 `hash(cardId) mod m` 的相位偏移），或在 §5.2 之后、§5.4 之前插入一个显式的"首次投放分批"步骤，把新卡按 `dailyCapacity` 分到 day 0..k 再各自起算窗口。前者更符合"纯函数"的要求。

### F2. §5.4 的往前挪直接摧毁 §5.2 声明的核心不变量

**章节**：§5.2 步骤 3 ↔ §5.4

§5.2 写："累积比例保证 `d_n = E`，即**最后一次复习强制落在面试前 buffer 天**。"
§5.4 写："某天排期超出容量时，把溢出的卡挪到**前一天**，递归直到不超或挪到今天。"

这两句互斥。实算（`/tmp/sched_check/cap.py` Case 1）：

失败输入：150 张全新卡，`R=7`（一周后面试），`dailyCapacity=30`。
`buffer=1, E=6, n=4, d=[1,2,3,6]`（全部 150 张相同）。

```
均衡前  day1:150  day2:150  day3:150  day6:150
均衡后  day0:420  day1:30  day2:30  day3:30  day4:30  day5:30  day6:30
```

**输出的错误**：

1. `day0` 拿到 **420 张卡，容量 30，超载 14 倍**。§5.4 自己说"递归直到不超**或挪到今天**"——今天没有前一天，所以今天是唯一被豁免 `dailyCapacity` 的日子。文档从未承认这一点。
2. `day6`（= `E`，面试前 buffer 天）只剩 30 张。**150 张里有 120 张的最后一遍被从 day6 拽走了**，落到 day5/4/3/…/0。§5.2 的"强制落在面试前 buffer 天"对 80% 的卡不成立。
3. 600 次复习里有 420 次挤在今天，意味着平均每张卡有 2.8 遍在同一天完成。文档没有任何规则禁止同一张卡的多次复习被压到同一天——而同日重复刷 4 遍对间隔重复毫无价值。

这不是参数调不对，是两个模块的目标函数相反。**§5.2 要的是"末端对齐"，§5.4 要的是"前端填平"，在满载时只能二选一。**

**建议修法**：三选一，并在文档里明写选了哪个。
(a) 把"最后一遍必须在 `E`"降级为软约束，`d_n` 允许在 `[E-k, E]` 内浮动，`d_1..d_{n-1}` 才是可挪的；
(b) 容量约束改成**排期时的硬约束**而非事后均衡——按天贪心装箱，装不下就在 §5.2 阶段减少该卡的 `n`（少刷一遍，而不是把一遍挪到没用的位置）；
(c) 显式声明"超载时放弃末端对齐"，并同步修正 §6 屏③ 的圆点 UI（它现在会画出一个不会发生的未来）。

### F3. §5.5 的超载判据检测不到 §5.4 的失败；文档自己的收窄建议也救不回来

**章节**：§5.5 ↔ §5.4

§5.5 的判据是 `Σn > R × dailyCapacity`。这只是**可行性的必要条件**（全局总量），而 §5.4 只能往前挪，真正的可行性条件是**前缀和条件**：对每一天 `t`，`Σ(排在 day 0..t 的复习次数) ≤ (t+1) × dailyCapacity`。§5.5 只测了 `t = E` 那一项，也就是最松的那一项。而 F1 保证了负载全部集中在早期尖峰上，**卡死的永远是前缀，不是总量**。

**反例 A（§5.5 说没问题，§5.4 照样爆）**：100 张全新卡，`R=30`，`dailyCapacity=30`。

```
buffer=2, E=28, n=4, d=[2,6,13,28]
Σn = 100×4 = 400  ≤  R×C = 30×30 = 900   →  §5.5: 不告警
均衡后 day0:40 day1:30 day2:30 day3:10 day4:30 ... day28:30
```

`day0` 拿到 40 张，容量 30。**超载警告不会响**，用户得到的是一个静默溢出的排期——恰恰是 §5.5 承诺"不静默降级"要避免的。同时 100 张里有 70 张的最后一遍被从 day28 拽走。

**反例 B（把 §5.5 自己开的药吃下去，病还在）**：150 张卡、`R=7`、`C=30`，§5.5 告警并建议"按 frequency 降序取最大前缀使 `Σn ≤ R×C`"。`4k ≤ 210 → k = 52`。用户听话砍到 52 张：

```
52 张全新卡，d=[1,2,3,6]
Σn = 208 ≤ 210   →  §5.5: 通过，不再告警
均衡后 day0:66  day1:30  day2:30  day3:30  day5:22  day6:30
```

**今天仍然是 66 张 / 容量 30，超载 2.2 倍**，而且 52 张里有 22 张丢掉了末端对齐。**§5.5 的补救措施在它自己的判据下"成功"了，实际问题一点没解决。**

另外 §5.5 还有三处小的但会改变数字的问题：
- 分母用 `R` 而不是可用天数。`R=30` 时 `R×C=900`，而实际槽位是 day 0..E = 29 天 × 30 = 870（若 day 0 不可用则 840）。**高估 30–60 张卡的容量**。
- `Σn` 里的 `n` 是 §5.2.4 降级**前**还是降级**后**的？`R=2` 时两者分别是 600 和 150，差 4 倍。未定义。
- `frequency` 是三值枚举，"降序取最大前缀"在 `high` 组内部（假设 60 张，只能留 52 张）没有任何定序规则。哪 8 张被砍掉未定义。

**建议修法**：判据换成前缀和检查
`for t in 0..E: prefixDemand(t) ≤ (t+1) × dailyCapacity`，任一 `t` 违反即告警，并把最早违反的 `t` 报给用户（"你前 3 天就已经排不下了"比"总量超了"可操作得多）。收窄建议同样按前缀条件求解，而不是按 `Σn`。

### F4. 第 0 天 `todayQueue` 恒为空

**章节**：§5.2 步骤 3、§5.1

`d_i = round(E × (2^i - 1) / (2^n - 1))  for i = 1..n`，下标**从 1 起**。穷举验证（`n=1..5, E=n..199`，见脚本 E 节）：**不存在任何 `(n, E)` 使某个 `d_i = 0`**。文档自己的例子也是 `D1、D4、D9、D20`，没有 D0。

失败输入：新用户，20 张卡，`R=21`，`dailyCapacity=30`。
`d=[1,4,9,20]`，没有一天超过容量 30 → §5.4 不触发 → 没有任何卡被挪到今天。
**输出：`todayQueue = []`。**

用户按 §12 ① 的设计走完激活流程，回答完"你什么时候面试"，看到的第一屏是"今天没有要复习的题"。这是产品第一印象上的致命 bug，而且直接由公式的下标起点导致。

`R ≤ 1` 是唯一能把卡排到今天的路径（§5.2.4 第三条特判），或者 §5.4 溢出兜底——两条都是异常路径。也就是说：**正常路径下今天永远没有卡**。

顺带，这暴露了一个更深的建模缺失：算法把每张卡都当成"已有记忆痕迹、等待复习"的对象，**没有"首次学习/首次曝光"这个状态**。`d_1` 究竟是"第一次见到这张卡"还是"第一次复习"，文档没说，而两者的排期语义完全不同。

**建议修法**：明确 `d` 的语义是"相对今天的偏移，0 合法"，且未刷过的卡首次曝光必须是 `d_1 = 0`（受 `dailyCapacity` 约束分批）。已刷过的卡从 `d_1 ≥ 1` 起算。

### F5. `R ≤ 1` 时同一天死循环；全文没有"这张卡刷完了"的终止状态

**章节**：§5.2.4 第三条 ↔ §8

§5.2.4："极端情况 `R ≤ 1`（今天或明天面试）时 `n = 1`，全部卡排在今天。"
§8："提交勾选 → … → **重跑 `schedule()`** → 返回 { …, 下次复习日, … }"

失败输入：`R = 1`（明天面试），用户刷一张卡。
`schedule()` 返回该卡"下次复习日 = 今天" → 卡重新进入 `todayQueue` → 用户刷 → 重跑 → 又是今天 → …

**无限循环，且发生在面试前一天**——这个产品最重要的一天。文档里没有任何一处定义"一张卡在本周期内已完成"的终止条件；`schedule()` 在任何输入下都至少吐出 `n ≥ 1` 次未来复习。

同样的循环在 `R ≥ 2` 时也能触发，走 §5.3：勾选比例 `< 0.5` → "当天稍后"重排 → 用户又答错 → 又是"当天稍后" → …。**§5.3 没有单日重试次数上限**，也没说"稍后"是多久之后、插在队列第几位。一个卡在概念上没懂的用户会被这张卡卡死在今天。

连带问题：这些同日重试算不算 §6 屏① 的"今日进度 `12/30`"的分母？算的话进度条分母会自增（`12/30 → 12/31 → 12/32`）；不算的话用户做了 45 次复习而进度条写着 30。两种读法都能从文档里读出来。

**建议修法**：
- 定义卡的终止状态：`d` 中已无 `> today` 的项 ⇒ 本周期完成，不再进入 `todayQueue`。
- §5.3 加单日上限（如同一张卡当天最多重排 1 次），超限后强制推到次日。
- 明确同日重试不计入 `dailyCapacity` 和今日进度分母。

## 严重

### S1. §8 的"所有排期状态都能从 review_log 重放"不成立

**章节**：§8

先说前提：**`review_log` 的字段在全文中从未定义**。§8 只说它 append-only。所以"能重放"是在一个未定义的 schema 上做的断言。

即便假设它记了 `(cardId, timestamp, checkedCount)`，重放 `schedule(cards[], userState, examDate, dailyCapacity, today)` 需要五类输入，其中**四类不在日志里**：

| 输入 | 在 log 里吗 | 后果 |
|---|---|---|
| `examDate` | 否 | 用户在 day 5 把面试从 10-06 改到 10-20，用**当前** `examDate` 重放得到的历史与真实发生过的历史完全不同。需要 examDate 变更事件流。 |
| `dailyCapacity` | 否 | 从 30 改到 50 会改变 §5.4 的挪卡结果，即"哪张卡在哪天被刷"。同上。 |
| `keyPoints.length` | 否 | §4.4 定义 `s = 勾选数 / 要点总数`。§7 说内容在 Git、构建时同步；§4.2 只保证 `id` 稳定，**明确没有保证 `keyPoints` 稳定**。某张卡的要点从 4 条改成 6 条后，历史日志里"勾了 3 条"的含义从 `0.75` 变成 `0.5` → `n` 从 2 变成 3 → 整条排期变了。这不只影响重放，**它会静默改写用户当前的掌握度和知识地图**。 |
| 算法版本 | 否 | §8 自己说"排期算法必然要反复迭代"。用新代码重放旧日志适合做 A 类用途（回测新算法），但 §8 同时声称 B 类用途（"`card_state` 写坏了也能恢复"）。B 类必须用**当时那个版本**的算法重放，需要版本戳 + 可回溯的代码。两种用途被混为一谈。 |
| 用户在哪些天打开过 App | 否 | log 只记录发生过的复习。用户 day4 该刷没刷、day9 才打开——**逾期卡怎么处理，全文没有任何规则**。而这决定了 day5..day8 的排期状态。没打开的日子在 log 里是空白，无法区分"那天没排卡"和"排了没刷"。 |

**"多设备冲突：`card_state` 按时间戳重算"也不成立**：§8 同时要求断网时本地队列先落 IndexedDB、联网后回传，时间戳只能由**客户端时钟**产生。两台设备时钟偏差或跨时区，排序就错，`s` 就错。而且"按时间戳重算"只能重算 `s`，**重算不出排期**——排期还需要上面那四类输入。

**建议修法**：要么把 `examDate`、`dailyCapacity`、`algoVersion`、`keyPointsTotal`（复习当时的分母）全部作为不可变字段写进每一条 `review_log`，要么把 §8 的表述降级为"`review_log` 足以重算掌握度 `s`，不足以重放排期"。现在这个措辞是一张空头支票。

### S2. 时区与日界完全缺失

**章节**：§5.2、§8

整套算法以"天"为单位（`R = examDate - today`，`d_i` 是天偏移），但文档从头到尾**没有出现过时区、日界、UTC 或本地时间**。而这个产品的目标用户按定义会为了 onsite 面试跨时区移动，§8 又明确要支持断网本地队列。

未定义的具体问题：
- `today` 是 UTC 日期还是设备本地日期？`examDate` 呢？两者不一致时 `R` 差 1，整条 `d[]` 全变。
- 用户 23:50 刷了一批卡，00:10 又打开——是同一天还是新的一天？"今日进度 12/30" 该不该清零？
- 设备 A（UTC+8）在本地 00:10 刷卡，设备 B（UTC-5）此刻还是前一天。"按时间戳重算"排序正确，但两条记录属于哪一天？
- DST 切换那天是 23 或 25 小时，`examDate - today` 用毫秒差再除 86400000 会得到 `.96` 或 `1.04`，`round` 一下就可能少一天。

**建议修法**：在 §5.1 的接口定义里把 `today` 和 `examDate` 的类型钉死为本地日历日（`YYYY-MM-DD` 字符串或 civil date），日差用日历天数计算而非毫秒除法；日界规则（如"凌晨 4 点算前一天"）写进 §5，因为刷题产品的用户会熬夜。

### S3. `n` 表的三个阈值与 `keyPoints` 的离散取值不匹配（三处 off-by-epsilon）

**章节**：§5.2 步骤 1 ↔ §4.2（`keyPoints` 3–6 条）↔ §4.4

`s` 不是连续值。§4.2 规定 `keyPoints` 是 3–6 条，所以 `s ∈ {k/tot : tot ∈ [3,6], k ∈ [0,tot]}`。把 §5.2 的表代进去（脚本 F 节）：

```
3 条:  0/3=0.000→n4  1/3=0.333→n4  2/3=0.667→n3  3/3=1.000→n1
4 条:  0/4=0.000→n4  1/4=0.250→n4  2/4=0.500→n3  3/4=0.750→n2  4/4=1.000→n1
5 条:  0/5=0.000→n4  1/5=0.200→n4  2/5=0.400→n3  3/5=0.600→n3  4/5=0.800→n2  5/5=1.000→n1
6 条:  0/6=0.000→n4  1/6=0.167→n4  2/6=0.333→n4  3/6=0.500→n3  4/6=0.667→n3  5/6=0.833→n2  6/6=1.000→n1
```

三个具体错误：

1. **`s ≥ 0.67` 的边界把 2/3 排除在外**。`2/3 = 0.6667 < 0.67`。作者显然想写的是 2/3（0.34 ≈ 1/3、0.67 ≈ 2/3 是很明显的意图），但十进制写法**恰好落在错误的一侧**。后果：3 要点卡答对 2 条的用户拿到 `n=3`（还要刷三遍），4 要点卡答对 3 条（0.75）的用户拿到 `n=2`。**同样是"大部分说对了"，3 要点卡的用户被多排一遍。**
2. **`s ≥ 0.34` 同理把 1/3 排除在外**。`1/3 = 0.3333 < 0.34` → `n=4`，掉进最差的一档，和"一条都没说出来"、"从没见过这张卡"同档。6 要点卡的 2/6 也一样。
3. **`s ≥ 0.9` 这一行只在 `s = 1.0` 时可达**。3/4/5/6 条卡里，`1.0` 之下的最大值是 5/6 = 0.833。所以"`s ≥ 0.9` 且已复习 ≥3 次 → n=1"实际含义是"**全对**且已复习 ≥3 次"。0.9 这个数字是假的精度，会让实现者以为有一个 0.83–1.0 之间的区间。

**建议修法**：阈值改用分数比较（`3*k >= 2*tot` 而不是 `k/tot >= 0.67`），或者干脆把表改成按"勾选比例的档位"定义并写出每种 `tot` 下的实际分界点。`0.9` 那行直接写 `s == 1.0`。

### S4. §5.2.4 与 §5.3 对同一个条件给出两个互相矛盾的降级规则

**章节**：§5.2.4 第三条 ↔ §5.3 第二段

同一个条件——"窗口装不下 n 次复习"——有两套规则：

- §5.2.4："若 `E < n`，先把 `n` 下调为 `max(1, E)`，再铺**连续日**。"
- §5.3："窗口不足以铺下 n 次时，压到最小间隔序列：**当天稍后、次日、面试前 buffer 天**（按 n 取前几项）。"

失败输入：`R=3`，`s=0.2`（刚答错），`n=4`。`buffer=1, E=2`。

- 按 §5.2.4：`E=2 < 4` → `n := max(1,2) = 2` → 铺连续日 → `d = [1, 2]`（今天什么都没有）
- 按 §5.3：`n` 取前 2 项 → `d = [0(当天稍后), 1(次日)]`（今天有一次）

**两条规则对同一输入给出不同输出，且刚好在"是否今天再刷一次"这个用户可见的点上分歧。** 而 §5.3 触发的条件（`勾选比例 < 0.5`）和 §5.2 的正常路径在 §8 里是同一次 `schedule()` 调用——§8 说每次提交都重跑 `schedule()`，`schedule()` 里已经用新 `s` 算了新 `n`。所以 **§5.3 的第一句话（"重算 s → 重算 n → 用剩余窗口重新铺 §5.2"）是 §5.2 的完全重复，§5.3 唯一的增量内容就是这条和 §5.2.4 打架的降级规则。**

另外 §5.2.4 的"铺**连续日**"本身有三种读法，实现者必须猜：`[1..E]`？`[0..E-1]`？`[E-n+1..E]`？三者给出不同排期。而且 `R=1` 时 `E=0, n=max(1,0)=1`，按 `[1..n]` 读法得 `d=[1]` = 明天 = **面试当天**，这与同一条里"`R ≤ 1` 时全部卡排在今天"直接矛盾，也违反 `d_n = E` 不变量（1 ≠ 0）。

**建议修法**：删掉 §5.3 的第二段，把降级规则收敛到 §5.2.4 一处并写成伪代码；显式写出 `E ≤ 0` 时 `d = [0]`。

### S5. `1:2:4:8` 递增间隔在 `E ≤ 12` 时不成立，`E ≤ 7` 时完全退化为每日复习

**章节**：§5.2 步骤 3 + 4

§5.2 结尾声称："递增间隔（利用遗忘曲线的关键）保留了。" 实算不成立。

先看文档**自己的例子**：`R=21, E=20, n=4 → d=[1,4,9,20]`。
理想累积 `[1.333, 4.0, 9.333, 20.0]`，理想间隔 `[1.333, 2.667, 5.333, 10.667]` = 1:2:4:8 ✓
实际间隔 `[1, 3, 5, 11]` = **1:3:5:11**。第一个间隔被 round 砍掉 25%。这一例还能接受。

小窗口就不行了。`n=4` 时按 `E` 扫（脚本 C 节，`raw` = 公式原值，`forward` = §5.2.4 第一条顺延后）：

| E | 公式原值 | 顺延后 d[] | 实际间隔 | 1:2:4:8? |
|---|---|---|---|---|
| 4 | `[0,1,2,4]` | `[1,2,3,4]` | `[1,1,1,1]` | **完全退化成每日刷** |
| 5 | `[0,1,2,5]` | `[1,2,3,5]` | `[1,1,1,2]` | 否 |
| 6 | `[0,1,3,6]` | `[1,2,3,6]` | `[1,1,1,3]` | 否 |
| 7 | `[0,1,3,7]` | `[1,2,3,7]` | `[1,1,1,4]` | 否 |
| 8 | `[1,2,4,8]` | `[1,2,4,8]` | `[1,1,2,4]` | 否 |
| 12 | `[1,2,6,12]` | `[1,2,6,12]` | `[1,1,4,6]` | 否 |
| 15 | `[1,3,7,15]` | `[1,3,7,15]` | `[1,2,4,8]` | **是**（唯一干净的点）|
| 20 | `[1,4,9,20]` | `[1,4,9,20]` | `[1,3,5,11]` | 否 |

**`E ≤ 12`（即 `R ≤ 13`，一到两周内面试——本产品最核心的使用场景）时，前两个间隔恒为 1 天**，也就是连刷三天再等一段。`E = 4..7` 时是四天连刷。这个场景下算法退化成"连着刷几天"，与"递增间隔利用遗忘曲线"没有关系了。

根因是 `round(E × 1/15)` 在 `E < 8` 时为 0，被 §5.2.4 的 `d_i ≥ 1` 和 `d_i ≥ d_{i-1}+1` 连锁顶成 1,2,3。文档没有意识到这条"顺延"规则会吃掉整个比例结构。

**建议修法**：短窗口下不要靠 round 后打补丁。要么在 `E < 2^n - 1` 时直接降 `n`（保证每个间隔至少能拉开），要么把比例从 1:2:4:8 换成随 `E` 自适应的底数 `b`，使 `d_1 ≥ 1` 自然成立。并在文档里写明"递增间隔"这个性质在什么 `E` 范围内有保证。

### S6. 每次提交重跑 `schedule()` 导致复习次数发散：承诺 3 遍，实际 13 遍

**章节**：§8 ↔ §5.2 ↔ §6 屏③

§8 规定每次提交后"重跑 `schedule()`"。§5.2 的 `d_i` 是**相对当前 `today`、以剩余窗口 `E` 的比例**算出来的。于是每复习一次，`d_1` 就按新的（更短的）窗口重新取一个比例分数——这是典型的芝诺式递推：**每次都只走剩余距离的一小部分，步长随窗口缩短而缩短，复习次数发散。**

失败输入：一张卡，`R=21` 起，用户**每次都通过**（`s = 0.6 → n = 3`）。逐次实算（脚本 G 节）：

```
day  0: R=21 E=20 n=3 d=[3, 9,20] → 下次 day3
day  3: R=18 E=17 n=3 d=[2, 7,17] → 下次 day5
day  5: R=16 E=15 n=3 d=[2, 6,15] → 下次 day7
day  7: R=14 E=13 n=3 d=[2, 6,13] → 下次 day9
day  9: R=12 E=11 n=3 d=[2, 5,11] → 下次 day11
day 11: R=10 E= 9 n=3 d=[1, 4, 9] → 下次 day12
day 12: R= 9 E= 8 n=3 d=[1, 3, 8] → 下次 day13
day 13: R= 8 E= 7 n=3 d=[1, 3, 7] → 下次 day14
day 14: R= 7 E= 6 n=3 d=[1, 3, 6] → 下次 day15
day 15: R= 6 E= 5 n=3 d=[1, 2, 5] → 下次 day16
day 16: R= 5 E= 4 n=3 d=[1, 2, 4] → 下次 day17
day 17: R= 4 E= 3 n=3 d=[1, 2, 3] → 下次 day18
day 18: R= 3 E= 2 → E<n，降级路径（见 S4，行为未定义）
```

**实际复习 13 次（含降级尾巴约 15 次），而这张卡在第一次复习后被告知"还剩 3 遍"。** 从 day11 开始变成每日复习。

这直接把 §6 屏③ 的核心 UI 打成谎言："**下次 2 天后 · 面试前还会再过 2 遍**"配一排圆点——这排圆点每刷一次就重画一次，每次都比上次多。§6 自己说"算法再聪明，用户感知不到就等于不存在"；现在的问题是用户感知到的东西是错的。

同时这也让 §5.5 的 `Σn` 失去意义：`Σn` 按每张卡当前的 `n` 求和，但实际发生的复习次数是 `n` 的 4–5 倍。**超载检测系统性地低估真实负载。**

**建议修法**：`schedule()` 必须有稳定不动点。两个方向：
(a) **计划持久化**：一张卡的 `d[]` 在生成时写进 `card_state`，后续复习只消费不重算；只有 `s` 掉档（`< 0.5`）或 `examDate` 变更才重新生成；
(b) **改成绝对间隔 + 末端截断**：`d_1` 不按剩余窗口比例算，而是按"距上次复习的绝对间隔"算（SM-2 式），只在超过 `E` 时截断到 `E`。这保留了 §3 的核心洞察（收口在面试日），但消除了发散。

推荐 (b)，因为它同时修掉 S5（短窗口退化）。

### S7. §5.1 声明"输入确定则输出确定"，但 §5.4 的排序规则在最常见的场景下零区分度

**章节**：§5.1 ↔ §5.4

§5.4 的挪动优先级是"先按 `frequency` 升序，同频度内按掌握度降序"。这个规则的区分度取决于 `(frequency, s)` 有多少个不同取值：`frequency` 是 3 值枚举，`s` 在 3–6 要点卡上最多 7 个取值。

失败输入：第 0 天，150 张全新卡（F1：`s` 全为 0），`R=7`，`C=30`。需要从 day1 挪走 120 张。
排序键 `(frequency, s)` 只有 3 个不同值（`s` 全是 0）。假设 `high` 组 60 张——**要从这 60 张里挑若干张挪走，排序规则给不出任何依据**。

文档没有规定同键时的 tie-break。实现者会用数组顺序，而数组顺序取决于数据库返回顺序 / `Object.keys` 顺序 / 内容文件遍历顺序——**不在 `schedule()` 的参数里**。这直接违反 §5.1 的"纯函数、输入确定则输出确定"，也让 §7 的"可完整单测"和 §8 的重放都落空。

同类未定义：§5.4 的扫描方向（从 day E 往前扫还是从 day 1 往后扫）会给出不同结果，文档没说。

**建议修法**：排序键末尾追加 `cardId` 作为确定性 tie-break，并在 §5.4 明写扫描方向（应为从 `E` 递减，否则早期溢出会被重复搬运）。

### S8. `s` 无时间衰减、无历史，"没刷过"与"刷了但很差"不可区分

**章节**：§4.4 ↔ §5.2

§4.4："卡掌握度 `s` = **最近一次**的 `勾选数 / 要点总数`；未刷过的卡 `s = 0`。"

三个后果：

1. **无衰减**。§3 的整个立论是遗忘曲线，但 `s` 是一个冻结在上次复习那一刻的值。20 天前满分的卡和昨天满分的卡，`s` 都是 1.0，都拿 `n=1`。**掌握度模型里完全没有时间这个变量**，而这是一个以时间排期为核心卖点的产品。
2. **无历史**。连续 5 次满分的卡，第 6 次因为走神漏了 2 条（`s=0.6`），`n` 立刻从 1 跳回 3，整条排期重来。反过来，第一次碰运气蒙对 4/5（`s=0.8`）的卡直接拿 `n=2`。单次观测做估计量，方差极大。§4.3 说"预测值与实际勾选的差距量化元认知偏差"——这需要历史，但 `s` 的定义里没有历史。
3. **未刷 = 最差**。`s=0`（从没见过）和 `s=1/4`（见过、只说出一条）都落进 `n=4` 同一档。标准 SRS 严格区分 new 卡和 lapsed 卡，因为它们需要的干预完全不同。这里被合并了。

顺带：§5.2 表格第 4 行的条件"**已复习 ≥ 3 次**"引用了一个 `s` 之外的量。`复习次数` 在 §4.2（卡片内容）里没有，§4.4（掌握度）里没有，§8 只提到 `review_log` 和 `card_state`。所以 `card_state` 必须存 `reviewCount`，但文档从未说过——`userState` 参数是个黑盒。同时表格的第 3 行（`s ≥ 0.67 → 2`）和第 4 行（`s ≥ 0.9 且 ≥3次 → 1`）在 `s=1.0, reviews=5` 时同时匹配，**优先级只能从行序推断，没有明文**。

**建议修法**：`s` 改成带衰减的估计量（如按 `exp(-Δt/τ)` 衰减，或直接用 last-N 的加权平均），并把 `新卡` 作为独立状态而非 `s=0`。`card_state` 的字段在 §8 里显式列出。

### S9. §4.4 × §5.5：用户听从产品的建议，知识地图就永远不可能变绿

**章节**：§4.4 ↔ §5.5 ↔ §1

§4.4："块掌握度 = 块内所有卡 `s` 的加权平均，权重按 `frequency`（high=3, mid=2, low=1）。**未刷的卡以 `s=0` 计入**。"
§5.5：超载时建议用户"按 `frequency` 降序取最大前缀"，即只刷高频卡。

失败输入：一个知识块，3 张 high(w=3) + 4 张 mid(w=2) + 3 张 low(w=1)，`Σw = 20`。用户被 §5.5 告知只刷高频，并且**把 3 张高频卡全部刷到满分 `s=1.0`**。

```
块掌握度 = (3×3×1.0 + 4×2×0 + 3×1×0) / 20 = 9/20 = 45%
```

**45% 是这个用户在这个块上的永久天花板。** §1 的用户旅程是"在知识地图上看到哪块**红了** → 刷那块 → ..."。按产品自己的建议执行到完美，地图仍然是红的。用户能做的唯一"变绿"动作，是去刷产品刚刚明确告诉他不要刷的低频卡。

**建议修法**：块掌握度的分母只算**当前排期计划内**的卡，被 §5.5 收窄掉的卡从分母里移除（并在 UI 上单独标注"已排除 N 张低频"）。或者把地图指标从"绝对掌握度"改成"计划完成度"。

### S10. `examDate` 已过去（`R < 0`）完全未定义

**章节**：§5.2、§5.6

这是必然发生的输入：用户设了 9-20 的面试，9-25 才打开 App。`R = -5`。

实算（脚本 H 节）：`buffer = clamp(round(-0.25), 1, 3) = 1`，`E = -6`。
`E < n` → `n := max(1, -6) = 1`，然后"铺连续日"——从哪铺？`d_1 = round(-6 × 1/1) = -6`，**排在 6 天前**。

文档的所有特判都只到 `R ≤ 1`（"今天或明天面试"），`R < 0` 没有任何规则。§5.6 的退化路径只在 `examDate` **为空**时触发，不在它**过期**时触发。所以一个过期的面试日期会让引擎一直算负数窗口。

**建议修法**：§5.2 开头加 `R < 0 → 视同 examDate 为空，走 §5.6，并提示用户更新日期`。这个分支应该是 §11 验收标准第 2 条的第五类边界单测。

### S11. §5.2.4 的"反向压缩"是死代码，永远不会执行

**章节**：§5.2.4 第二条

原文："顺延后若 `d_n > E`，从 `d_n = E` 起反向依次压缩，保证严格递增且末项落在 `E`。"

穷举验证（脚本 D 节，`n = 1..8`，`E = n..3999`，共约 32000 个组合）：**顺延后 `d_n ≠ E` 的情况一例都没有**。

可以证明：`E ≥ n` 时（`E < n` 已被第三条提前降级拦掉），顺延后有 `d_i ≥ i`，而 `d_{n-1}` 的公式原值 `round(E(2^{n-1}-1)/(2^n-1)) ≤ E-1`，加上 `n ≤ E`，所以 `d_n = max(E, d_{n-1}+1) = E` 恒成立。

这本身不造成运行时错误，但它说明**作者对自己算法的行为判断是错的**：作者担心的是"序列会顶出窗口右端"，而真实发生的是相反的事——序列在窗口左端**坍缩成连续日**（S5），而这个才是真问题，文档里一个字都没提。评审提示里问的"反向压缩是否真能收敛"，答案是：它不需要收敛，因为它不会被调用；真正无法收敛的是 `E < n` 且 `d_i ≥ 1` 的约束组（如 `n=2, E=1` 要求 `d_1 ≥ 1, d_2 = 1, d_1 < d_2` 无解），而那种情况靠第三条的 `n` 降级绕开了——绕开的方式又和 §5.3 矛盾（S4）。

**建议修法**：删掉这一条，把省下的篇幅写小 `E` 的坍缩处理。

## 一般

### G1. §5.6 没有可实现的规格，但 §11 要求为它写单测

§5.6 全文是："退化为标准递增间隔（1/3/7/15/30 天）的日常维持模式，按 `s` 决定进档或退档。"

实现者必须自己猜：档位存在哪（`card_state` 没定义）？新卡从第几档起（1 天还是 0 天）？进档的 `s` 阈值是多少（复用 §5.2 的 0.34/0.67？还是 §5.3 的 0.5？）？退档是退一档还是清零？**到了 30 天这一档之后呢**（数列到此为止，是停在 30 还是继续翻倍）？`examDate` 中途被设上时，档位状态怎么映射回 `n`？

§11 验收标准第 2 条明确要求"四类边界单测全绿"，其中一类就是"无面试日期退化"。**当前规格写不出这个测试的断言。**

### G2. `round` 的半值语义未定，`R=50` 时两种实现给出不同排期

`d_i` 不会遇到半值（`(2^i-1)/(2^n-1)` 的最简分母是奇数，`E × 奇数分数` 不可能等于 `k+0.5`），这点没问题。

但 `buffer = round(R × 0.05) = round(R/20)` 会（脚本 I 节）：

```
R=50: 2.5  JS Math.round → 3 → buffer 3 → E=47
           banker's      → 2 → buffer 2 → E=48      ← 不同的 E，不同的整条 d[]
```

对一个声称"纯函数、输入确定则输出确定"的模块，`round` 的语义应该在 §5.2 里钉死。

### G3. `buffer` 公式里的 `× 0.05` 在 `R < 30` 时是死参数

实算（脚本 B 节）：

```
R:    2  3  5  7 10 14 20 21 29 | 30 40 | 50 60 100
buf:  1  1  1  1  1  1  1  1  1 |  2  2 |  3  3   3
```

`R ≤ 29` 时 `round(R/20) ≤ 1`，被 `clamp` 下界吃掉；`R ≥ 50` 时被上界吃掉。**这个公式只在 `R ∈ [30, 49]` 这个区间里真正起作用，其余全是常数。** 而产品的主场景（1–3 周备考）落在常数区。不是 bug，但"面试前留白按 5% 比例"这个说法与实际行为不符，文档应该直说"buffer 固定 1 天，长窗口最多 3 天"。

### G4. §5.4 可能把同一张卡的多次复习压到同一天

`d=[1,2,3,6]`（`R=7` 场景，S5 已证明短窗口必然产生这种紧凑序列）。day3 超载把某张卡的第 3 次挪到 day2，而它的第 2 次已经在 day2。**同一张卡同一天出现两次。** F2 的实算里，150 张卡平均有 2.8 次复习落在 day0。

文档对"卡被挪到它已经占据的那一天"没有任何规则：合并成一次？保留两次？还是继续往前挪？三种处理的语义和负载计算都不同。

### G5. §5.3 的"当天稍后"没有任何操作性定义

"稍后"是队列末尾？隔 N 张卡？隔 M 分钟（但 §5.1 说 `schedule()` 不读时钟，只有天粒度，压根表达不了"分钟"）？`schedule()` 的返回类型 `todayQueue` 是有序数组还是集合，文档没说，但"稍后"这个语义要求它必须有序并且能表达插入位置。

### G6. §5.5 的文案数字与 §10 的范围互相矛盾
