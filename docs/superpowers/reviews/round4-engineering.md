## 先说可以放心的地方

四条常见担忧，查证后不是问题。写在前面，免得实现计划里浪费工期：

1. **排序稳定性不是风险。** ES2019 起规范要求 `Array.prototype.sort` 稳定；V8 自 7.0 / Chrome 70 起用 TimSort，SpiderMonkey 与 JavaScriptCore 一直是稳定的（[v8.dev/features/stable-sort](https://v8.dev/features/stable-sort)）。而且 §5.1 已经要求所有排序键末尾追加 `cardId`，同键本就不存在。**唯一要守的是比较函数良构**——必须返回带符号的值，写成 `(a,b) => a > b ? 1 : 0` 会让 V8/JSC 原样返回而 SpiderMonkey 正常排序，这是引擎间差异的真实来源。加一条 ESLint 规则即可。

2. **浮点不是风险。** §5.2 已经把 `s` 钉成整数分子/分母 + 交叉相乘，`INTERVALS` 是整数，`E` / `offset` / `buffer` 全是整数天。整条排期链路没有浮点。要守住它，在 `lib/scheduler` 里禁掉浮点字面量即可。

3. **IndexedDB 容量不是问题。** 一条中文要点 30-60 字约 90-180 字节 UTF-8；一个大类约 900 条要点合计 **80-160 KB**，全库 6,300 条要点约 **0.6-1.1 MB**，加上全部 `detail` markdown 也就几 MB。而 Chrome 全局配额按磁盘比例（数十 GB 量级）、Firefox 每源可到剩余磁盘 50%、Safari 主屏 App 60%（[MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)）。**"本地存不下"是个假问题——真问题是"不该给的内容给出去了"（E2）。**

4. **构建时全量同步 1400 题不是问题，不需要做增量。** 1400 行、几百 KB、一个事务、亚秒级。§7 那句"构建时同步进库"在数据量上完全成立。真问题是它把内容发布和应用部署耦在一条流水线上（E13），那是另一回事。

## 致命

### E1. §8.3 把 `plan[]` 变成多写者字段，而 §8.2 已声明它不可重建 —— 这是全文唯一一处"数据坏了没有恢复路径"

**严重程度：致命。所在章节：§8.3 × §8.2 × §5.5 × §6。**

`card_state` 里的字段分两类：`s` / `reviewCount` 是**派生的**（§8.2：`review_log` 自带 `keyPointsTotal`，足以重算），`plan[]` 是**权威且不可重建的**（§8.2 明写"`card_state` 写坏后完整恢复排期做不到，只能按当前设置重新生成计划"）。

§8.3 现在要往这个不可重建的字段上放第二个写入者。

**具体失败序列：**

1. 用户在地铁上断网，刷今天的 40 张卡（计划已落盘，能刷，这部分 §8.3 是对的）。
2. 第 7 张答错，勾选比例 `< 1/2`。§5.5 触发"起始档退回 0，从明天起重新生成"。**此时客户端必须跑 `schedule()`。**
3. 之后又错 5 张 → 客户端一共跑了 6 次重新生成。
4. 出站联网，回传。服务端面对两个选择，**文档没有选**：
   - **接受客户端的 `plan[]`**：用户中午在公司电脑上也刷了两张、也触发过一次重排——那份 `plan[]` 被静默覆盖。§6 明写"圆点答对时只会少一个，不会重画"，这里它会整排重画；而且服务端无从判断这次同步是"正常消费"还是"重排"，§6 要求的"计划已重排"提示**不会弹**。文档自己的判词："用户感知到的东西是错的，比感知不到更糟。"
   - **服务端重放**：要求服务端 Node 与客户端浏览器对同一输入逐字节同结果，且要按正确顺序重放那 6 次重排（顺序变了结果就变，因为 §5.3 的装箱依赖当时的占用状态）。
5. 两条路走到哪一条出问题，§8.2 都已经提前说了没有恢复手段。

**顺带暴露一个规格空洞：§5.5 没说"重新生成"的作用域。** 是只重排这一张卡（把它的新阶梯装进现有的占用图，别的卡不动），还是重跑整个选中集合（那 §5.2 ④ 的 `newPerDay` 排位和末端窗口 `fw = ceil(计划内卡数 / dailyCapacity)` 都要重算，**所有卡的末次都可能挪位**）？两种读法给出不同的 `plan[]`、不同的圆点。而对离线来说这个差别决定了客户端要带多少数据：单卡重排只需要一张占用图（几百字节），全集重排需要全部选中卡的状态。**文档没给出足以做这个决定的信息。**

**关于"逐字节一致"这件事本身**——排序和浮点都不是风险（见上一节），但有一处真的不一致：

**日期。** `today` 是输入没错，但"今天是几号"要按 §5.1 的本地 04:00 日界算出来，这一步依赖时区数据。已查证：JS 引擎的时区数据来自各自打包的 ICU 快照，版本会漂移——Node 至今有 issue 追踪其 ICU tzdata 落后于 IANA 2026a（[nodejs/node#62323](https://github.com/nodejs/node/issues/62323)）；历史上 `Europe/Kyiv` 在 Node 18.7 抛 `RangeError` 而 `Europe/Kiev` 正常（[nodejs/node#44333](https://github.com/nodejs/node/issues/44333)）。浏览器端你完全控制不了 ICU 版本。对主场景（`Asia/Shanghai`，自 1991 年起无 DST）风险很低，但 §11 自己把"DST 切换日 / 跨时区"写进了验收标准。

**建议修法（按代价从低到高，推荐第一条）：**

- **方案 A（推荐，几乎零成本）：离线只读不重排。** 客户端断网时**只消费已落盘的计划，不跑 `schedule()`**。答错时本地不重排，只把提交入队，UI 显示"计划将在联网后更新"。联网后由**服务端**按队列顺序逐条重放 §5.5，**服务端是 `plan[]` 的唯一写者**。
  这条修法消灭 E1 的全部分支，且不违反"断网也能刷完当天的量"——**当天的量来自已落盘的计划，本来就不需要重排**；§5.5 自己也规定答错是"从明天起"重排，当天不会再见到这张卡。
  §7 那句"排期引擎是纯函数，客户端可同构运行"要改成"**客户端只读计划，不生成计划**"。同构运行仍然有用，但用在 §11 的一致性测试上（同一份输入在 Node 与 headless 浏览器里跑出同一份 JSON），不用在生产写路径上。
- **方案 B：** 客户端可重排，但结果只是本地预览；服务端重放后以服务端为准，差异回传时显式提示"计划已重排"。工作量大一个数量级，换来的只是答错后立刻看到新圆点。不值。

**另外三条必须补的（都属于方案 A 的范围内）：**

- **幂等键。** 回传队列每条必须带客户端生成的 `submissionId`（ULID / UUIDv7），`review_log` 上建唯一索引。文档写 `review_log` append-only"天然无冲突"——**append-only 消除的是写冲突，不是重复提交**，这两件事被混为一谈了。超时重试 = 重复日志 = "最近 3 次"里塞进两条同一次提交 = `s` 错 = 起始档错 = 计划错。
- **顺序。** `s` 是 `3:2:1` 加权，顺序敏感。服务端必须按 `reviewedAt` 排序后重算，而 `reviewedAt` 是客户端时钟（§8.3 自己承认有偏差）。至少要在同一 `submissionId` 序列内保序，并对明显异常的时钟（早于上一条、晚于服务端 now 超过阈值）做钳制并记录。
- **日界的唯一判定方。** `localDate` 只由**服务端**算，用用户设置里存的 IANA 时区 + **锁定版本的 tz 库**（不是 `Intl`），不用客户端上报的日期。客户端离线期间可以用自己的判断临时排队，同步时由服务端重新归属。见 E6。

### E2. 第 2 层干扰项必须跨块取，而免费用户没买那些块 —— 三方冲突，且有解

**严重程度：致命。所在章节：§4.3 × §10.1 × §8.3 × §6。**

§4.3 要求 3 条干扰项里 **2 条来自"同大类其他块"**（池约 900 条要点）。§10.1 规定免费用户只解锁 **2 个块**（约 30-50 题，约 180 条要点）。这两条硬冲突。

**先算泄露量。** 免费用户刷完 2 个块一轮：40 题 × 约 6 次复习（§5.6 的数）= 240 次出题，× 2 条跨块干扰项 = **480 次跨块抽取**。在 900 条池上抽 480 次，期望见过的不同要点数：

```
900 × (1 − e^(−480/900)) ≈ 900 × 0.413 ≈ 372 条
```

**372 条要点 ≈ 83 道题的完整答案要点**，而免费层本身只有 30-50 题。也就是说，免费用户**通过正常 UI、不碰任何开发者工具**，就看到了他没买的约 83 道题的答案。

**更狠的是 §6 屏②。** 文档明写："错勾的选项要显示**它实际属于哪道题**——这是本方案独有的信息。" 于是泄露的不只是要点文本，还有 **(要点 → 题) 的归属关系**——那正是付费内容的结构本身。每错勾一次，用户白拿一条带归属的答案。

**再加上离线。** §8.3 要求断网能刷，那这 900 条跨块要点必须**预先下载进 IndexedDB**。那就不是"看到 372 条"，是"本地完整存着 900 条"，改前端就能全读。

**付费用户也有一个没人提过的问题：内容加载范围 ≠ 排期范围。** §5.6 说"`schedule()` 的 `cards[]` 永远是选中子集"，但 §4.3 说干扰项要从"同大类其他块"抽。于是用户哪怕只选 1 个块，也得把**整个大类**（8-12 块、约 900 条要点）拉到本地。文档没有任何一处说过这件事，而它直接决定了同步 API 的形状。

#### 这个冲突有解，而且解很便宜

关键观察：**E8 里为了 SEO，公开题目页上本来就要放出一部分要点（lead-in）。那部分要点是公开的，泄露成本为零。用它做免费层的第 2 层干扰池。**

具体方案：

| | 第 1 层（同块） | 第 2 层（跨块） | 泄露 | 离线 |
|---|---|---|---|---|
| **免费用户** | 1 条，从已解锁的 2 个块抽 | 2 条，从**本大类的公开 lead-in 要点池**抽 | 零（本来就公开） | 成立 |
| **付费用户** | 1 条，同块 | 2 条，从整个大类抽（他买了） | 不适用 | 成立 |

若每个大类的约 200 道题各公开 1-2 条 lead-in 要点，公开池 = **200-400 条**。免费用户 240 次跨块抽取在 300 条池上，期望见过 `300 × (1 − e^(−240/300)) ≈ 165` 条，即 55%。不理想，但远好于下面这个替代方案。

**为什么不能简单地让免费层走 3:0（全从同块抽）**：20 题的块 × 6 次复习 × 3 条 = **360 次抽取，90 条池** —— 这正是 §4.3 开头自己算出并否定的那个 **98.2%** 场景。免费层恰恰是唯一一个必须演示"机制有用"的地方（§10.1 的三条理由之一），在那里让机制退化，等于演示产品**不能**做什么。第 3 轮对旧的"分散 300 道"设计下过同样的判词；换成"2 个完整块"之后，第 1 层没问题了，**但第 2 层的问题原封不动地留着**，文档把它当成已解决。

**同时必须改的两处实现：**

1. **干扰项在服务端抽，客户端只拿渲染好的选项。** 取今日队列时（一天一次），服务端为队列里每张卡**预生成未来 K 次的选项集** `{ optionTexts[], correctIndices[], distractorKeyPointIds[] }`，随队列一起下发并落 IndexedDB。这样：离线成立（今天的量已在本地）、§4.3 的"每次重抽"成立（每次取预生成序列的下一项）、`review_log.distractorIds` 真的可复现、**未解锁块的要点永远不出现在客户端的完整语料里**——只出现在已渲染好的选项文本里，且只出现被抽中的那几条。
2. **屏②的"这条属于哪道题"对未解锁块降级**：显示为"属于本大类的另一道题（未解锁）"。保住"你把 A 和 B 搞混了"的一半信息价值，堵住归属关系泄露，顺便是一个自然的转化点。

### E3. "改变选中的知识块"不在 §5.5 的重生成触发条件里 —— 而那是产品的核心交互

**严重程度：致命。所在章节：§5.5 × §5.6 × §10。**

§5.5 列了三个触发条件：答错、`readyByDate` 变更、`dailyCapacity` 变更。

§10 的"做"清单第 2 条是"**块级选择**：用户勾选这轮要刷哪些块"。§5.6 推论 1 是"排期只作用于用户选中的知识块"。§5.6 推论 3 说知识地图与超载收窄"合起来才兑现核心承诺"。

**产品最核心、最高频的用户动作，在排期侧没有定义的语义。**

**具体失败序列：**

1. day0，用户在地图上勾「MySQL 索引」「Redis 持久化」，`schedule()` 生成计划落盘。
2. day3，用户想起来还要考并发，加勾「AQS 与锁」（20 张新卡）。
3. §5.5 的三个条件一个都没命中。实现者必须自己选，两条路都坏：
   - **不重排**：新块 20 张卡 `phase = new`、`plan[] = []`，永远不进 `todayQueue`。用户勾了块，什么都没发生。
   - **全局重排**：§5.2 ④ 的 `newPerDay` 排位和末端窗口 `fw = ceil(计划内卡数 / dailyCapacity)` 都要按新的卡数重算——**原来两个块里每一张卡的末次都可能挪位，全部圆点重画**。§6 明写这是"比感知不到更糟"的情形。
4. **取消勾选更糟。** 用户 day3 取消「Redis 持久化」，那 20 张卡的 `plan[]` 还在 `card_state` 里。它们还进不进 `todayQueue`？§5.5 的"逾期卡并入下次打开时的 `todayQueue`"没有"除非用户取消了这个块"的例外条款。实现者只能猜，而猜错的表现是"我明明取消了，它还在给我出题"。

**建议修法：§5.5 加第 4 条触发条件「选中块集合变更」，并明确三件事：**

- **加块**：只为**新增块**的卡生成计划，**不动已有卡的计划**。新增卡装箱时把已有计划占用的容量算作**已占用**——这需要 E4 的签名修改，**E3 和 E4 是同一个缺口的两面**。末端窗口对新增卡单独算，可能轻微突破 I5（已有计划的末端窗口与新卡的撞在同几天），必须走 §5.4 告警。
- **减块**：`phase` 加第四个状态 `paused`。被取消的块的卡置 `paused`，`plan[]` 保留但不进 `todayQueue`；重新勾选时按剩余窗口续上。当前 `phase` 的三值枚举（`new` / `learning` / `done`）少这个状态。
- **§11 加三条验收**：加块不动老计划；减块不进队列；加减往返后计划一致。

### E4. §5.8 临时加密在 §5.1 的 `schedule()` 签名下实现不出来

**严重程度：致命。所在章节：§5.8 × §5.1 × §5.3 × §5.4 × §11。**

```
schedule(cards[], cardStates[], readyByDate, dailyCapacity, today)
```

签名里没有"已被 `cards[]` 之外的卡占用的容量"这个参数。而：

- §5.8 要求"只重排选中块，**不影响其他块的计划**"。
- §5.3 的装箱规则是"中间次遇到**当天已满**→ 往后推一天"。
- **"当天已满"的判断需要知道当天的总负载，包括不在 `cards[]` 里的卡。**

**具体失败场景：**

用户周三接到周五的字节面试，按 §5.8 勾 MySQL + Redis（60 张卡），`readyByDate` = 周四。这 60 张卡按 §5.2 铺进周三/周四。装箱时 `schedule()` 看到 day0 用了 0/45、day1 用了 0/45 —— 因为它的输入里只有这 60 张。装得下。

但用户原本的计划在周三、周四各有 40 张其他块的卡。**实际负载 = 40 + 30 = 70，超容量 56%。** I5 被违反，而 `schedule()` 内部无从知晓；§5.4 的前缀和判据也只看 `cards[]`，**不告警**。

用户体验：周三打开 app 看到 70 道题（约 25-30 分钟，承诺 15-20 分钟），**产品在它最该可靠的那天（面试前一天）超载 56% 且一声不吭**。§5.6 同样依赖这条（"`cards[]` 永远是选中子集"），只是症状没这么急。

**更坏的是 §11 有一条验收标准会把这个 bug 盖住。** §11 写的是"§5.8 临时加密：只重排选中块，其余块计划不受影响"。这条断言在当前签名下**写得出来而且会通过**——其余块的 `plan[]` 确实没变。但它只测了一半：**没测 I5 是否仍然成立**。一个会通过的半截测试，比没有测试更危险。

**建议修法（纯加参数，不破坏零依赖）：**

```ts
schedule(
  cards: Card[], cardStates: CardState[],
  readyByDate: LocalDate, dailyCapacity: number, today: LocalDate,
  reservedLoad?: ReadonlyMap<number /* dayOffset */, number /* count */>
)
```

`reservedLoad` 由调用方从"不在 `cards[]` 里但有计划的卡"汇总。§5.3 的装箱与 §5.4 的前缀和都先减去它。`lib/scheduler` 仍然纯函数、零依赖、可完整单测。

**这个参数必须现在加**：§5.6（只排选中块）、§5.8（只重排部分块）、E3（加块不动老计划）三条都依赖它。而 §11 那条验收标准要改成"其余块 `plan[]` 逐字节不变 **且** 重排后每一天的总负载仍 ≤ `dailyCapacity`"。

### E5. 选项总数 = 正确条数 + 3 —— 用户数一下选项个数就知道该勾几条

**严重程度：致命。所在章节：§4.3。纯逻辑问题，不需要查证。**

§4.3 的出题规则逐字抄下来：

> **出题规则**：正确要点全出（3-6 条），干扰项抽 3 条，合计 6-9 个选项。**不告诉用户有几条是对的**，否则用户会数数做排除法。

正确条数 3-6 可变，干扰项固定 3 条 ⇒ **选项总数 − 3 = 正确条数**。

用户不需要被告知。他只要数一遍屏幕上有几个选项，减 3，就是该勾的条数。这个规律一眼可见，第二次刷题就会被发现，之后每一道题都能靠"勾出看起来最像的那 N 条"做，而 §4.4 的扣分机制（`勾对 − 勾错`）此时反而在帮他——知道 N 之后，多勾没有收益，少勾没有收益，恰好勾 N 条是最优策略，而且他不需要真的理解内容。

**这条直接推翻 §4.3 自己写的设计目标，也削弱 §12 ④ 那个单点赌注**（"反复辨认一道题的完整要点结构能否迁移成口述"——如果用户是在做"选 N 个最像的"而不是"判断每一条是否属于这道题"，被反复曝光的就不是要点结构）。

**建议修法（两个方向，选一个写进文档）：**

- **A. 选项总数恒定。** 固定为 9：正确 3 条配 6 条干扰项，正确 6 条配 3 条。代价：干扰项抽取次数从平均 3 次/题升到 4.5 次/题（**+50%**），直接放大 §4.3 的枯竭和 E2 的泄露量。
- **B. 总数在一个小集合里随机，但保证不可反推。** 例如总数从 `{8, 9, 10}` 随机取，干扰项数 = 总数 − 正确条数，并强制干扰项 ≥ 2。当正确条数为 6 时总数只能是 8/9/10 → 干扰 2/3/4；当正确条数为 3 时 → 干扰 5/6/7。用户数出 9 个选项，正确条数可能是 3、4、5、6 中任意一个。抽取次数平均约 4.5 次/题，和 A 差不多。

**推荐 B**，因为 A 在"正确 3 条"的卡上会稳定地给 6 条干扰项，反过来也构成一个可学习的信号（"选项越多，对的越少"）。B 需要在文档里写死总数分布和 `≥ 2` 的下界，并在 §11 加一条断言：**任意一组出题参数下，从选项总数无法唯一确定正确条数。**

无论选哪个，池消耗都会涨 50%，E2 的方案要按新数字复核一遍。

### E6. `review_log` 缺 `localDate`、时区、幂等键 —— §11 有一条验收标准因此测不了

**严重程度：严重。所在章节：§8.1 × §5.1 × §8.3 × §11。**

§5.1 把日界定在本地 04:00，§8.3 说"'属于哪一天'按 §5.1 的本地日界单独判定"。但 §8.1 的字段清单里**判定所需的输入一个都没有**：只有 `reviewedAt`（UTC 瞬时）。要还原"属于哪一天"，需要**复习当时**用户所在的时区。

**具体失败场景：** 用户在上海刷了两周，去新加坡面试，手机时区自动切换。回看历史时，同一批 `review_log` 记录被算进不同的本地日。§5.5 的逾期卡判定（"计划日已过但没刷"）、§6 的今日进度分母、§4.4 的"最近 3 次"边界全部跟着漂。

而 §11 的验收标准里有一条："**DST 切换日 / 跨时区：日差按日历天计算，不偏移**"。在数据层缺输入的情况下，这条**只能测 `lib/scheduler` 的纯函数部分，测不了端到端**。

**建议修法：**

- `review_log` 加三列：`localDate`（`YYYY-MM-DD`，按 04:00 日界算好的归属日）、`tz`（IANA 名，如 `Asia/Shanghai`；**存 offset 不够，offset 反推不出 DST 规则**）、`submissionId`（客户端生成，唯一索引，E1 的幂等键）。
- `localDate` **只由服务端算**，用存在用户设置里的 IANA 时区 + **锁定版本的 tz 库**，不用 `Intl`（引擎间 ICU 版本漂移，见 E1 的查证）。客户端离线期间可临时判断用于排队，同步时由服务端重新归属。
- tz 库版本记进 `algoVersion` 或单列一列——否则 tzdata 升级会让历史归属静默改变。
- 若决定不补齐，则 §11 那条验收标准要**显式降级**为"仅 `lib/scheduler` 层的日历天运算测试"，别让它假装覆盖了端到端。

### E7. 干扰项抽取没有任何可测规格 —— 而它是"整套设计能成立的支点"

**严重程度：严重。所在章节：§4.3 × §11 × §8.1。**

§4.3 自称是"整套设计能成立的支点"，§11 为它写了 **0 个测试**。而它有四个洞，每个都必须由实现者自己发明：

1. **随机源没有定义。** §4.3 说"每次出现重抽干扰项、重排顺序"。如果实现者用 `Math.random()`：
   - 不可单测（没有可控输入就没有可断言的输出）；
   - §8.1 存 `distractorIds` 声称"不存就无法复现这一次到底考了什么"——用 `Math.random()` 只能**记录**，不能**复现**；
   - 服务端无法校验客户端离线时抽的结果。

   **修法一处解决三件事**：`drawDistractors(card, pool, rng): Distractor[]`，`rng` 由 `seed = hash(userId, cardId, reviewIndex)` 构造的确定性 PRNG（xoshiro / sfc32 之类，十几行）。可单测、可复现、可校验。这也是 E2 方案里"服务端预生成选项集"的前提。

2. **池不足时的降级规则不存在。** §2 说每块 15-25 题，取下界 15 题 × 4.5 = 67 条要点池，减去本题的要点、减去 `excludeAsDistractorFor` 命中的（§4.3 预计 5-10%），第 1 层还剩约 56 条，够。真正的窄边是 **E2 的免费层**、以及新大类只有 2-3 个块的过渡期。文档没有 fallback。三条可能的路**都改变可见行为**：少给干扰项（配合 E5 会直接泄露正确条数）、重复抽同一条（用户立刻发现）、跨大类抽（§4.3 明确说只分两层）。必须选一条写死，并在 §11 加一条"池不足"的边界测试。

3. **分层比例的调节规则没有公式。** §4.3 说"掌握度越高，同块层占比越大（2:1 甚至 3:0）"。`s` 的哪个值对应 2:1？哪个对应 3:0？实现者要自己发明阈值——而 `s` 是精确有理数（§5.2 的硬要求），**阈值也必须写成分数**，否则会原样重演 §5.2 记录在案的那个 `2/3 = 0.6667 < 0.67` 的 bug。给一张和 §5.2 起始档表同构的分数表即可。

4. **`excludeAsDistractorFor` 的查询方向需要一张物化表。** 字段语义是"本要点对**这些题**也成立"，而抽取时要做的是反向查询：给定目标题 T，排除所有 `excludeAsDistractorFor` 含 T 的要点。需要 `Map<cardId, Set<keyPointId>>` 反向索引。内容同步时要额外物化这张表，§7 / §8.1 的存储结构里没有它。

### E8. SSR 长尾获客与付费墙：三条路各有明确代价，且公开页在 §7 的架构图里不存在

**严重程度：严重。所在章节：§7 × §10.1。**（第 2 轮已评过这条渠道的胜算，本轮只谈技术上做不做得出来。）

**先修正一个定性：给爬虫全文、给用户付费墙，不必然是 cloaking。** Google 官方文档明写结构化数据的目的就是区分这两者：

> "Enclose paywalled content with structured data in order to help Google differentiate paywalled content from the practice of cloaking, where the content served to Googlebot is different from the content served to users."
> —— [Google Search Central, Flexible Sampling](https://developers.google.com/search/docs/appearance/flexible-sampling)

构成 cloaking 的是**按 User-Agent 分发不同 HTML**。合规做法是给所有人发同样的 HTML，用客户端 JS/CSS 遮住，并用 `isAccessibleForFree: false` + `hasPart` 标注（[Paywalled content 结构化数据](https://developers.google.com/search/docs/appearance/structured-data/paywalled-content)）。

**但同一页上 Google 还写了另一句，正好是本产品的死结：**

> "If you don't want the content to be accessible to the browser at the time of serving, choose a paywall implementation that doesn't supply the paywalled content to the browser."

翻译：**想要真付费墙，就别把内容发给浏览器；而没发给浏览器的东西，Googlebot 也看不到。**

于是三条路，每条的技术代价：

| 路 | 实现 | 付费墙 | 可索引正文 | 对 §4.3 的影响 |
|---|---|---|---|---|
| **A** 全文进 HTML + 结构化标注 | 合规 | **形同虚设**，`curl` 即可 | 最好 | **干扰项池全部公开**，§4.3 的机制被掏空 |
| **B** 只进 lead-in（题面 + 1-2 条要点） | 有效 | 只有题面 + 一两句 | 池不泄露 |
| **C** 按 UA 分发 | — | 有效 | 属 cloaking，降权/移除风险 | — |

A 的额外杀伤必须说清楚：`keyPoints` 不只是付费内容，**它还是干扰项池**（§4.3："`keyPoints` 一份内容同时干两件事——这是整套设计能成立的支点"）。全文公开等于把那个"未公开的、专业的、似是而非的陈述池"公开了。这不只是内容被白嫖，是产品机制被掏空。

**推荐走 B，并把公开出去的那部分直接当作 E2 的免费层干扰池**——一箭双雕，公开页上的要点本来就公开，用它们做免费用户的第 2 层，付费墙一点不漏。

**两条必须写进文档的连带结论：**

1. **停止把 SEO 当作选 Next.js 的"实际理由"。** B 路线下公开页是纯静态的，任何静态站生成器都能做。Next.js 的正当理由是别的（团队熟悉、App Router + RSC 的开发效率、刷题 SPA 和公开页同仓库），把理由写对，免得后面有人拿"我们是为 SEO 选的 Next"去论证别的决策。
2. **`/q/[slug]` 在 §7 的目录树里根本不存在。** §7 只有 `app/(drill)/` 和 `app/map/`。整个获客押注所依赖的那个页面，架构图里没有位置。而且它和刷题主循环需要**两套完全不同的渲染与缓存策略**：公开页要静态/ISR、可被 CDN 缓存、可被爬虫抓；刷题页要带用户态、要能被 Service Worker 预缓存以支持离线。Next.js 做得到，但必须在实现计划里分成两个 route group 并各自定档。

### E9. 内容 id 由人手写、无跨提交稳定性守卫 —— 一次目录重构就能静默报废 25-60 小时的互斥登记

**严重程度：严重。所在章节：§7 × §4.2 × §8.1 × §8.3。**

§4.2 要求 `id` "稳定标识。间隔重复要求同一道题在整个复习周期内 ID 不变"，`KeyPoint.id` "块内唯一"。§7 说内容是 Git 里人手写的 Markdown/YAML，示例文件名是 `001-aqs-exclusive-lock.md`。

**谁生成 id、怎么保证不重复、重构目录时怎么不破坏 `card_state`——文档一个字都没写。**

三个具体失败场景：

1. **序号派生 id。** 如果 id 来自文件名/序号，在 `001` 和 `002` 之间插一道题就要重编号 → 所有下游 id 变 → `card_state` 全部对不上 → **用户的复习进度归零，而且是静默的**：新 id 的卡 `phase = new`，在产品里看起来像"上新内容了"，不像事故。
2. **`KeyPoint.id` 块内唯一 + 人手写。** 两个作者在同一个块的不同文件里各加一条 `kp-7`。Git **不会**产生冲突（不同文件、无文本重叠），只有校验器能发现。而 §8.3 写的校验是"要点少于 3 条或缺 `sources` 的卡直接构建失败"——**per-card 校验，抓不到跨文件碰撞**。
3. **跨提交稳定性无人守。** 没有任何机制阻止 id 在两次构建之间消失或改变，`validate.ts` 看到的只有当前工作树。而 `review_log.distractorIds` 存的是 keyPoint id、`excludeAsDistractorFor` 存的是 card id——**id 一动，历史日志和互斥登记一起变成悬空引用。互斥登记是花了 25-60 小时人工做出来的（§9.1），一次重构就能报废其中一部分，而且没有任何东西会报错。**

**建议修法（都很便宜，但必须在写第一道题之前就位）：**

- **id 由脚手架生成，不由人写。** `pnpm content:new <block>` 铸一个 ULID/nanoid 写进 frontmatter，人只写内容。文件名与 id 解耦，文件随便改名。
- **CI 加跨提交 id 守卫。** 把上一次 `main` 的全量 id 集合作为 lockfile（`content/.ids.lock`）提交；CI 比对，id 消失或改变即构建失败，除非同一个 PR 里显式写了 `movedFrom` / `retiredAt`。
- **校验必须是全库一次性，不是 per-card。** id 全局唯一、`KeyPoint.id` 块内唯一、`excludeAsDistractorFor` / `relatedBlocks` 指向存在的 id、每块干扰项池容量 ≥ 阈值（E7 第 2 点）。`lib/content/validate.ts` 当前的定位撑不住这些，要么扩展它，要么单列 `lib/content/audit.ts`。
- **删除用 tombstone。** `retiredAt` 标记，不真删——`review_log` append-only 且引用 `cardId`。

**量级：3-5 人日。** 不做的代价是 §9.1 那 25-60 小时的人工成果随时可能静默蒸发。

### E10. 审核工具在 §7 里没有落点，且它的运行形态与生产部署形态互斥

**严重程度：严重。所在章节：§9.1 × §7 × §10。**（第 3 轮已估 40-80 h，本轮不重估。）

§10 把审核工具列进"做"清单，§9.1 末段和 §10 的内容轨顺序都要求它**排在内容生产之前**——也就是说它是整个项目第一个要交付的东西。而 §7 的架构里没有它的位置。

**它的运行形态被一条硬约束钉死：它必须写回 Git 工作树。** `excludeAsDistractorFor` 的确认结果要落进内容源文件（§7：内容进 Git 不进 CMS，审核走 PR）。需要文件系统写权限 ⇒ **它不可能是部署在 serverless 上的那个 Next.js 应用**（只读 FS、没有本地工作树）。

**所以它只能是本地运行的独立工具**：`tools/reviewer/` 下一个本地 web 应用（Vite + 一个直接读写 `content/` 的本地 HTTP server），或 CLI + 本地 UI，产出 PR。**建议在 §7 的目录树里加一级 `tools/`，并注明它不进生产构建。** 这件事必须在下周就定，因为它是第一个开工的模块。

**它的 LLM 召回管线有三条不能省的工程属性**（§4.3 的 120,000 次判断）：

- **可断点续跑**——限流、崩溃、跑到一半改了内容。
- **按 `(要点内容哈希, 目标题内容哈希)` 缓存结果**——内容轨有 145-220 小时的持续编辑。
- **人工确认队列要有持久化状态**——8,500-17,000 条确认（§4.3 的 5-10% × 120,000）不可能一次做完，必须能中断续做，且内容改动后受影响的条目要能重新入队。

**推理成本不是约束，这点值得说破，免得实现计划为了省几十块钱去做复杂的增量逻辑。** 按每块缓存一次该块全部要点上下文（约 7,000 token）、每条要点一次调用（70 块 × 90 要点 ≈ 6,300 次调用）、每次输出约 200 token 估算：约 4,400 万输入 token + 126 万输出 token。**即使完全不计 prompt caching 折扣**，按 Haiku 4.5（$1 / $5 每百万 token）约 **50 美元**，Sonnet 5（$2 / $10）约 **100 美元**；走 [Batch API](https://www.anthropic.com/pricing) 再打五折。**全量重跑一次的钱可以忽略——做缓存的理由是"别让一次内容改动导致几小时等待和人工队列重置"，不是省钱。**

（这三条属于第 3 轮 40-80 h 估算里大概率没算的部分，但本轮不重新给数字。）

### E11. 权限 × 选块 × 收窄三层筛选没有归属层，而 §11 一个测试都没有

**严重程度：严重。所在章节：§7 × §5.6 × §10.1 × §4.4 × §11。**

三层筛选：

- **(a) entitlement**：用户买了哪些块（§10.1）
- **(b) selection**：这轮勾了哪些块（§5.6、§10）
- **(c) narrowing**：§5.4 的超载收窄按 `(frequency 降序, cardId 升序)` 砍掉哪些卡

§7 的分层是 `app → server → lib`，`lib/scheduler` 零依赖；§5.6 说 `schedule()` 的 `cards[]` 是筛好的子集。**三层筛选于是全落在 `server/`——那个有 DB 访问、最难单测的层。** §11 第 2 条列了 11 条 scheduler 边界测试，这三层的组合**零测试**。

**而顺序会改变结果。** §5.4 的收窄建议如果跑在**未限权**的集合上，建议里会包含用户买不到的卡。这不是小事：§5.6 说收窄屏是"核心交互"、§10 说它同时是**付费转化入口**。**产品的主交互屏兼付费转化屏，它的输入集合边界未定义。**

另外 §4.4 要求"被 §5.4 收窄排除的低频卡不进分母，UI 上单独标注'已排除 N 张低频'"——这个 `N` 现在没有出处，没有哪个函数负责产出它。

**建议修法：抽一个 `lib/selection/`，纯函数、零依赖：**

```ts
resolveDrillSet(
  allCards: Card[],
  entitlement: { unlockedBlockIds: ReadonlySet<string> },
  selectedBlockIds: ReadonlySet<string>,
  narrowing: NarrowingDecision,
): {
  cards: Card[];            // 传给 schedule()
  excludedLowFreq: Card[];  // §4.4 的 "已排除 N 张低频"
  lockedBlocks: string[];   // §10.1 的转化入口素材
}
```

`server/` 只负责取数和传参。三层顺序钉死在一个可单测的地方，§4.4 的 `N` 有了唯一出处。**半天写完，加 15-20 条单测一天。** 不做的代价是付费转化屏的行为靠实现者临场发挥。

## 一般（但都必须做）

### E12. `card_state` 上没有 `algoVersion`

§8.1 只在 `review_log` 上记 `algoVersion`，理由写得很对："§5 必然迭代"。但 §8.2 已承认排期不可重放 ⇒ **算法一改，存量用户的 `plan[]` 是旧形状且无法重建**。

**失败场景**：上线三周后修一个 §5.3 装箱的 bug，`algoVersion` 从 1 到 2。此刻在窗口里的所有用户，`plan[]` 是按 v1 生成的。新代码消费它？语义可能变了。重新生成？§6 的圆点全部重画，且这不是 §5.5 的任何一个触发条件。

**修法**：`card_state.algoVersion`，新算法只对**新生成的计划**生效，旧计划跑完当前窗口（≤ 3 周）自然退场。加一列 + 一个分支，**半天**。

### E13. 构建时同步把内容发布和应用部署耦在一条流水线上

全量同步 1400 行不是问题（见"可以放心的地方"）。问题是**改一个错别字要重新构建并部署整个 Next.js 应用**。内容轨 4-9 个月持续编辑，这会变成每天几十次部署；而且**应用回滚回滚不了已经写进 DB 的内容**——两者的回滚语义不同却共用一条流水线。

**修法**：内容同步拆成独立 job（`content/**` 变更触发，跑脚本直连 DB 做 upsert + tombstone），与应用部署解耦；应用运行时从 DB 读内容，不从构建产物读（否则 DB 与 bundle 会漂移，`keyPointsTotal` 对不上）。**0.5-1 人日。**

### E14. §6 的今日进度分母没有存储位置

§6 写"今日进度的分母 = 今天开始时 `todayQueue` 的长度（含逾期卡），**当天内不变**"。这是 per-(user, localDate) 的状态，§8.1 的 `card_state`（per-card）和 `review_log`（per-review）都放不下它。刷新页面、换设备、杀进程重开，分母就变了——而 §6 明说它当天内不变。

**修法**：加一张 `daily_session(userId, localDate, queueSize, startedAt)`。依赖 E6 的 `localDate`。**半天。**

### E15. 空提交会炸掉整份计划

§4.4：单次得分 `= max(0, (勾对数 − 勾错数) / 正确要点总数)`。一条不勾 = 0 分 = 勾选比例 0 `< 1/2` = **§5.5 触发重新生成**。

于是**误触"提交"的代价是计划被重排 + §6 要求弹出"计划已重排"**。在一个主打"碎片时间快速点击"的移动端产品上，误触是必然事件。

**修法**：空勾选不允许提交（前端拦），或空提交按"跳过本题"处理、不写 `review_log`。十分钟的事，但不写进文档就没人做。

### E16. PWA 与离线外壳的落地细节，"断网可刷"在 §10 里是一行字

已查证的四条硬约束：

1. **WebKit ITP 对所有 script-writable storage 有 7 天无交互清除**，覆盖 IndexedDB、localStorage、Service Worker 注册与缓存；**主屏 web app 的第一方域名豁免**（[WebKit Tracking Prevention Policy](https://webkit.org/tracking-prevention/) 原文："The first-party domain of home screen web applications is exempt from ITP's 7-day cap on all script-writeable storage"）。产品是"移动端优先 Web + PWA"、目标用户会断网刷题 ⇒ **离线队列的可靠性依赖用户手动把它加到主屏**。
2. **iOS 不实现 `beforeinstallprompt`**，没有任何 API 能弹安装提示，只能自画"点分享 → 添加到主屏幕"的引导层，用 `navigator.standalone` / `display-mode: standalone` 检测后收起（[Apple 开发者论坛上的官方请求贴](https://developer.apple.com/forums/thread/807603)、[MDN Making PWAs installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)）。iOS 上的 Chrome/Edge **根本装不了**，得引导用户换 Safari 打开。
3. **`navigator.storage.estimate()` 在 Safari 不支持**，`persist()` 行为不可靠 ⇒ **不能靠配额 API 做容量决策**，写入必须 `try/catch` `QuotaExceededError`。
4. **Next.js 官方 PWA 指南推荐 Serwist**（[nextjs.org/docs/app/guides/progressive-web-apps](https://nextjs.org/docs/app/guides/progressive-web-apps)）。有一条需要在第一周验证的兼容性：Next.js 16 默认 Turbopack，官方文档现在同时给了 Turbopack 与 webpack 的 Serwist 示例，但社区仍有报告需要 `next build --webpack`。

**工程量：manifest + Serwist + iOS 引导层 + "有未同步提交，别关页面"的警告，3-5 人日。**

### 支付的前置资质必须这周启动，它是日历时间上的硬依赖

§10 把"支付接入"写成一个工程 bullet。已查证的实际链路（目标市场是境内——§10.1 的定价对标面试鸭，人民币买断）：

- **微信支付商户号只面向企业 / 个体工商户 / 小微商户**，个人主体做不了；网站场景接入要求**支付域名完成 ICP 备案**（[微信支付 PC 网站接入指引](https://pay.weixin.qq.com/static/applyment_guide/applyment_detail_website.shtml)）。
- **ICP 备案**：法定审核时限是省级通信管理局收齐材料后 20 个工作日，实际整体周期 **15-45 天**；之后 **30 天内还要做公安备案**。
- 商户入驻审核本身 1-2 个工作日，H5 支付权限 7 个工作日。

**整条链路（营业执照 → 域名实名 → ICP 备案 → 公安备案 → 商户号 → 支付权限）要预留 4-8 周日历时间。** 它完全不占工程人力，但它必须和写第一行代码在**同一周**启动，否则会直接成为上线的关键路径。这是本轮里唯一一件"今天不做，六周后一定后悔"的事。

## 如果只能改三件事

1. **把 §8.3 改成"离线只读计划、服务端是 `plan[]` 唯一写者"**（E1 方案 A）。这一条几乎零成本，消灭掉全文唯一一处无恢复路径的数据损坏风险，并把"客户端同构运行"从生产写路径降级成测试手段——文档想要的"断网也能刷完当天的量"一点没丢。
2. **把干扰项抽取改成服务端预生成 + 免费层从公开 lead-in 池取**（E2 + E8 路线 B 合并）。一次改动同时解决：付费墙泄露、离线出题、`distractorIds` 可复现、SEO 与付费墙的取舍。这是本轮里唯一一个**一处修法解四个问题**的改动。
3. **补 §5.5 第 4 条触发条件「选中块集合变更」+ `schedule()` 加 `reservedLoad` 参数**（E3 + E4）。这两条是同一个缺口的两面，不补则"在地图上勾块"和"临时加密"这两个产品动作在排期侧没有定义，且 §11 有一条验收标准会以半截断言的形式把 bug 盖住。

E5（选项总数泄露正确条数）排在第四，因为它改起来最便宜（写死总数分布 + 一条断言），但它推翻的是 §4.3 自己写下的设计目标，不能留着。
