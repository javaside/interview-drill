## 结论先行

**8 大类这个列表大体是对的，但配额是错的，而且最致命的问题根本不在分类上——在题型上。**

三条判断：

1. **`keyPoints` 模型只覆盖约 1/3 的真实八股题。** 实测 131 道公开真题（MySQL 94 + JVM 37），天然可枚举的占 **33.6%**。剩下 2/3 里最大的一块是**因果链/过程型（19.8%）**——而 §4.3 明文规定「每次出现重抽干扰项、**重排顺序**」。**对这五分之一的题库，产品每次复习都在系统性摧毁它要考的那个东西（顺序）。** 这不是粒度问题，是模型与内容的结构性错配。

2. **8 大类的配额是均分的（每类 8-12 块、12.5% 份额），而真实分布是 4-8 倍倾斜的。** 两个独立来源一致：「分布式/框架」在小林 coding 占 23.9%、在 JavaGuide 文档占 38.8%，而 JVM 是 6.0% / 4.8%。文档给它们同样的预算。结果是**JVM 必然注水、分布式/框架必然被砍**——而后者装着 Spring 全家 + 消息队列 + 微服务 + 分布式理论 + 系统设计，是 666 份 JD 里出现频率最高的技术簇。

3. **块划分标准和要点粒度标准都完全没写，而这两件事各自都有一条通向排期引擎的污染路径。** 要点条数是 §4.4 得分公式的分母、是 §5.5「得分比例 < 1/2 触发重排」的分母。同样是「我说到了两个核心点」，3 要点卡不重排、6 要点卡重排——**§5.2 花了一整段修掉 1/1296 的浮点误差，却留着一个 2 倍的粒度误差。**

**这个知识体系划分不算错，但它的配额、块标准、要点标准三样都没定，而没定的那三样正好是 170-280 小时内容投入的方向盘。** 按现状开工，产出的会是一个**列举题占七成、分布式/框架残缺、块粒度各作者一套**的题库。

## 致命

### T1. `keyPoints` 只覆盖约 1/3 的真实八股题型，且**三条力同向**把题库推向列举题

这是本轮最重要的一条，也是 170-280 小时投入的方向问题。

#### 实测：逐题分类 131 道公开真题

分类判据（可复现）：

- **可枚举型**——答案天然是一个无序清单，条数有限且可穷举（「索引失效有哪些」）
- **对比推理型**——问的是 X vs Y，或"为什么不用 Z"（「为什么 MySQL 不用跳表」）
- **因果链/过程型**——答案是一个**有序**的步骤链或推导链（「binlog 两阶段提交过程」）
- **权衡判断型**——答案取决于条件，没有唯一正确集（「性别字段能加索引么？为啥」）
- **情景推演型**——给定具体条件判定一个结果（「联合索引(a,b,c)，where b > x and a = y 会生效吗」）
- **单点事实型**——一句话就答完（「MySQL 默认隔离级别是什么」）
- **手写/操作型**——写 SQL、敲命令

| 题型 | MySQL 94 题 | JVM 37 题 | 合计 131 | `keyPoints` 契合度 |
|---|---|---|---|---|
| **可枚举型** | 27 (28.7%) | 17 (46.0%) | **44 (33.6%)** | ✅ 完美契合 |
| **对比推理型** | 16 (17.0%) | 4 (10.8%) | **20 (15.3%)** | ⚠️ 结论可编码，推理本身丢失 |
| **因果链/过程型** | 19 (20.2%) | 7 (18.9%) | **26 (19.8%)** | ❌ **顺序是答案，而 keyPoints 是无序集合** |
| **权衡判断型** | 11 (11.7%) | 4 (10.8%) | **15 (11.5%)** | ❌ 没有唯一正确集 |
| **情景推演型** | 9 (9.6%) | 1 (2.7%) | **10 (7.6%)** | ❌ 答案是「会/不会」+ 一条推理 |
| **单点事实型** | 9 (9.6%) | 4 (10.8%) | **13 (9.9%)** | ❌ 凑不满 3 条 |
| **手写/操作型** | 3 (3.2%) | 0 | **3 (2.3%)** | ❌ 完全不适用 |

顺带一个重要发现：**可枚举比例在大类之间差 1.6 倍**（JVM 46% vs MySQL 29%）。JVM 的八股天然是清单（回收器有哪些、类加载器有哪些、判断垃圾的方法有哪些），MySQL 的八股天然是推理和过程。**这意味着统一的 `keyPoints` 模型对 JVM 是合身的，对 MySQL 是硌人的——而文档给了它们同一个模型和同一个配额。**

#### 三条力同向，没有任何反向的力

问题不是"作者可能偏爱列举题"。是**流程在付钱请他写列举题**，三条各自独立的机制方向完全一致：

1. **CI 硬拒（§8.3）**：「要点少于 3 条的卡直接构建失败」→ 单点事实型（9.9%）与情景推演型（7.6%）**被自动挡在库外**，除非注水凑数。这两类合计 17.5%。
2. **审核经济学（§9.1）**：文档要求「每条要点在 `sources` 里逐条验证」且 source 必须是英文一手资料。**枚举型要点最好验证**——官方文档里就有那个列表，复制章节链接即可。**因果链和权衡型最难验证**——「为什么不用跳表」在 MySQL 官方手册里根本没有这一段，它是推理出来的，验证它意味着作者要自己承担论证责任。在 145-220 小时的压力下，作者会自然漂向好审的题型。
3. **互斥登记惩罚（§4.3）**：对比型和权衡型的要点**天生对兄弟题也成立**——「B+ 树非叶子节点只存键，树更矮」这一条，对同块几乎每一道索引题都成立，必须逐个登记 `excludeAsDistractorFor`。这类题的互斥登记负担是枚举型的数倍。12 万次判断的预算会倒逼作者少写这类题。

**三条全部同向。** 这和 §12 ③ 对自评方案下的那句判词结构完全一样——「不是用户有动机自欺，是产品**付钱请他**自欺」。这里是：不是作者偏爱列举题，是流程**付钱请他**写列举题。

预估收敛结果：题库题型分布会落在 **70-85% 列举题**，对上真实世界的 33.6%。

#### 这对 §11 的两个验收指标意味着什么

**先打中的是命中率，不是迁移率。** 命中率按题计：如果题库 80% 是列举题而面试 66% 不是列举题，那么即使选题的**主题**完全命中，**题型**不匹配的那部分也没有对应的卡。50% 阈值在数学上就吃紧了——这与第 2 轮发现的"只做并发一个大类时 50% 不可达"是同一类错误，只是换了一个维度（当时是覆盖面，现在是题型面）。

**更坏的是它对迁移率的影响方向。** §12 ④ 的赌注是「反复辨认完整要点结构 → 面试时说得出来」。这个赌注**恰恰在列举型上最可能成立**（结构就是一个清单，背清单确实能迁移成说清单），**在因果链/权衡型上最不可能成立**（结构是一个顺序或一组条件，而打乱顺序的 9 个复选框承载不了任何一个）。

于是：**题库向列举题漂移 → 验收访谈问到的多是列举题 → 迁移率数字好看 → §12 ④ 的赌注被"验证"了。** 内容漂移和赌注的偏向是同一个方向，**§11 会确认 §12 ④，无论 §12 ④ 是不是真的**。这是最坏的一种失败：不会被证伪。

#### 必须采用的修法：`cardType` + 分型出题

**不要放弃 `keyPoints`**——它对 1/3 的题是最优解，而且 §4.3 的干扰项复用机制确实成立。要做的是**承认题型存在，并在同一个 9 选框架里给每型一条规则**。

`§4.2` 题卡结构增加一个必填字段：

```ts
cardType: 'enumeration' | 'comparison' | 'sequence' | 'judgment' | 'atomic'
```

| cardType | 目标占比 | 出题形式 | 计分 | 复用了什么 |
|---|---|---|---|---|
| `enumeration` | ≤ 45% | 现状：9 选，3-6 条正确 | 现状 | 全部现有机制 |
| `comparison` | ~15% | 9 选，但**正确要点必须成对出现**（X 的特性 + Y 的对应特性）；干扰项优先抽"把两边说反"的变体 | 现状 | 现有机制 + 一条抽取偏好 |
| `sequence` | ~20% | **排序题**：给 4-6 个步骤，用户拖动排序。**选项不打乱是本型的强制例外** | 全序正确记满分，或按逆序对数量给部分分 | 需新渲染器 + 新判分 |
| `judgment` | ~12% | **二段式**：先选结论（会 / 不会 / 取决于），再选支撑要点；结论错则本题 0 分 | 结论 × 要点 | 复用 keyPoints 做第二段 |
| `atomic` | ~8% | **单选 4 选 1**，不走 keyPoints 计分 | 对/错 | 干扰项从同块 `public` 要点抽 |

配套的四处联动改动（都很小）：

- **§8.3 的 CI 规则改成 per-cardType**：`atomic` 允许 1 条要点，`sequence` 要求 ≥ 4 条且要点自带 `order`。现在这条规则会挡掉 17.5% 的真实高频题（见 T9）。
- **§4.4 的得分公式按型分派**，`sequence` 与 `judgment` 各有各的分子分母，但都归一化到 `[0,1]` 再喂给 §5.2 的起始档判断——**排期引擎一行不用改**。
- **§11 增加验收**：`lib/options` 对每种 cardType 各一组测试；`sequence` 型必须断言选项**未被打乱**。
- **§2 的配额表增加一列**：每个大类声明各题型的目标条数，审核时按型收题，防止漂移。这是唯一能对抗上面那三条力的机制——**目标占比必须是配额，不能是倡议。**

**如果只肯做一件事，做 `sequence`。** 它是 19.8% 的题库、是现行模型**主动出错**（不是覆盖不到，是打乱顺序把答案毁了）的唯一一型，也是最便宜的一型——一个拖拽排序 UI + 一次排列比较，没有新的内容成本（顺序本来就在要点里）。

### T2. 因果链型（19.8%）与 §4.3 的「每次重排顺序」直接冲突

T1 里已经点到，单列是因为它是**产品会主动做错事**的唯一一处，其余都是覆盖不到。

§4.3 白纸黑字：「**每次出现重抽干扰项、重排顺序。**」`PreparedOptions.optionTexts` 注释是「9 条，**已打乱**」。理由写得很好——防止用户记住"第 2、4、5 个是对的"。这条对枚举型完全正确。

但对这些题，**顺序就是答案本身**：

- 「SQL 查询语句的执行顺序是怎么样的？」——答案是 `FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT` 这个**排列**
- 「binlog 两阶段提交过程是怎么样的？」——prepare 写 redo → 写 binlog → commit 改 redo 状态
- 「讲一下类加载过程？」——加载 → 验证 → 准备 → 解析 → 初始化
- 「创建对象的过程？」「一条 update 语句的具体执行过程？」「执行一条 SQL 请求的过程？」

用户可以在「两阶段提交」这张卡上反复拿 5/5、掌握度刷到 1.0、圆点走完全程，**然后在面试里把 redo 和 binlog 的先后说反**。产品对此一无所知，因为它从来没考过顺序，还每次主动把顺序抹掉。

这直接击穿 §11 的迁移率定义：「刷到过的那些题，你当场说得出来吗」——用户会说"说出来了"，因为他说出了五个步骤；面试官记的是他说错了顺序。**这两件事在验收访谈里区分不出来。**

修法就是 T1 的 `sequence` 型。**在此之前，这五分之一的题库不应当开始生产**——按现状写的卡，将来改成排序题时要重新确认每条要点的 `order`，那是返工。

### T3. 8 大类的配额是均分的，而真实分布是 4-8 倍倾斜的

§2 给每个大类同样的预算：8-12 块 × 15-25 题 = 120-300 题，即每类约 12.5% 的份额。

两个独立来源实测的真实分布：

| 文档的大类 | 小林 coding 题数 | 占比 | JavaGuide 文档数 | 占比 | 文档配额 | 偏差 |
|---|---|---|---|---|---|---|
| 语言基础（Java 基础 + 集合 + IO） | 133 | 19.9% | 33 | 14.5% | 12.5% | **配额不足 1.4x** |
| 并发 | 68 | 10.1% | 17 | 7.5% | 12.5% | 大致相当 |
| JVM | 40 | **6.0%** | 11 | **4.8%** | 12.5% | **配额过剩 2.3x** |
| 操作系统 | 51 | 7.6% | 16 | 7.0% | 12.5% | **配额过剩 1.7x** |
| 计算机网络 | 76 | 11.3% | 24 | 10.6% | 12.5% | 大致相当 |
| MySQL | 94 | 14.0% | 24 | 10.6% | 12.5% | 大致相当 |
| Redis | 48 | 7.2% | 14 | 6.2% | 12.5% | **配额过剩 1.9x** |
| **分布式/框架** | **160** | **23.9%** | **88** | **38.8%** | 12.5% | **配额不足 1.9-3.1x** |

（小林口径：分布式/框架 = Spring 60 + 消息队列 38 + 分布式 26 + Docker 22 + 系统设计 14。JavaGuide 口径：system-design/framework 13 + distributed-system 系列 28 + high-availability 9 + high-performance 系列 15 + system-design 系列 12 + security 11。）

**两源在"谁最大、谁最小"上完全一致，只在幅度上有分歧。** 分布式/框架是最大的一类，JVM 是最小的一类，两者差 4-8 倍。文档给它们同样的预算。

666 份 JD 的关键词统计从需求侧独立佐证同一件事：Spring Boot 370 次（55.6%）、MyBatis 263、Spring 210、Spring Cloud 116、Spring MVC 104——**Spring 生态是除 Java 本身之外被提及最多的技术**；微服务架构 178（26.7%）、消息队列 172 + Kafka 162。而这些**全都被塞进一个和 JVM 等大的格子里**。

#### 实际后果，按文档自己的规则推演

「分布式/框架」在 8-12 块的上限（12 块 × 25 题 = 300 题）里要装下：Spring IoC/AOP/Bean 生命周期/事务、Spring Boot 自动装配、MyBatis、Kafka/RocketMQ（发送失败、重复消费、顺序、积压）、Nacos/Gateway/Sentinel/Seata/Dubbo、CAP/一致性/分布式锁/分布式事务/分布式 ID/限流、高并发高可用、系统设计。**至少 6 个互不相干的技术栈，每个分到 2 块。**

而 §2 自己写过判词：「用户点进『MySQL 索引』发现只有 20 道题，刷完心里还是没底，核心承诺就没兑现」。**用户点进「消息队列」发现只有 2 块 40 题——这正是 §2 自己否决过的那个场景，只不过发生在最大的那个类里。**

反方向同样坏：JVM 诚实地只有 6 个块（见 T5），要凑到 8-12 就得把「垃圾回收器」拆成「CMS」「G1」「ZGC」——而 ZGC 在中文 Java 八股里是低频的（小林 40 道 JVM 题里没有一道单独问 ZGC），且按块拆回收器会让 CMS 的要点大量对 G1 那道题成立，互斥登记爆炸（违反后文 B4）。

#### 产出 A：8 大类 → 11 大类修订建议（可直接采用）

不改总量（仍在 1200-1600），只改分配，并把「每类 8-12 块」作废、改为**按类声明配额**：

| # | 大类 | 块数 | 题数 | 依据 |
|---|---|---|---|---|
| 1 | **Java 语言基础与集合** | 10 | 180 | 实测 19.9%；集合是独立高频（小林单列 50 题），不能当「基础」的附属 |
| 2 | **并发** | 9 | 160 | 实测 10.1%，但块密度高（JMM/锁/线程池/并发容器/工具类各自都撑得起） |
| 3 | **JVM** | **6** | 100 | 实测 4.8-6.0%。**明确写死 6 块，不给 8-12**，避免注水 |
| 4 | **MySQL** | 9 | 155 | 实测 14.0%，块划分样例见产出 B |
| 5 | **Redis** | 6 | 100 | 实测 6.2-7.2%。注意它会被 T8 的"分布式锁磁铁效应"掏空，需按产出 B 同法钉死边界 |
| 6 | **Spring 生态**（Spring / Boot / MyBatis / 安全）| 8 | 140 | **必须独立成类。** 小林单列 60 题；JD 里 Spring Boot 55.6%，是第二高频关键词。含 1 块「Spring 里的设计模式」+ 1 块「认证授权与 Web 安全」（见 T10） |
| 7 | **消息队列** | 5 | 85 | **必须独立成类。** 小林 38 题；JD 消息队列 172 + Kafka 162 |
| 8 | **微服务与 RPC** | 5 | 85 | **必须独立成类。** JD「微服务架构」178 次，是出现频率最高的架构词。含 1 块「容器与部署基础」（Docker/K8s，见 T10） |
| 9 | **分布式理论与中间件** | 7 | 120 | CAP/一致性协议/分布式锁/分布式事务/分布式 ID/限流降级/一致性哈希 |
| 10 | **计算机网络** | 7 | 120 | 实测 10.6-11.3% |
| 11 | **操作系统与 Linux** | **6** | 100 | OS 实测 7.0-7.6%，诚实块数是 5；+1 块 Linux 排查命令（JD Linux 122 次 / 18.3%，高于 Docker 和 K8s） |
| | **合计** | **78 块** | **1345 题** | 落在 §2 的 1200-1600 区间内 |

改动本质：**把「分布式/框架」这一个格子拆成 4 个（6/7/8/9），把 JVM、Redis、操作系统从 8-12 块下调到 6 块。** 总块数从 64-96 变成 78，落在原区间中段；总题数 1345，落在原区间中段。**这个修订不增加任何工时预算，只是把同样的预算放对地方。**

#### 大类边界：synchronized 锁升级算哪类

文档没定边界规则，而 `blockId` 同时是掌握度单位、用户选择单位、干扰项第 1 层池——**边界错了不只是不整齐，是直接污染干扰项质量**。

「synchronized 锁升级」三个类都有正当主张：语言基础（它是关键字）、并发（它是互斥手段，要和 ReentrantLock 对比）、JVM（偏向/轻量/重量级锁是对象头 Mark Word 的状态机，`monitorenter` 是字节码）。

实证定音：[二哥的面渣逆袭](https://javabetter.cn/sidebar/sanfene/javathread.html) 把「synchronized 锁升级了解吗？」放在**并发 → 锁**，紧挨着「synchronized 和 ReentrantLock 的区别」和「AQS 了解多少」；小林 coding 同样归在并发。

**规则（建议写进 §4.1）：一张卡归属于「面试官会从哪个块自然问到它」的那个块，不是它的实现住在哪一层。** 理由与产品目标一致——`followUps` 追问链就是面试官的真实遍历路径，而用户要练的正是这条路径。

三类的操作化边界：

| 大类 | 判据 | 正例 | 反例（该归别处） |
|---|---|---|---|
| **语言基础** | 单线程下就成立的语言/类库行为 | HashMap 扩容为什么是 2 的幂、`==` vs `equals`、String 不可变 | 「HashMap 为什么线程不安全」→ **并发** |
| **并发** | **一旦引入"多个线程"才成立**的一切（含 synchronized 全家、JMM、volatile、线程池、并发容器） | synchronized 锁升级、i++ 是否原子、ConcurrentHashMap 实现 | 「String 常量池在哪块内存」→ **JVM** |
| **JVM** | **不写业务代码也成立**的运行时机制 | 运行时数据区、类加载、GC 判定与回收器、OOM 排查 | 「JMM / happens-before」→ **并发**（尽管它字面是"内存模型"） |

注意最后一条的代价：JMM 划给并发之后，JVM 又少一块——这也是 T3 建议 JVM 只给 6 块的原因之一。

## 严重

### T4. 块划分标准完全缺失，而 block 同时是**三个互相冲突**的约束的单位

§2 只说「每类 8-12 个知识块」，§4.1 举例「AQS 与锁」。**什么是一个块、边界怎么定、8-12 怎么来的，一个字都没写。** 这意味着 78 个块会由不同的人按不同的直觉划，而块是内容轨最先落地的结构——划错了，后面 1345 道题全挂在错的树上。

关键在于 block 身兼三职，而**这三职的最优粒度不一致**：

1. **作为用户选择单位**（§5.6 推论 3、§10 的块级选择）：块名必须让用户在 3 秒内判断"我这块行不行"。倾向**具体、可识别**。
2. **作为掌握度统计单位**（§4.4）：块内卡片的掌握度必须**互相相关**——会 A 应该预示会 B。否则块掌握度那个平均数不指向任何行动（B+ 树满分、事务零分 → 块 50%，这个 50% 什么也没告诉用户）。倾向**主题紧凑**。
3. **作为干扰项第 1 层池**（§4.3）：块内要点必须**似是而非但不互相成立**。**这一条与前两条方向相反**——块切得越紧凑，块内要点越容易互相成立，`excludeAsDistractorFor` 登记越多，可用池越小。§9.1 已经记过这个机制（「复用率越高净收益越负」），但没意识到它同时是**块粒度的约束**。

所以块粒度有一个**最优值，不是单调的**，而文档连方向都没给。

#### 产出的一半：块划分标准 B1-B6（审核可照判）

- **B1 · 共享坐标系**——同一块内的题必须共享同一套一手资料与版本坐标（同一份官方文档章节 / 同一段源码 / 同一个 RFC）。若一个块内要翻三套不同资料，它是三个块。**这一条同时是 §9.1「按块批量审省 25-30%」那条压缩手段成立的前提**——省的是上下文加载，而上下文就是这套资料。块划错了，那 25-30% 就省不出来。
- **B2 · 追问可达**——块内任意两题之间，存在一条不超过 2 跳的面试官追问链（A 的 `followUp` 能问到 B）。跨不到就该拆。这保证块是"一次面试对话的自然单位"，也保证了 T3 的归属规则可执行。
- **B3 · 掌握度相关**——若一个人能答对块内 70% 的题，他应当也能答对其余的。反例：把「索引」和「事务」放一块。
- **B4 · 要点可辨别（干扰项约束）**——块内任取两题，要点应当似是而非但不互相成立。**可量化的双边判据：块内需要登记 `excludeAsDistractorFor` 的要点若超过 20%，块切得过细，应与兄弟块合并；若随机抽一条块内要点明显不属于目标题（人工抽检 20 组，>80% 一眼可排除），块切得过粗，应拆分。** 这给 §9.1 那 12 万次互斥检查找到了一个副产品用途——**它本身就是块粒度的度量器**，在单块试点时就能给出反馈。
- **B5 · 命名即选择**——块名必须是用户在地图上一眼能判断的**具体知识对象**。**禁止**：「XX 基础」「XX 进阶」「XX 高级」「XX 其他」「常见问题」「面试高频」。这些名字用户无法据以选择，而块是选择单位（§10）。这条可以做成 CI 的黑名单正则，零成本。
- **B6 · 容量下界服从统计，不服从"内容够不够"**——见 T7。

#### 块粒度错了的三个后果（对应三个身份）

| 错法 | 例子 | 后果 |
|---|---|---|
| **太粗** | MySQL 只切成 索引/事务/锁/日志 4 块 | 用户选「索引」拿到 40 题，占掉 §5.6 的 157 题容量的 1/4；块掌握度环永远停在中间值，地图失去指示作用（这是 §4.4 已经修过一次的死结，换个成因复发） |
| **太细** | 切成「聚簇索引」「联合索引」「覆盖索引」「索引失效」 | 每块 6-8 题 = 约 32 条要点池。§4.3 自己算过 90 条池会 98.2% 枯竭，32 条更快；且相邻块要点大量互相成立，`excludeAsDistractorFor` 爆炸 |
| **边界错** | 把「B+ 树」和「跳表」分到不同块 | 「为什么 MySQL 不用跳表」这道题**最好的干扰项在另一个块里**，第 1 层抽不到。区分度直接损失，而这道题是 §4.3 号称的"最难辨别"那一层要保护的典型 |

### T5. 「每类 8-12 块」不成立——JVM 撑不起 8 块，分布式/框架装不下 12 块

T3 给了配额修订，这里给判据和反例，说明 8-12 为什么必须作废而不是微调。

**JVM 的诚实块划分是 6 块**（按 B1，每块对应 JVM 规范 / HotSpot 文档的一个独立章节）：

1. 运行时数据区与对象内存布局
2. 引用类型与内存泄漏
3. 类加载与双亲委派
4. 垃圾判定与回收算法
5. 垃圾回收器（Serial / CMS / G1 / ZGC）
6. 调优参数与线上排查（OOM / CPU 飙高 / jstack / jmap / Arthas）

要凑到 8 块，唯一的办法是拆第 5 块。拆完违反两条：**低频**（小林 40 道 JVM 真题里没有一道单独问 ZGC）和 **B4**（CMS 的要点「并发标记阶段不 STW」对 G1 那道题也成立，按块拆回收器会让互斥登记率远超 20%）。

**分布式/框架**方向相反：按 B1 它至少有 30 个块（Spring 8 + MQ 5 + 微服务 5 + 分布式理论 7 + 系统设计 5+），12 块的上限意味着 60% 的内容根本进不来。

**结论：8-12 应当整体作废，替换为 T3 产出 A 里的 per-类配额表。** 这不是"放宽区间"——放宽成 5-15 只是把问题推给作者。配额必须写进 §2 并在 CI 里校验（块数不符即构建失败），因为**没有硬配额，三条漂移力（T1）会把内容推向好写的那些块**。

### T6. 要点粒度标准缺失，且粒度不齐**直接污染 §5.5 的重排阈值**

§9 ③ 要求「要点粒度是否齐整」，但全文没有定义什么叫齐整。审核员拿到这条清单，只能各判各的。

#### 先诊断文档自己举的例子

AQS 那道题的五条要点：

| # | 原文 | 诊断 |
|---|---|---|
| 1 | `volatile int state 表示锁状态` | ✅ 合格 |
| 2 | `CLH 变体的双向 FIFO 等待队列` | ❌ **折叠了 4 个独立事实**（CLH 血统 / 是变体 / 双向 / FIFO），能提出两个互不相干的追问（「为什么双向？」「CLH 原版什么样？」） |
| 3 | `CAS 改 state 失败则包装 Node 入队` | ✅ 合格 |
| 4 | `自旋一次后 LockSupport.park 阻塞` | ⚠️ 「自旋一次」是实现细节，漏掉面试官不扣分；「park 阻塞不忙等」才是得分点 |
| 5 | `release 时 unpark 后继节点` | ✅ 合格 |

三个问题，各自独立：

**(a) 两类陈述混在一起。** #1、#2 是**静态结构**（AQS 有什么），#3、#4、#5 是**动态流程**（AQS 按顺序做什么）。用户拿到 4/5 时，不知道自己缺的是结构还是流程——而这两种缺口的补救完全不同。顺带一提：#3#4#5 构成一条有序链，这张卡本身就有一半属于 T1 的 `sequence` 型。

**(b) 信息量不等。** #2 装 4 个事实，#5 装 1 个。漏 #2 和漏 #5 都扣 1/5。

**(c) 得分价值不等，而这一条直接污染排期。** 面试官听到 #1 + #3 就会点头放行；#4 的「自旋一次」漏掉毫无影响。但 §4.4 的公式一视同仁。

后果是精确可算的。§5.5：「得分比例 `< 1/2` → 起始档退回 0，**从明天起重新生成**」，§4.4：得分 = `max(0, 勾对 − 勾错) / 正确要点总数`。同样是真实水平"我说到了两个核心点、0 个错"：

| 该卡要点条数 | 得分 | 是否触发 §5.5 全卡重排 |
|---|---|---|
| 3 条 | 2/3 = 0.67 | 否 |
| 5 条（AQS 现状） | 2/5 = 0.40 | **是** |
| 6 条 | 2/6 = 0.33 | **是** |

**要点条数是一个未标准化的作者选择，却直接决定同一个用户是否被判定为"答错"、整张卡的计划是否被推倒重来、§6 屏②「计划已重排」的提示是否弹出。**

这正是 §5.2 已经识别过的那类错误。文档为此写了整整一段，把 `s ≥ 0.67` 改成分数比较、要求 `s` 用精确有理数存储，理由是「`2/3 = 0.6667 < 0.67`，三要点卡答对两条会掉进下一档——同样是『大部分对了』，三要点卡的用户被平白多排一遍」。**§5.2 修掉了 1/1296 量级的浮点误差，却留着一个 2 倍量级的粒度误差在同一条路径上。**

#### 要点应该是"事实陈述"还是"得分点"？——**必须是得分点，两者不是一回事**

文档把这两个概念混用了（§4.2 写「3-6 条**可得分要点**」，§9 ③ 又要求「每条要点能在 `sources` 里逐条验证」——后者是事实标准，前者是得分标准）。

**判据应当是得分点，理由来自产品自己的承诺。** §11 的迁移率测的是「你当场说得出来吗」，而"说得出来"的计量单位是**面试官会点头的东西**，不是**技术上为真的东西**。一条为真但面试官不会认可的陈述，在这个模型里不是中性的——它会**稀释分母**，进而按上表错误触发 §5.5。

好消息是模型里已经有放事实的地方：**`keyPoints` = 得分点（3-6 条，计分）；`detail` = 事实与展开（不计分）。** 文档只是从来没说过什么进哪边。

#### 产出 C：要点粒度标准 KP1-KP6（审核可照判，带正反例）

- **KP1 · 独立可说出**——一条要点必须是候选人能用一句话（约 15-25 字）说出、且说出后面试官会点头的最小单位。**判据：「他只说了这一条，面试官会不会认为答到了点上？」**
- **KP2 · 单一信息核**——一条要点只含**一个可被独立追问的事实**。**判据：能不能对这条要点提出两个互不相干的 `followUp`？能，就是两条。**
- **KP3 · 同卡同类型**——一张卡的要点必须**全是结构、或全是流程、或全是权衡**，不混。混了说明这张卡问了两个问题，应拆卡，或把其中一类降为 `detail`。（与 T1 的 `cardType` 是同一条约束的两种表述——`cardType` 定了型，KP3 就是它的审核形态。）
- **KP4 · 等价可失**——漏掉任意一条的后果应大致相当。**判据：把 3-6 条按「面试官会不会因为漏这条扣分」排序，若第一条和最后一条落差明显（一条致命、一条无所谓），最后那条进 `detail`。** 这条直接保护 §5.5 的 1/2 阈值，是六条里唯一有排期后果的。
- **KP5 · 不含承载词**——要点里不得出现「等」「多种」「一系列」「若干」「之类」「诸如」。它们把多个事实折叠进一个词，是"把不可枚举硬塞进枚举"的语法标志。
- **KP6 · 与题面同粒度**——要点的抽象层级要和 `question` 一致，既不下沉到实现细节，也不上浮到定义。

**正反例（就用 AQS 那道题）**

按标准重写后（全流程型，KP3 合格；五条各含一个信息核，KP2 合格）：

1. `state 是 volatile int，表示同步状态，独占锁下 0 表示空闲`
2. `获取锁是对 state 做 CAS，成功即持有`
3. `CAS 失败则把线程包装成 Node，入等待队列尾部`
4. `排队线程用 LockSupport.park 阻塞，不自旋空转`
5. `释放时改 state，再 unpark 后继节点`

下沉到 `detail` 的：CLH 血统、队列为什么是双向、`Node.waitStatus` 的取值、"自旋一次"这个细节。其中「为什么是双向不是单向」应当提升为一条 `followUp`——它本来就是面试官的真实追问。

**审核时应当直接打回的三种写法：**

| 反例 | 违反 | 为什么 |
|---|---|---|
| `AQS 是 AbstractQueuedSynchronizer 的缩写，是 JUC 包的基础框架` | KP1 | 面试官不会点头，这是背景不是得分点 |
| `AQS 支持独占和共享两种模式，ReentrantLock、Semaphore、CountDownLatch 等都基于它` | KP5 + KP6 | 「等」折叠了未知数量的事实；且抽象层级高于题面 |
| `Node 的 waitStatus 有 CANCELLED(1)、SIGNAL(-1)、CONDITION(-2)、PROPAGATE(-3) 四个值` | KP6 | 下沉到实现细节，该进 `detail` |
| `AQS 用 CLH 变体的双向 FIFO 队列管理等待线程，入队用 CAS 保证线程安全` | KP2 | 三个信息核（CLH 变体 / 双向 FIFO / CAS 入队），能提出三个不相干追问 |

**三条可机器校验、零审核成本的规则**（建议加进 `lib/content/validate.ts`，CI 里跑）：

1. **要点长度上界 30 个汉字**——超过 30 字的要点几乎必然违反 KP2。这是 KP2 的廉价代理，不能替代人工判断，但能在人工看到之前挡掉大部分。
2. **承载词黑名单正则**——`等|多种|一系列|若干|之类|诸如|各种` 命中即失败（KP5）。
3. **块名黑名单正则**——`基础|进阶|高级|其他|常见问题|高频` 命中即失败（B5）。

这三条在 1345 张卡 × 4.5 要点 = 约 6000 条要点上跑，成本为零，而它们覆盖的正是审核到第 15 道题时最容易放水的那类问题（§9.1 自己承认「同块连审 20 道题极其单调，第 15 道后判断质量下降」）。

### T7. 15-25 题/块：上下界的**理由都是错的**，而下界同时是干扰项池容量的下界

#### 先回答"每个块都有 15-25 道值得记的题吗"——**不是**

用真实题量对照：

| 块 | 真实可支撑题数 | 判定 |
|---|---|---|
| Spring IoC / AOP / Bean 生命周期 | 40+ | **撑爆** ——它是唯一人人写在简历上的框架 |
| MySQL 索引（小林原分组） | 34 | **撑爆**——我在产出 B 里把它拆成三块 |
| 线程池 | 18+（二哥单列 18 题） | 刚好 |
| Linux 常用排查命令 | 8-10 | **不足** |
| Seata 分布式事务 / ZGC | 6-8 | **不足** |
| 系统设计 | 14（小林全部） | **不足**（且见 T13，它根本不该进） |

真实块容量分布大约在 **8-40**，15-25 这个窗口自然覆盖大约 60-70% 的块。

#### 下界 15 的理由，文档没给，而我能想到的那个是错的

如果理由是"干扰项池容量"，那它撑不住。用文档自己的模型算：

§4.3 原文实算：20 题 × 4.5 要点 = 90 条池；一轮刷完抽 360 次 → **见过 98.2%**，文档判定"干扰性归零"，因此引入 1:2 分层。分层之后同块层只占 1/3，同块抽取降到约 180 次，见过比例 = `1 − e^(−180/90)` ≈ **86.5%**。

**分层只把枯竭从 98% 降到 86%，没有解决它。** 而且文档漏了自己的一张表：§4.3 的分层比例随掌握度**升高同块占比**，`s = 1` 时是 **3:0（100% 同块）**。也就是说，**每个块的终局恰恰是文档一开始否决的那个纯同块场景**，而且发生在池子已经被见过 86% 之后。

要让同块见过比例降到 60% 这个勉强可接受的水平，需要 `n/P ≤ 0.92`；以 20 题块、平均每次抽约 2 条同块干扰项算，`n ≈ 240`，得 `P ≥ 261 条要点 ≈ 58 题/块`。

**58 题/块是不可能的（内容成本翻 2.5 倍）。所以结论是：在任何现实的块大小下，第 1 层干扰项池一轮之内必然被见过 70-95%。把下界定在 15、20 还是 25，对这个结论没有影响。** 干扰项池不能作为下界的理由。

#### 下界 15 的**正确**理由（可以保留这个数字，但要换个论证）

块掌握度是块内卡片 `s` 的加权平均（§4.4）。若块内只有 8 张卡，单张卡从 1.0 掉到 0.4 会让块掌握度跳约 7.5%，地图上的环会明显闪动；15 张卡时是 4%，25 张时是 2.4%。**下界 15 的正当理由是「掌握度统计的最小样本」，不是「内容够不够」，也不是「干扰项池够不够」。** 这个论证站得住，建议直接写进 §2。

#### 上界与例外

- 上界放宽到 **40**，但加一条：**块题数 > 25 时必须在 §2 的配额表里显式声明并给理由**。Spring IoC、MySQL 索引（若不拆）、线程池 三个确实该超。
- 允许 **8-14 的小块**，标记 `thin: true`，其第 1 层干扰项池**强制并入 `relatedBlocks`**（见 T11）。

#### 干扰项枯竭的唯一结构性解，文档已经写了，但放错了地方

§12 ④ 的补救路径第 3 条：「**要点乱序 + 相似表述**——同一条要点用两种措辞出现，其中一种是错的（例如『CAS 失败则入队』vs『入队失败则 CAS』）」。

**这一条不该是"迁移率低时的补救"，它是干扰项池枯竭的唯一结构性解，应当提前到第一版。** 理由：措辞变体**不从有限池里抽**——它是按目标要点现场构造的，池子无限大，且天然是"最难辨别"的那一层，正好补上第 1 层的功能。

代价必须说清楚，因为它戳破了 §4.3 的一句话。§4.3 称干扰项「内容成本是**零**」——对同块复用的那部分成立，对措辞变体**不成立**。需要给 `KeyPoint` 加一个字段：

```ts
nearMiss?: string[]   // 该要点的错误变体：把因果反过来、把版本说错、把数量说错
```

**建议的范围控制**：只给 `frequency = high` 的卡、每条要点 1 个变体。工时归第 3 轮口径，此处只标出**它不为零**，与 §4.3「零内容成本」的说法冲突，须在 §4.3 改口。

### T8. 单一归属的磁铁块 / 掏空块效应，与 T3 的配额错误**同向叠加**

#### 跨块题的真实比例

在 MySQL 94 题里逐题判断"是否有第二个正当归属"：「为什么 MySQL 不用跳表」（跳表要点在 Redis）、「如何用 MySQL 实现可重入锁」（分布式锁）、「MVCC 实现原理」（事务 / MVCC 边界）、「一条 update 是不是原子性的」（事务 / redo-undo）、「MySQL 如何保障数据不丢失」（日志 / 复制）、「分表分库」（分布式）、「主从延迟处理」（缓存一致性）等——**约 13-19% 的题有真实的第二归属**，其中约三分之一是**跨大类**的。这是我逐题判断的结果，不是查来的数字，标明为经验判断。

#### 磁铁块与掏空块（这才是代价所在）

**系统性膨胀的"磁铁块"**——它们是大量跨领域题的自然唯一归宿：

| 磁铁块 | 被它吸走的题来自 | 膨胀量级 |
|---|---|---|
| **分布式锁** | Redis（SETNX / Redisson 看门狗 / RedLock 争议）、ZooKeeper、MySQL（可重入锁）、并发（可重入语义） | 轻松超 40 题 |
| **缓存一致性** | Redis、MySQL、消息队列（延迟双删 / 订阅 binlog） | 超 25 题 |
| **JMM** | 并发、JVM | 超 25 题 |
| **线程池** | 并发、语言基础（Executor API）、框架（Tomcat / Spring 线程池） | 超 30 题 |

**系统性被掏空的"捐赠块"**：

- **Redis**——若分布式锁、缓存穿透/击穿/雪崩、缓存一致性全部归到分布式类，Redis 只剩 数据结构 / 持久化 / 内存淘汰 / 主从哨兵集群 = **4-5 块**，撑不起 8-12（而文档给它 8-12）
- **操作系统**——零拷贝被网络和 Kafka 争，IO 多路复用被网络和 Redis 争。让出去之后 OS 只剩 进程线程 / 调度 / 内存与虚拟内存 / 死锁 = **4 块**
- **JVM**——JMM 按 T3 的规则划给并发之后又少一块

**关键观察：掏空的方向（Redis、OS、JVM）和 T3 里配额过剩的方向（Redis 1.9x、OS 1.7x、JVM 2.3x）完全一致；膨胀的方向（分布式）和配额不足的方向完全一致。两个错误同向叠加。** 按现状执行，Redis / OS / JVM 三个类会在"要凑够 8-12 块、每块 15-25 题"的压力下大量注水，而分布式类塞不下。T3 的配额修订同时解掉这一半。

#### 不要放弃单一归属——但 `relatedBlocks` 现在是死字段（接 T11）

单一归属的理由（重复统计会让掌握度地图失真）是对的，应当保留。问题在于 §4.2 给 `relatedBlocks` 写的是「软链接，**不参与掌握度统计**」，而 §4.3 的干扰项分层只有"同块 / 同大类"两层，**也不用它**。它在全文里不驱动任何行为。修法见 T11。

### T9. §8.3 的「要点少于 3 条构建失败」会把 17.5% 的真实高频题挡在库外

§8.3：「要点少于 3 条或缺 `sources` 的卡直接构建失败，坏内容进不了生产。」

这条规则的意图（防止半成品进库）是对的，但它把**题型问题误当成质量问题**。按 T1 的实测，**单点事实型 9.9% + 情景推演型 7.6% = 17.5% 的真实题结构上就凑不满 3 条**：

- 「MySQL 默认隔离级别是什么？」→ RR。一条。
- 「B+ 树的叶子节点链表是单向还是双向？」→ 双向。一条。
- 「联合索引 (a,b,c)，`where b > x and a = y` 会生效吗？」→ 会，优化器会重排条件，a 是最左列。一个结论 + 一条理由。
- 「GC 只会对堆进行 GC 吗？」→ 不是，方法区/元空间也会。一条。

这些是**最容易被记住、也最常被真的问到**的那类八股——短、硬、二选一。

内容团队面对这条 CI 规则只有两条路，都坏：

1. **注水到 3 条**——违反 KP1 和 KP4，把分母从 1 撑到 3，然后按 T6 的表污染 §5.5 的重排阈值
2. **整批放弃**——丢掉 17.5% 的高频题，直接压低 §11 的命中率

**没有第三条路，除非引入 T1 的 `cardType`。** `atomic` 型走 4 选 1 单选、允许 1 条要点；`judgment` 型走"先选结论再选支撑"、结论本身就承载了那个二值答案。CI 规则相应改成 per-cardType 的 `minKeyPoints`。

## 一般（但都要改）

### T10. 两个缺失的类目：认证授权与安全、设计模式

**认证授权与 Web 安全**——文档 8 大类里完全没有。JavaGuide 把它列为[通关计划第三阶段的独立模块](https://javaguide.cn/interview-preparation/backend-interview-plan.html)（认证基础 / JWT / SSO / 权限系统设计），[面试突击版](https://interview.javaguide.cn/)单列「认证与授权 / Web 安全」，docs 下 `system-design/security` 有 11 篇。真实面试里「JWT 怎么做登出」「SSO 单点登录流程」「CSRF 和 XSS 的区别」是常见题。**建议：Spring 生态类下 1 块**（它几乎总是跟着 Spring Security 一起问），不独立成类。

**设计模式**——数据有意思，两个方向相反：JD 侧 126 次 / 18.9%，**高于 Elasticsearch(93)、Docker(90)、Kubernetes(85)**；但面试题侧很薄——小林 coding 没有设计模式套题，二哥的设计模式页只有 5 道题。解释是一致的：**设计模式是简历/JD 关键词，但它转化成的八股题很少，且几乎总是穿过 Spring 问**（工厂 → Spring 容器，代理 → AOP 原理），或穿过并发问（DCL 单例 → volatile → 指令重排）。

**建议：Spring 生态类下 1 块「Spring 里的设计模式」**，另外把 DCL 单例作为一张卡放进并发的 JMM 块并标 `relatedBlocks`。**不独立成类**——23 种 GoF 模式撑 8-12 块正是 T3 说的"占了名额但实际低频"的典型失败模式。但**零覆盖也是错的**，现状是零。

**云原生 / K8s**——JD 侧 Docker 90 + K8s 85，但表述形式是"加分项 / 优先"（校招）或 infra 方向岗位的任职要求（社招），不是通用 Java 后端的八股考点。小林有 22 道 Docker 题。**建议：微服务与 RPC 类下 1 块「容器与部署基础」**，v2 再评估是否独立。

**Linux 实操**——JD 侧 122 次 / 18.3%，**高于 Docker 和 K8s**；小林单列 21 道命令题。真实问法是「怎么查 CPU 占用最高的进程」「怎么在大日志里定位」。**建议：操作系统类下 1-2 块。** 但要注意：**这些题是全库最不适合 `keyPoints` 的**——答案是一条命令，不是 3-6 个要点。它们几乎全是 T1 的 `atomic` 型。在 `cardType` 落地之前，这两块不要开工。

### T11. `relatedBlocks` 是死字段，让它承重可以同时解掉三个已知问题

§4.2 定义了它，§4.3 的干扰项分层不用它，§4.4 的掌握度不用它，§5 的排期不用它，§6 的 UI 不用它。**全文没有任何行为依赖这个字段。**

建议在**三处**让它承重，都近乎零成本，且每一处都解掉一个文档已经承认的问题：

1. **成为干扰项的第 1 层池的一部分**——目标卡有 `relatedBlocks` 时，第 1 层池 = 同块 ∪ relatedBlocks 的要点。**这把 T7 算出的池子从约 90 条扩到 180-250 条，把见过比例从 86% 压到约 70%。** 也解掉 T4 说的"边界错导致最好的干扰项抽不到"（「为什么不用跳表」终于能抽到跳表的要点）。改动范围：`lib/options` 的池构造，一处。
2. **驱动地图提示**——用户选了 A 块，地图提示「你选的块里有 6 张卡与『分布式锁』强相关，那个块你没选」。**§11 已经要求统计「块选择准确率」并写明"选错块 = 地图引导有问题"，而地图目前除了颜色没有任何引导机制。** 这是唯一能让那个指标变好的杠杆。
3. **CI 校验磁铁块**——任一块的 `relatedBlocks` 入度若超过总块数的 30%，判定为磁铁块，要求拆分。这是 B4 的推论，机器可查，能在内容生产早期发现 T8 的膨胀。

### T12. 前置依赖：**不要做门禁，但要做三处零成本的利用**

**先回答"需不需要"：不需要 `prerequisites` 作为门禁。** 理由不是"前置不重要"，而是场景不对——**面试复习的用户不是在学习，是在回忆**。§1 说得很清楚：问题是「看了就忘」，不是「没学过」。硬门禁会拦住一个面试前两天想突击索引失效的用户，而那正是 §5.8 临时加密要服务的核心场景。另外它会变成权限 × 选块 × 收窄之外的**第四层筛选**，而第 4 轮的 E11 已经指出前三层就已经没有归属层了。

**但前置关系确实存在，而且它的缺失会伤到干扰项质量，不只是理解。** 用户没刷过 JMM 块就刷 volatile 题时，跨块层会从 JMM 块抽要点——用户看到的不是"似是而非"，是"完全不认识"。**区分度同样归零，但方向相反：太容易排除掉。** 文档设计干扰项时假设了用户对同大类内容有基本熟悉度，这个假设没有任何机制保障。

**建议：不加新字段，给 `relatedBlocks` 加一个方向标记：**

```ts
relatedBlocks: Array<{ blockId: string; kind: 'sibling' | 'foundation' }>
```

`foundation` 的三个用途，**全都不拦截用户**：

1. **地图角标提示**——用户勾了「volatile 与 JMM 应用」没勾「Java 内存模型」，后者显示「6 张卡依赖它」。可无视。同 T11 第 2 条，服务块选择准确率。
2. **干扰项层级**——foundation 块的要点进第 1 层池。**这把前置关系从门禁变成了区分度资产**：用户不懂 JMM 时，JMM 的要点作为错误选项恰恰最有教学价值——§6 屏② 会告诉他"这条属于『Java 内存模型』"，而这正是文档自己设计的转化点（§4.3 末尾的归属显示降级）。
3. **§5.2 的新卡排位键**——`newPerDay` 现在按 `(frequency 降序, cardId 升序)` 排位。加一条：**同 frequency 内，foundation 块的新卡优先**。**这是纯排序键变更，不动任何不变量，I1-I5 全部不受影响**，但用户会先见到基础卡、几天后见到依赖卡——恰好是间隔重复本来就会产生的顺序。

标注成本：78 块 × 0-2 个 foundation ≈ 100 条，一次性，不进 §9.1 的预算讨论。

**一处例外值得考虑硬引导（不是硬门禁）**：免费层只解锁 2 块（§10.1），而免费层的跨块干扰项已经降级到 `public` 池。若用户选的块带 foundation 而没选那个 foundation，他的体验会是"选项全是不认识的东西"。**建议：免费层选第 2 块时，把 foundation 块作为默认推荐（可改）。** §10.1 自己说过「免费层是唯一必须演示『机制有用』的地方」。

### T13. 系统设计应当**显式排除**，并在 §2 写明理由

文档没有系统设计类，这个决定是对的，但**理由不该是"低频"**（对社招它不低频，JavaGuide 专门有一个子站），而应该是**结构性不可判分**。

「设计一个短链服务」没有 3-6 条离散正确要点，它有一个解空间。强行编码只有两种结果：把一种实现写成标准答案（教出错的东西），或把所有分支都标成正确（什么也没教）。它同时违反 KP1（面试官不会因为你说出"用发号器"就点头，他要听取舍）和 KP4（漏掉的后果完全不等价）。

**建议在 §2 加一句：「不做系统设计与场景题——它没有离散的得分点集合，与 §4.3 的判分模型结构性不兼容。这是能力边界，不是优先级排序。」** 这比静默省略强：它给后续的范围讨论一个可引用的判据，也和 §6.1「不做理解辅导、不做模拟面试」的边界声明是同一种诚实。

同理，**手写 SQL / 算法题（T1 里的 2.3%）也应当显式排除**。

几点必须说明的划分决策：

- **索引被拆成三块（M2 / M3 / M4）。** 小林把 34 道题全归在「索引」一组，那超出了任何合理上界。拆的依据是 **B1**——三块分别对应 MySQL 手册的三个独立章节（B-Tree 结构 / 多列索引 / EXPLAIN），换块确实要换资料。同时满足 **B3**：懂 B+ 树结构的人未必会看执行计划，两者掌握度不相关。
- **M5 / M6 的边界是 B4 的典型考验。** 「事务隔离级别」和「MVCC」关系极紧，合成一块会是 31 题（超上界）且块内要点大量互相成立；拆开后 M6 的「ReadView 记录活跃事务 ID 列表」对 M5 的 RR/RC 题是否成立需要逐条登记。**建议把 MySQL 选为 §10 要求的"单块试点"对象，并且试点块就选 M6**——它是全库互斥登记率最高的块之一，能最快校准出 §9.1 那 5-10% 的预筛命中率是不是真的。
- **M1 的题最杂**（数据类型 + 引擎对比 + SQL 基础），是本划分里唯一有点勉强的块，B1 上跨了两个手册章节。若审核时发现它违反 B3（掌握度不相关），应当把数据类型部分并入 M3（"什么字段适合当主键/建索引"和数据类型天然相连）。
- **三道手写 SQL 题（14,15,16）不进库**，按 T13 显式排除。
- **「为什么 MySQL 不用跳表」(40) 归 M2，但必须标 `relatedBlocks: [Redis/跳表与有序集合]`**，否则按 T4 它最好的干扰项抽不到。这是产出 B 里最能说明 T11 价值的一张卡。

**题型分布（按 T1 的 `cardType` 预标）**：M2/M3 偏 `comparison`，M4/M5 偏 `enumeration`，M6/M8 大量 `sequence`（MVCC 版本链遍历、两阶段提交、崩溃恢复），M3 有多道 `judgment`（主键选型、性别字段、status 字段），M7 几乎全是 `judgment`/`atomic`（会不会阻塞）。**MySQL 是全库最不适合纯 `keyPoints` 的大类**——这也是我建议拿它做试点的第二个理由：**如果 `cardType` 在 MySQL 上跑通了，其余大类都不会更难。**

## 如果只能改三件事

1. **在生产任何一张卡之前，先定 `cardType` 和 §2 的题型配额表。** 这是本轮唯一有硬截止期限的改动，性质与第 3 轮的 `KeyPoint` 结构相同——1345 张卡按无型的 `keyPoints` 写完之后再分型，`sequence` 型要重新确认每条要点的顺序、`judgment` 型要重新拆结论和支撑，是整段返工。**不定型就开工，等于赌真实八股有 80% 是列举题，而实测是 33.6%。**

2. **把「分布式/框架」拆成 4 个类，把 JVM / Redis / 操作系统下调到 6 块，并作废「每类 8-12 块」。** 两个独立来源一致：前者是最大的一类（23.9% / 38.8%），后者是最小的（6.0% / 4.8%），文档给了它们同样的预算。这个修订不增加一分钟工时，只是把 170-280 小时放对地方。

3. **把 KP1-KP6 和 B1-B6 写进 §9 ③ 的审核清单，并把其中三条做成 CI 正则。** §9 ③ 现在写的是「要点粒度是否齐整」——这句话审核员照着判不了，78 个块会长成 78 种样子。而粒度不齐不只是不整齐：**它是 §5.5 重排阈值分母的 2 倍误差，而 §5.2 已经为同一条路径上 1/1296 的浮点误差写了整整一段。**
