# 判据歧义：提示语「属于这道题」与答案集不对齐

- 日期：2026-10-03
- 发现方式：**用户实测**（线上刷题踩到，非代码审计）
- 涉及：`src/app/(drill)/DrillQuestion.tsx`、`src/app/(drill)/DrillFeedback.tsx`、`src/lib/ai/qa.ts`、`src/app/map/KnowledgeMap.tsx`、`content/**`、spec §4.3
- 状态：**诊断完成，修法待用户拍板**（本文件只记录，未改动任何代码或内容）

## 结论先行

**提示语「勾出所有属于这道题的要点」有歧义，且这个歧义会让用户按字面正确作答却被判错。**

「属于」有两种读法：

| 读法 | 含义 | 那条干扰项算不算 |
|---|---|---|
| spec 作者原意（§4.3） | 属不属于**本卡的答案集** | ❌ 不算 |
| 中文自然读法（用户实测的读法） | 和**这道题的话题**相不相关 | ✅ 算 |

对**开放式题干**（「X、Y、Z 分别是什么？」），这个歧义必然爆发：该话题的**所有真话**在字面意义上都"属于"这道题。

## 触发实例

卡 `01M3M39N0X9CV1HJ9G0XDVHS6P`：《final、finally、finalize 分别是什么？》（`java/language-basics`，enumeration，4 条要点）

用户线上作答：勾了 1、6、8（三个关键字的定义），**未勾**第 9 项。
判分：`得分 3/4 · 漏选 1 条 · 错勾 0`。

- 被判定漏选的：`finally 不执行的三种情况：System.exit、JVM 崩溃、守护线程里的死循环`
  ——**这是边缘情况，不回答「是什么」**
- 用户困惑的干扰项：`返回 finally 的值：try 的返回值与异常都被丢弃（字节码把覆盖路径编进返回）`
  ——**它讲的就是 finally，按「属于」的字面意思该勾，系统却当它是干扰项**

**用户按题干字面作答（只答定义）→ 被判漏选；按提示语字面作答（勾沾边的）→ 会判错勾。两个指令互相矛盾，用户无路可走。**

## 根因：spec 的一条假设在开放式题干下失效

spec §4.3 的原文：

> 从同知识块的兄弟题里抽要点当干扰项，抽到的天然是真实、专业、似是而非的东西——比人工编的干扰项质量还高，因为它们本来就是正确的技术陈述，**只是不属于这道题**。

设计假设：**干扰项不属于目标题**。
对「HashMap 为什么死循环」（抽到 Spring AOP 代理）成立；对「X、Y、Z 分别是什么？」**不成立**——话题的全部真话都"属于"它。

### 量化（实测）

按三层池分别统计「与本题话题（final/finally/finalize）重合」的可用干扰项：

| 层 | 话题重合条数 | 归属 |
|---|---|---|
| 层1 同块 | **0 条** | —— |
| 层2 同大类跨块 | **11 条** | `java/exceptions` ×7、`java/reflection-proxy` ×2、`java/string` ×1、`java/hashmap` ×1 |
| 层3 相邻大类 | **2 条** | `jvm/class-loading` ×1、`jvm/gc-basics` ×1 |

**正确答案 4 条，同话题的"正确干扰项" 11 条（同大类）+ 2 条（邻类）。**

**层1 同块是干净的（0 条）** —— 这解释了坑为何只在特定条件爆发：`layerCounts` 的配比随掌握度变（<1/3 时 1:2、=1 时 3:0），**全掌握时干扰项只从同块抽，该坑出现率归零**；新手期跨块占大头，正是坑最多的阶段。实测命中率：s=0 约 3%，s=1 为 0%。

池子规模 176 条（同块 16 + 跨块 160），每次抽 5 条干扰项 → **单条命中率约 3%**，所以这个坑**偶发、难复现**（用户首次刷题恰好命中）。

## 附带发现（独立于本题，但同源）

### 1. 答案集与题干不对齐（这题尤其明显）

4 条要点里，前 3 条是三个关键字的**定义**（回答「是什么」），第 4 条是 finally 的**边缘情况**（不回答「是什么」）。题干问「是什么」，答案集却有 1/4 不在这个范围——**边界不一致**。

用户漏选的**恰好是第 4 条**，这不是巧合：任何按题干正常作答的人都会漏它。

### 2. 没有任何机制校验「答案集是否匹配题干」

`content:audit` 只查要点文本规范（承载词、序号、标点配对、池容量…），**从不检查答案集与题干的一致性**。所以这类不一致可以一路活到线上。

### 3. `review:pairs` 有工具盲区

`pnpm review:pairs` 的扫描范围是**单个块内部**（`tools/review/pairs.ts`：`c.blockId === blockId`），而干扰项是**跨整大类**抽取的。

于是本题的雷（`java/exceptions` × `java/language-basics` 两个块之间的话题撞车）**该工具永远看不见**——不是内容没审，是工具够不着。

### 4. 要点 id 跨块撞车（同日发现的独立 bug）

`kp-lb4-1` … `kp-lb4-4` **同时属于两张卡**：

- `java/language-basics/01M3M39N0X9CV1HJ9G0XDVHS6P.md`
- `agent/llm-basics/01M3NE18CNV3D6F8H0K2M5N7Q9.md`

成因：要点 id 写成 `kp-lb4-N`（「该块第 4 张卡的第 N 条」），**id 里不带块名**，而 `lb` 在 `language-basics` / `llm-basics` 里都成立。`key_points` 主键是 `(card_id, id)`，库层面接受这种撞车。

后果：`drawDistractors` 用 `ownIds = keyPoints.map(kp => kp.id)` 过滤干扰项 → 同 id 要点被静默剔除（跨大类邻接时整卡要点都会消失，池子白白缩小）。

## 修法（待拍板）

两条独立、互补，建议都做；也可先做其一。

### A. 改提示语（治局部，4 处代码）

```
勾出所有属于这道题的要点
→ 勾出完整回答这个问题的要点
```

判据从「话题相关」移到「回答所必需」：「返回 finally 的值」不是回答「这三个是什么」所必需的 → 用户能明确排除。

涉及位置：
- `src/app/(drill)/DrillQuestion.tsx`（enumeration / comparison / judgment 三行）
- `src/app/(drill)/DrillFeedback.tsx`（批改标题）
- `src/lib/ai/qa.ts`（AI 上下文里的任务描述）
- `src/app/map/KnowledgeMap.tsx`（知识地图引导语）

代价：要发版；测试文案需同步。

### B. 改题干 + 拆卡（治这道题本身）

```
题干  final、finally、finalize 分别是什么？
  →  final、finally、finalize 各自的作用是什么？     ← 只留前 3 条，边界对齐

第 4 条要点拆成独立卡（它本来就是另一个问题）：
  finally 在什么情况下不会执行？
    ✓ System.exit 主动终止 JVM：调用线程的 finally 被跳过
    ✓ JVM 崩溃：进程猝死，代码没有执行收尾的机会
    ✓ 守护线程被 JVM 粗暴终止：收尾代码不保证有机会执行
```

改完，用户截图中那次作答（勾 1、6、8，不勾 9）**会得满分**。

代价：`content:upsert`（本地 + 生产）。

### C. 更彻底但更大的方向（未评估）

开放式题干是**批量隐患**：339 张 enumeration/comparison 里，**209 张是多要点 + 开放式措辞**（「有哪些」「怎么工作」「为什么」…）。它们不都踩雷（要同类话题在别块有要点才会），但这是一个**需要盯的模式**，不是一次性修完的。若要系统解决，选项有：

- 内容侧：给开放式题干加「答这几点」的收敛措辞（工作量大）
- 工程侧：扩展 `review:pairs` 到**同大类跨块**，或加一条 audit 规则，检测「同大类内话题词重合的要点被抽作干扰项」
- 判分层：不现实（会动摇判分口径）

## 不要做的事

- **不要用 `excludeAsDistractorFor` 逐条排除这些要点（11 条同大类 + 2 条邻类）。** 只是掩盖症状：池子里还有别的题的同款问题，新增内容又会漏。该字段应留给「两题之间必然矛盾」的真歧义。
- **不要改判分口径或选项总数。** 选项恒 9 是为了不泄露正确条数（spec §4.3），不能动。

## 复现方式（供后续核对）

```bash
# 1) 取出这道题的答案集（= 卡文件里的 keyPoints）
sed -n '/^keyPoints:/,/^---$/p' content/java/language-basics/01M3M39N0X9CV1HJ9G0XDVHS6P.md

# 2) 复现某用户某次复习的 9 个选项
#    prepareOptions(card, pools, s, userId, reviewIndexBase, K)
#    种子 = fnv1a(userId + '\0' + cardId + '\0' + 复习次数)  见 src/lib/options/rng.ts
#    → 换 userId 或复习次数，选项全变（已实测：本地/线上账号、第 1/2/6 次复习互不相同）
```

**注意**：选项**不落库**（全库 11 张表无"选项表"），是运行时从 `key_points` 现算的。所以「第 N 个选项」不是稳定标识，**排查必须拿选项文本原文**，不能拿序号。
