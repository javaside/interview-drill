## 问题是什么

一句话：

> **系统判「对不对」，用的是「这条要点属不属于这张卡」；而正确答案应该是
> 「这条要点能不能回答这个问题」。系统没有语义能力，用归属代替了语义判断。**

于是：

- 一条要点如果**同时能回答两道题**，它在「自己那张卡」里是答案，在另一道题里
  就被当成**错的**——尽管它在语义上是对的。
- 这个代替在多数时候成立（兄弟题的要点通常与本题无关），**只要发生跨题重叠就必然误判**。

判据的实际代码（`draw.ts`）：

```ts
const ownIds = new Set(card.keyPoints.map(kp => kp.id))
const eligible = (pool) => pool.filter(kp =>
  !kp.retiredAt && !ownIds.has(kp.id) && !kp.excludeAsDistractorFor.includes(card.id))
```

`ownIds` 之外的一切都是干扰项 = **「不是本卡的要点」即「错的」**。

## 触发实例（用户实测）

卡 `01M3M39N0X9CV1HJ9G0XDVHS6P`：《final、finally、finalize 分别是什么？》
（`java/language-basics`，enumeration，4 条要点）

用户线上作答：勾了三个关键字的定义，未勾第 4 条。
判分：`得分 3/4 · 漏选 1 条 · 错勾 0`。

用户困惑的是干扰项：

```
返回 finally 的值：try 的返回值与异常都被丢弃（字节码把覆盖路径编进返回）
```

**这句话是对的**——已用 `javac` 实测确认（`try { return 1; } finally { return 2; }`
返回 2；try 抛异常时异常确实被吞，字节码里连一条 `athrow` 重抛都没有）。

它归 `java/exceptions` 的卡《finally 里 return，方法返回什么？》，是**那道题的
atomic 唯一正解**（且 `public: true`，SEO 公开页可见）。

**用户的推理是成立的**：它讲的就是 finally，这道题问的就是 finally，按「属于
这道题」的字面意思就该勾。系统判它错，只因为它不归这张卡。

## 为什么不是措辞问题

初版把根因归为提示语歧义（「属于」有「属于答案集」/「与话题相关」两种读法）。
这个歧义**真实存在**，但它只是表征：

| 把提示语改成什么 | 用户选那句真话的结果 |
|---|---|
| 勾出所有属于这道题的要点（现在） | ❌ 判错 |
| 勾出完整回答这个问题的要点 | ❌ 判错 |
| 任何更精确的措辞 | ❌ 判错 |

**因为判分不看措辞，只看 `ownIds`。** 措辞只影响用户**猜**得准不准，不影响判定。
所以改措辞是止痛，不是治病。

## 根因：两条判据并存，系统只实现得了其中一条

```
语义判据：这条要点能否回答这个问题？      ← 真实世界的「对不对」，系统没有这种能力
归属判据：这条要点属于哪张卡？            ← 系统实际使用的，也是唯一实现的
```

系统用归属**代替**语义。这个代替的代价，spec 自己已经预言过。

## 附带发现（独立问题，同日查证）

### 1. 答案集与题干不对齐

4 条要点里，前 3 条是三个关键字的**定义**（回答「是什么」），第 4 条
（`finally 不执行的三种情况`）是**边缘情况**，不回答「是什么」。题干问
「是什么」，答案集却有 1/4 不在这个范围。

用户漏选的**恰好是第 4 条**——任何按题干正常作答的人都会漏它。

### 2. 没有任何机制校验「答案集是否匹配题干」

`content:audit` 只查要点文本规范（承载词、序号、标点配对、池容量…），
**从不检查答案集与题干的一致性**。这类不一致可以一路活到线上。

### 3. `review:pairs` 有工具盲区

扫描范围是**单个块内部**（`tools/review/pairs.ts`：`c.blockId === blockId`），
而干扰项是**跨整大类**抽取的。本题的雷（`java/exceptions` ×
`java/language-basics`）该工具**永远看不见**——不是内容没审，是工具够不着。

### 4. 要点 id 跨块撞车

`kp-lb4-1` … `kp-lb4-4` **同时属于两张卡**：

- `java/language-basics/01M3M39N0X9CV1HJ9G0XDVHS6P.md`
- `agent/llm-basics/01M3NE18CNV3D6F8H0K2M5N7Q9.md`

成因：要点 id 写成 `kp-lb4-N`（「该块第 4 张卡的第 N 条」），**id 里不带块名**，
而 `lb` 在 `language-basics` / `llm-basics` 里都成立。`key_points` 主键是
`(card_id, id)`，库层面接受这种撞车。

后果：`drawDistractors` 用 `ownIds` 过滤时，同 id 要点被静默剔除
（跨大类邻接时整卡要点都会消失，池子白白缩小）。与根因同源：**判定依赖 id
归属，而 id 归属本身就可能不唯一**。

## 修法（方向已定：先立检查规则）

**用户 2026-10-03 拍板：先走第 1 步。**

### 第 1 步：立内容检查规则（不改任何题目，立刻做）

> 检测「同块（后续扩到同大类）内，某条要点与另一道题的题干/答案共享话题词」的
> 组合，输出清单，并在 audit 中对**新增内容**报警。

价值：把 870 这个隐形数字变成**持续可见的清单**，且新内容一犯就报，防止继续烂。
这一步替代了绝大部分人工翻查。同时应**扩到跨块**——本次踩到的雷在跨块，而
现有工具只覆盖同块。

### 第 2 步：按清单改题干到「答案封闭」

**不变量**：题干必须具体到——**本卡的要点是它的完整答案，且别的卡的要点都不构成
答案**。

| 现在（开放，已被证明会踩） | 改成（封闭） |
|---|---|
| final、finally、finalize **分别是什么**？ | final、finally、finalize **各自的作用是什么**？ |
| —— | 第 4 条要点拆独立卡：《finally 在什么情况下不会执行？》 |

改完，用户那次作答（勾三个定义、不勾第 4 条）**会得满分**。

优先级：先改最开放的（「分别是什么」「有哪些」「怎么…」）。

### 第 3 步：残留的真冲突才用 `excludeAsDistractorFor` 逐条登记

改题干也解不掉的（两条要点真的互相矛盾），才登记。数量应远小于 870。

### 更彻底但更贵的方向（未采纳，记录在案）

换干扰项来源：不再用「别卡的真话」，改用「同话题但陈述错误」的干扰项。
**语义上干净，但内容成本爆炸**——spec 当初否掉选择题方案正是这个理由，
才选了「复用兄弟题要点」这条省成本的路。不推荐，除非前 3 步证明不够。

## 不要做的事

- **不要以为改提示语能解决。** 它只影响用户猜得准不准，不影响判定（见「为什么不是措辞问题」）。
- **不要直接去补 870 条（更别说跨块）登记。** 那是设计好的路，但工作量巨大、
  且 spec 自己预言过这负担会把内容逼向列举题。先用第 2 步把大部分消化掉。
- **不要改判分口径或选项总数。** 选项恒 9 是为了不泄露正确条数（spec §4.3）。
- **不要只改这一张卡。** 这是模型层面的问题，单卡修复不改变其余 270 张的风险。

```bash

sed -n '/^keyPoints:/,/^---$/p' content/java/language-basics/01M3M39N0X9CV1HJ9G0XDVHS6P.md

# 2) 复现某用户某次复习的 9 个选项
#    prepareOptions(card, pools, s, userId, reviewIndexBase, K)
#    种子 = fnv1a(userId + '\0' + cardId + '\0' + 复习次数)  见 src/lib/options/rng.ts
#    换 userId 或复习次数，选项全变（实测：本地/线上账号、第 1/2/6 次复习互不相同）

# 3) 看互斥登记欠了多少
#    countPairs(cards, blockId)  vs  buildPairs(cards, blockId)  见 tools/review/pairs.ts
```

**注意**：选项**不落库**（全库 11 张表无「选项表」），是运行时从 `key_points`
现算的。所以「第 N 个选项」不是稳定标识，**排查必须拿选项文本原文**，不能拿序号。
