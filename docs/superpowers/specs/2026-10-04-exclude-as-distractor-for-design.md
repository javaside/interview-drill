# excludeAsDistractorFor 全量补全与自动维护 · 设计

- 日期：2026-10-04
- 状态：**待实现**
- 上游诊断：[reviews/2026-10-03-ownership-vs-correctness.md](../reviews/2026-10-03-ownership-vs-correctness.md)
- 用户拍板：**① 范围三层全量 ② LLM 直判、不做 token 预筛 ③ 流程固定 + CI 闸门**

## 1. 要解决什么

判分只看归属（`ownIds`）：不属于本卡的要点一律判错。于是兄弟题的真话一旦被抽成本题
干扰项，用户按题意勾它就被判错 —— 用户线上实测过
（[reviews/2026-10-03-ownership-vs-correctness.md](../reviews/2026-10-03-ownership-vs-correctness.md)：
`java/exceptions` 的「返回 finally 的值：…」出现在《final、finally、finalize 分别是什么？》里，判 3/4）。

修法是在出题**前**就把这类要点从干扰项池里剔掉，工具就是这个字段。它全链路已实现，
只是**全库为空 —— 1,769 条活要点无一登记**（诊断文档记作 0 / 7058，分母是它的旧口径）：

```
content/*.md  excludeAsDistractorFor: [卡 id, …]
   → content:upsert → key_points.exclude_as_distractor_for
   → adapters 装配池 → drawDistractors 过滤
```

本设计补的是**数据与流程**，不改这条管道。

### 目标

1. **存量**：404 张活卡、1,769 条活要点，全部补上 `excludeAsDistractorFor`
2. **增量**：以后加题时自动更新，不需要任何人记得这件事
3. **正确**：判定标准可校准、结果可复核、漏判可被构建拦住

### 非目标

- 不改判分口径、不改 `drawDistractors`、不改 schema、不改 `content:upsert`
- 不做「题干封闭化」的内容改写（那是诊断文档的第 2 步，独立工作）
- 不引入运行时依赖：判定只发生在内容生产期，线上不受影响

## 2. 范围（实测）

三层，共 **108,891** 组「要点 × 目标题」，覆盖 **371 道**目标题：

| 层 | 组合数 | 怎么来 |
|---|---|---|
| 同块 | 6,475 | `sameBlockPoolOf` |
| 同大类跨块 | 48,307 | `buildDistractorPools` 的 crossBlock |
| 相邻大类 | 54,109 | 同上 neighbor（`degradedTo='neighbor'`） |
| **合计** | **108,891** | 平均每道目标题 **294** 条候选 |

口径与 `drawDistractors` 逐字对齐（否则判了用不上的、漏了真正会抽的）：

- 候选 = **其他卡的未退役要点**（退役要点永不被抽，不判）
- 层划分按 `queue.ts` 的 `buildDistractorPools`：邻居方向是**从目标题所在大类**
  取循环后继（该关系不对称，方向写反会差约 0.3%）
- **目标侧排除 33 张 `sequence` 卡** → 404 活卡 − 33 = 371 道目标题。
  `prepare.ts` 的 sequence 分支直接返回、从不调 `drawDistractors`，它不可能成为受害方；
  但 sequence 卡的**要点照旧进池**（会被别的卡抽走），所以只在「目标题」一侧排除

## 3. 判据

判定标准写死成一句话，禁止各判各的：

> **只读目标题的题干。一个称职的面试者，会不会把这条要点勾进去？
> 会 → 登记 `excludeAsDistractorFor`。**

「会勾」= 这条要点在语义上能回答那个问题。**不是**「话题相关」、**不是**「共享术语」。

校准用例（进单测，作为回归基线）：

| 要点 | 目标题 | 判定 | 为什么 |
|---|---|---|---|
| `java/exceptions`「返回 finally 的值：try 的返回值与异常都被丢弃」 | 《final、finally、finalize 分别是什么？》 | **是** | 它讲的正是 finally，按题意会勾 |
| `java/string`「类 final + 私有 char 数组 + 不提供修改方法，共同保证不可变」 | 同上 | **否** | 说的是不可变性，不是「final 是什么」；只是共享 `final` |
| `java/generics`「数组用 Array.newInstance(cls, n)」 | 《ArrayList 是线程安全的吗？》 | **否** | 说的是反射建数组，只是共享 `array` |
| `java/language-basics`「finally 不执行的三种情况」 | 《finally 里 return，方法返回什么？》 | **否** | 说的是「何时不执行」，不是「返回什么」 |

### 已知界限（写下来，免得当 bug 修）

- **LLM 判定不是确定性的**：同一组重跑可能翻转。所以账本记录判据版本，改判据必须
  整体失效重判（§6.3）。
- **相邻大类多为「否」**：54,109 组里绝大多数会判否，这些 token 是为「不漏」付的钱。
- 判定**不区分置信度**：只有是/否。低置信度靠抽检发现，不靠分数阈值。

## 4. 架构

依赖方向沿用仓库铁律 `lib → tools/audit`，纯核零 IO：

| 组件 | 位置 | 职责 | 依赖 |
|---|---|---|---|
| **候选枚举**（纯核） | `src/lib/content/exclusion.ts` | 三层候选对枚举、账本 key、账本 diff、判定合并 | `lib/content` 类型 |
| **闸门**（纯核） | `src/lib/content/audit.ts`（扩展） | 完整性校验：三层内有无未判定的组合 | 上一行的枚举 |
| **批处理与解析**（纯核） | `tools/content-exclusion/batch.ts` | 按目标题分组、切块（≤40）、构造 prompt、解析与校验响应 | 无 IO |
| **调用**（IO） | `tools/content-exclusion/run.ts` | 调 LLM、并发控制、重试 | `src/lib/ai/qa.ts` 的 `PROVIDERS` 注册表 |
| **CLI** | `tools/content-exclusion/cli.ts` | `pnpm content:exclusion [--full\|--dry-run\|--prune]` | 以上全部 |
| **落账**（复用） | `tools/review/register.ts`（扩展批处理变体） | 安全写回卡文件 YAML | 已有 |

命名沿用 `tools/content-new/` → `content:new` 的先例（这条命令是内容生产工序的一环，
不是人工审核工具，所以不进 `tools/review/`）。

复用两处已有实现，不重造：

- **`register.ts`**：已经解决了 YAML 写回的两个坑（`MATTER_OPTS` 防 Date 化与乱加引号、
  `detachedData` 防缓存污染）与「排序去重保证 diff 只显示新增」。加一个批处理变体
  （一次写多组判定），避免逐组调用时对同一文件做上百次解析+序列化。
- **`qa.ts` 的 `PROVIDERS`**：表驱动供应商注册表，配哪家用哪家。

## 5. 数据流

### 5.1 存量（一次）

```
枚举三层候选对（108,891）
  → 按目标题分组（371 组，每组平均 294 条候选）
  → 切块 ≤40 → 约 2,700 次调用
  → 解析出「是」的 (要点, 目标题) 对
  → 按要点聚合 → 写回卡文件 excludeAsDistractorFor
  → 「否」写入账本（§6）
  → pnpm content:audit 复核池容量（§7.2）
```

体量估算：输入约 10M token、输出约 1.5M，**约 5 美元以内 / 半小时量级**（并发 20）。
分批而非逐对，是为了把调用从 108,891 次压到约 2,700 次（40 倍）。

### 5.2 增量（每次加题，自动）

加一张新卡（约 5 条要点、非 sequence）只产生两类新组合：

- 新卡的要点 × 已有 371 道题 ≈ 5 × 371 = 1,855
- 已有 1,769 条要点 × 新卡（1 道目标题）≈ 1,769

约 **3,600 组 / 张卡**（其余 105,000+ 组读账本即跳过）→ 秒级到分钟级、几毛钱。

**幂等**：同一组合判定过就跳过，命令可重复执行。

### 5.3 失败即拦住（fail-closed）

某批调用失败/响应解析不了 → 重试一次 → 仍失败则**不写账本**。该组合保持「未判定」，
闸门因此报错。绝不把「没判」当成「判否」——静默丢弃会让漏网项无人发现，这正是
spec §9.1 否决双模型交叉预审的那个失败模式。

## 6. 账本

### 6.1 为什么「否」也要留记录

不留的话，每次加题都要把 11 万组重判一遍（5 美元 / 半小时）。留了才能只判新的。
「否」对出题**没有任何影响**，唯一用途是记账。

### 6.2 存在哪、长什么样

- **「是」的权威源 = 卡文件本身**（出题时读的就是它），不重复存
- **「否」= `content/.exclusion-ledger`**，一行一组，形如
  `01M3M39N0X9CV1HJ9G0XDVHS6P/kp-lb4-1|01M3M39N0ZAM96P346K7E77E44`，排序后写入

**为什么不写进卡文件**：一条要点平均要对 **60 道**目标题判「否」（实测分布：最少 49、
中位 60、最多 77）。若全写进 `confirmedIndependentOf: [60 个 ULID]`，单条要点的 YAML
从 3 行长到约 **1.7KB**（最大 2.2KB），一张卡 4-6 条要点涨 **7-13KB**，其中九成是 ULID。
卡文件必须保持人可读，且「是」才是需要人复核的部分。

代价：账本约 **10.9 万行 / 约 6.5MB**。它是生成物、按行 diff、可 `--prune` 重建。

### 6.3 判据版本与失效

账本头部记录 `provider / model / 判据版本号`。三处任一变化 → **账本整体失效**，
闸门报「判据已变更，需重判」→ 重跑 `--full`。避免新旧判据的结论混在一份账本里
无法解释。

### 6.4 悬空条目

要点退役、卡退役会让旧条目悬空。`content:audit` 只警告不报错（历史记录无害）；
`pnpm content:exclusion --prune` 清理。

## 7. 闸门与正确性

### 7.1 完整性闸门（CI）

接进现有 `content:audit`（`.github/workflows/content.yml` 已在 `content/**` 变更时跑）：

> 枚举三层候选对，若存在既不在卡文件 `excludeAsDistractorFor`、也不在账本里的组合
> → **构建失败**，消息指名「哪条要点 × 哪道题未判定」。

纯计算，不调 LLM，秒级。加一张新卡 → 它的约 3,600 组未判定 → 红 → 跑
`content:exclusion` → 绿。**这就是「自动更新」的强制点**：不判就交不上。

缺失账本文件 = 首次运行 → 只警告不报错（同 `.overlap.baseline` 的先例），
否则一上线就永久红。

### 7.2 池容量风险（必须显式处理）

登记会**吃掉同块可用池**：`auditLibrary` 拿扣除 `excludeAsDistractorFor` 后的条数
跟 `MIN_BLOCK_POOL` 比（enumeration/comparison 12、judgment 8、atomic 6）。

- `--dry-run` 先输出「本次登记对每块可用池的影响」与预计触线的卡，**再决定是否落盘**
- 真触线时，**正确的修法是改内容**（给块补卡、或把题干改到答案封闭），
  **绝不允许为了过闸门而漏登记** —— 那等于把 bug 放回线上
- 相邻大类层的登记**不影响** `MIN_BLOCK_POOL`（该检查只数同块），但仍会缩小实际可用池

### 7.3 三层正确性保障

1. **标准可校准**：§3 的一句话 + 四条校准用例进单测
2. **结果可复核**：人工抽检（命令行随机抽样 N 条给出「要点 / 目标题 / 判定」），
   命中率达标才算验收通过；不达标则改判据重判
3. **漏判被拦住**：§7.1 的完整性闸门 + §5.3 的 fail-closed

## 8. 与相邻问题的边界（别混进来）

- **要点 id 跨块撞车**（实测：`agent/llm-basics` × `java/language-basics` 共用 20 个、
  `concurrency/sync-tools` × `java/string` 共用 13 个）：**独立问题，不在本设计范围**。
  `excludeAsDistractorFor` 的键是**卡 id**（audit 已保证卡 id 全局唯一），不受要点 id
  撞车影响。撞车影响的是 `ownIds` 过滤导致的池子静默缩小，另行处理。
- **token 判据的遗留物**：仓库里未提交的 `src/lib/options/overlap.ts`、
  `src/lib/content/overlap.ts`、`tools/review/overlap-cli.ts`、`.overlap.baseline`
  是「话题词重合」预筛，实测精度不够（随机抽 40 组真命中近乎为零）且只认 ASCII 词。
  **本设计不依赖它**。它们的去留单独决定。
- **现有 `review:pairs`**：只扫同块、用字符重合度占位打分器、交互式。本设计落地后
  它被 `content:exclusion` 取代（旧命令保留或废弃，实现时定）。

## 9. 测试

| 层 | 测什么 |
|---|---|
| 纯核单测（`tests/lib/content/`） | 三层枚举与 `buildDistractorPools` 口径一致；目标侧排除 sequence；账本 key 唯一；diff 正确（已判定的跳过）；判据版本变化 → 失效 |
| 闸门单测 | 未判定 → 报错并指名；无账本 → 只警告；悬空条目 → 警告；`excludeAsDistractorFor` 里有 → 不报 |
| 批处理单测（注入 fake scorer） | ≤40 切块；响应解析；缺项/多項/坏格式 → 重试 → 仍失败则 fail-closed（不写账本） |
| 集成（PGlite 无关，纯内容侧） | 夹具：加一张新卡 → 闸门红 → 跑 exclusion（fake scorer）→ 闸门绿；`--dry-run` 不改任何文件 |
| 写回 | `register.ts` 批处理变体：diff 只含新增项、`verifiedAt` 不被 Date 化、重复执行幂等 |
| 验收（非单测） | 人工抽检存量结果 |

## 10. 已否决的方案（记录在案，别翻案）

| 方案 | 否决理由 |
|---|---|
| 只扫同块（spec §4.3 原文） | 用户踩的雷在跨块，覆盖不到 |
| token 预筛 + 人工 | 判据精度不够（实测随机抽样真命中近乎为零）且纯中文有召回洞 |
| 「否」全量写进卡文件 | 实测每要点 49-77 道题（中位 60），卡文件涨 7-13KB、九成是 ULID |
| 判定结果存 DB 新表 | CI 无 DB，闸门跑不了；且违背「content/ 是权威源」 |
| 逐对调用 LLM（108,891 次） | 40 倍调用量，成本与耗时不可接受 |
| 不设闸门、只出待办清单 | 正是现状的成因：清单无人看，空了 4 个月 |

## 11. 未决 / 风险

- **抽检通过线**：暂定**随机抽 100 条、人工判定一致率 ≥90%** 为验收线；首轮实测后
  可调（这是验收阈值，不是实现阻塞项）
- **账本 6.5MB 进 git**：接受；若日后成为负担，可改为按块分片或只存摘要
- **相邻大类 54,109 组多为否**：花钱买「不漏」。若成本超预期，可降级为「只在
  `degradedTo='neighbor'` 日志出现时才补判该层」——但那是缩小范围，需重新拍板
- **LLM 判定翻转**：抽检若发现同一组复活率偏高，需引入「两次判定取一致」策略
