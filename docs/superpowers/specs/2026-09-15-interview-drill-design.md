## 1. 背景与目标

程序员准备面试时，八股文知识"看了就忘"：复习过的内容在面试当天想不起来。现有方案各有缺口——面试题仓库（JavaGuide 等）只解决"内容从哪来"，不解决"怎么记住"；通用记忆软件（Anki）有记忆算法但没内容，且算法目标与面试场景错位。

本产品把两者合起来：**按知识块组织的面试题库 + 为面试当天优化的复习排期**。

用户旅程：设定**就绪日** → 在知识地图上勾选要刷的知识块 → 系统按可消化量收窄出这轮该刷的题 → 刷 → 就绪日当天所有题处于记忆峰值 → 之后转入维持模式等面试。

## 2. 范围

- **目标用户**：准备后端面试的程序员（第一版聚焦 Java 方向）
- **形态**：移动端优先的响应式 Web + PWA
- **第一版内容范围**：后端八股文 **11 个大类全部完善**，合计 **78 块 / 1345 题**

> **配额按真实分布分配，不均分。** 早期写的是"8 个大类，每类 8-12 块"——即每类 12.5% 的均等份额。第 5 轮用两个独立来源实测，真实分布是 **4-8 倍倾斜**的：「分布式/框架」在[小林 coding](https://xiaolincoding.com/interview/) 占 23.9%、在 [JavaGuide 文档](https://github.com/Snailclimb/JavaGuide/tree/main/docs)占 38.8%，而 JVM 只有 6.0% / 4.8%。两源在"谁最大谁最小"上完全一致。
>
> 均分配额的后果是双向的：**JVM 必然注水**（诚实只有 6 块，凑到 12 就得把回收器拆成 CMS/G1/ZGC 这种低频块）；**分布式/框架必然残缺**——它要在 12 块里装下 Spring 全家 + 消息队列 + 微服务 + 分布式理论 + 系统设计，至少 6 个互不相干的技术栈每个分 2 块。而 §2 自己的判词是"用户点进去发现只有 20 道题，核心承诺就没兑现"——**这个被否决过的场景会发生在最大的那个类里**。

| # | 大类 | 块 | 题 | 依据 |
|---|---|---|---|---|
| 1 | Java 语言基础与集合 | 10 | 180 | 实测 19.9%；集合是独立高频，不能当"基础"的附属 |
| 2 | 并发 | 9 | 160 | 实测 10.1%，块密度高 |
| 3 | JVM | **6** | 100 | 实测 4.8-6.0%，**写死 6 块防注水** |

| 6 | **Spring 生态**（Spring/Boot/MyBatis/安全） | 8 | 140 | 独立成类：JD 中 Spring Boot 出现 55.6%，仅次于 Java 本身 |
| 7 | **消息队列** | 5 | 85 | 独立成类：JD 消息队列 172 次 + Kafka 162 次 |
| 8 | **微服务与 RPC** | 5 | 85 | 独立成类：JD"微服务架构"178 次，最高频架构词 |
| 9 | **分布式理论与中间件** | 7 | 120 | CAP/一致性/分布式锁/分布式事务/分布式 ID/限流 |

改动本质：把"分布式/框架"一个格子拆成四个（6/7/8/9），把 JVM、Redis、操作系统从 8-12 块下调到 6 块。**总预算不变，只是放对地方。**

范围定成"全部完善"而非"先做一个类"，是因为产品的核心动作是**"哪块知识记不住就刷哪块"**——块不完善这个动作就不成立。用户点进"MySQL 索引"发现只有 20 道题，刷完心里还是没底，核心承诺就没兑现。

**但题库规模与单用户可消化量是两件事**，见 §5.6。

## 3. 核心洞察

**间隔重复算法为"终身记忆"优化，而面试复习是"短期冲刺"。**

标准 SM-2/FSRS 的间隔无上界：答对就翻倍，1→3→7→15→30→60 天。用户 3 周后面试，一道 D11 答对的卡会被排到 D26 复习——落在面试之后。用户在面试当天的记忆强度，恰恰是这类算法从未优化过的目标。

因此排期目标应是**面试当天的记忆强度最大化**，而非长期留存。

**但这不构成差异化。** 第 2 轮评审（`reviews/round2-product-value.md`）查证后推翻了本文档最初的说法。已核实的事实：

- **RemNote Exam Scheduler 已上线**：*"adjusts your flashcard practice schedule based on your exam date"*、*"Starting shortly before your exam, we'll help you review everything one extra time"*——后一句正是 §5.2 ④ 的末端窗口。
- **Anki 官方 FAQ** 教用户手算同一件事：*"divide the total number of cards you have by the number of days you have to study"*、*"leave 2–4 weeks between the time you will study the last new material and the time you will be tested on it"*——即 §5.2 的 `newPerDay` 与 `buffer`。
- Quizlet Learn 自 2017 年起支持 set due date；Anki 插件层有 Exam Scheduler / Exam Notifier，FSRS 有 desired retention。

公允的表述是：**Anki 官方没有内置 deadline 调度器**（社区最常请求的调度功能之一，至 2025 年 11 月无实现承诺），但 RemNote 和 Quizlet 内置了。"有考试日期概念的间隔重复产品"不是空白，是已经拥挤的。

§5 仍然是有价值的工程——经第 1 轮打磨后它是一份扎实的排期规格——但那是**实现质量，不是差异化来源**。一个已有三家做过的功能，做得更对不构成立项理由。

附带一条同源事实，应计入 §12 风险：Anki 开发者对 deadline 调度的模拟显示，**任何 deadline 调度都会在截止日前造成复习堆积**。这与第 1 轮实测出的 `day0` 溢出是同一现象——它是这类问题的固有性质，不是本文档的实现缺陷。

第二个洞察：**八股面试是口述的**，而翻卡自评存在"熟悉感 ≠ 能说出来"的系统性偏差——用户看到答案觉得"我知道"，真让他说却说不利索。

这个问题的**理想**解法是让用户真的出声说，但它在时间预算里装不下：口述一个 3-6 要点的答案要 30-60 秒，而"碎片时间快速刷题"要求单卡 15-25 秒（详见 §12 ④ 的推导）。理想形态从来就不会发生。

因此本产品的实际解法是**多选题 + 客观判分**（§6）：要点本身就是选项，干扰项从同知识块其他题的要点池里动态抽取。这么做放弃了"练回忆"，换来三样东西——判分客观（用户无法自欺）、速度达标、以及干扰项零额外内容成本。

**这是一个显式的赌注**，记在 §12 ④：反复辨认一道题的完整要点结构，能否迁移成面试时说得出来。见该条的论证与证伪方式。

## 4. 内容模型

### 4.1 层级

```
大类 (category)  →  知识块 (block)  →  题卡 (card)
并发              AQS 与锁           "AQS 是怎么实现独占锁的？"
```

题卡**单一归属**于一个知识块。跨领域的题（如"Redis 分布式锁"）通过 `relatedBlocks` 软链接指向其他块，不做多归属——否则块掌握度会被重复统计，知识地图失真。

### 4.2 题卡结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定标识。间隔重复要求同一道题在整个复习周期内 ID 不变 |
| `blockId` | string | 唯一归属的知识块 |
| `relatedBlocks` | string[] | 软链接，不参与掌握度统计 |
| `question` | string | 面试官口吻的问法，非教科书标题 |
| `cardType` | enum | **必填**，决定出题形式与计分（§4.3）。`enumeration` \| `comparison` \| `sequence` \| `judgment` \| `atomic` |
| `keyPoints` | **KeyPoint[]** | **3-6 条可得分要点**。既是本题的计分单位，也是干扰项来源（§4.3）。**结构见下** |
| `detail` | markdown | 展开讲解，可折叠，不参与计分 |
| `followUps` | string[] | 1-2 个追问，模拟面试官深挖 |
| `appliesTo` | string | 卡级版本适用范围，如 `JDK 8+`。**要点级的版本范围在 `KeyPoint.appliesTo`** |
| `frequency` | `high`\|`mid`\|`low` | 面试出现频度（§9） |

**`KeyPoint` 结构**（第 3 轮评审的唯一有截止期限的改动——必须在批量生产 1400 张卡**之前**定好，否则全部返工）：

```ts
type KeyPoint = {
  id: string            // 块内唯一。互斥登记、漏点统计、干扰项引用都指向它
  text: string          // 要点正文
  source: Source        // 该条要点自己的出处，精确到类/方法/章节/RFC 小节
  appliesTo?: string    // 该条要点自己的版本范围，缺省继承卡级
  excludeAsDistractorFor: string[]   // 本要点对这些题也成立，不得抽作它们的干扰项
  verifiedAt: string    // 审核签字日期，驱动 §9.2 的增量复核
  public: boolean       // 公开要点：用于 SEO 题目页 lead-in，且构成免费用户的
                        // 跨块干扰项池（§4.3）。每题标 1-2 条
}
```

**四处改动，各有各的原因**：

- **`source` 下沉到要点级**。§9 ③ 要求"每条要点能否在 `sources` 里逐条验证"，但卡级 `sources: Source[]` 在结构上只能表达"这张卡参考了这几篇资料"，表达不了"这条要点对应这一段"。审核时无法机器校验覆盖，约束必然退化成"贴个章节链接了事"。
- **`appliesTo` 下沉到要点级**。同一张卡里"synchronized 会锁升级"（JDK 6+）和"偏向锁默认开启"（JDK 6-14）版本范围不同，卡级单值表达不了。
- **`excludeAsDistractorFor` 挂到要点上，不是卡上**。互斥的判断单位是"**某条要点**对某道题是否也成立"，挂在卡级会把整张卡的所有要点一起排除，误伤 3-6 倍。
- **`verifiedAt`** 让 §9.2 的版本衰减复核能按要点增量做，不必全量重读。

### 4.3 keyPoints 既是答案，也是选项池

`keyPoints` 一份内容同时干两件事——这是整套设计能成立的支点：

- 对**本题**：它是答案要点，是计分单位
- 对**同块其他题**：它是干扰项

于是干扰项的内容成本是**零**。这条很关键：最初排除选择题方案的理由正是"八股文出优质干扰项极难，内容成本反而高"。但从同知识块的兄弟题里抽要点当干扰项，抽到的天然是真实、专业、似是而非的东西——比人工编的干扰项质量还高，因为它们本来就是正确的技术陈述，只是不属于这道题。

**出题规则**：正确要点全出（3-6 条），**干扰项补足到固定 9 个选项**（即抽 3-6 条）。

> **选项总数必须固定。** 早期写的是"干扰项固定 3 条，合计 6-9 个选项"——那等于把答案数编码进了选项个数：`选项总数 − 3 = 正确条数`，每道题都能被数一遍破解。而同一段里写的设计目标正是"不告诉用户有几条是对的，否则用户会数数做排除法"。总数固定为 9 之后，选项个数不携带任何信息。

#### 题型：`keyPoints` 只覆盖三分之一的真实八股

第 5 轮逐题分类了 131 道公开真题（MySQL 94 + JVM 37），**天然可枚举的只占 33.6%**：

| 题型 | 占比 | 与"9 选框 + 无序要点"的契合 |
|---|---|---|
| 可枚举型 | 33.6% | ✅ 完美 |
| 因果链/过程型 | **19.8%** | ❌ **顺序就是答案，而要点是无序集合** |
| 对比推理型 | 15.3% | ⚠️ 结论可编码，推理本身丢失 |
| 权衡判断型 | 11.5% | ❌ 没有唯一正确集 |
| 单点事实型 | 9.9% | ❌ 凑不满 3 条 |
| 情景推演型 | 7.6% | ❌ 答案是"会/不会"+ 一条推理 |
| 手写/操作型 | 2.3% | ❌ 不适用 |

**问题不是作者可能偏爱列举题，是流程在付钱请他写列举题**——三条独立机制方向完全一致，没有任何反向的力：

1. **CI 硬拒**（§8.3）："要点少于 3 条的卡直接构建失败" → 单点事实型 + 情景推演型合计 **17.5% 被自动挡在库外**
2. **审核经济学**（§9.1）：要求每条要点在英文一手资料里逐条验证。枚举型最好验证（官方文档里就有那个列表）；因果链和权衡型最难验证（"为什么不用跳表"在 MySQL 手册里根本没这一段，是推理出来的）。在 145-220 小时的压力下，作者自然漂向好审的题型
3. **互斥登记惩罚**（本节）：对比型和权衡型的要点**天生对兄弟题也成立**——"B+ 树非叶子节点只存键，树更矮"对同块几乎每道索引题都成立，必须逐个登记 `excludeAsDistractorFor`，负担是枚举型的数倍

这与 §12 ③ 对自评方案下的判词结构完全相同：不是用户有动机自欺，是产品**付钱请他**自欺。这里是流程**付钱请作者**写列举题。预估收敛结果是 **70-85% 列举题**，对上真实世界的 33.6%。

#### 分型出题：五种 `cardType`，同一套框架

**不放弃 `keyPoints`**——它对三分之一的题是最优解，干扰项复用机制也确实成立。要做的是承认题型存在，在同一个框架里给每型一条规则：

| `cardType` | 目标占比 | 出题形式 | 计分 |
|---|---|---|---|
| `enumeration` | ≤ 45% | 9 选，3-6 条正确 | `max(0, (勾对−勾错)/正确总数)` |
| `comparison` | ~15% | 9 选，**正确要点必须成对出现**（X 的特性 + Y 的对应特性）；干扰项优先抽"把两边说反"的变体 | 同上 |
| `sequence` | ~20% | **排序题**：4-6 个步骤拖动排序。**选项不打乱是本型的强制例外** | 全序正确满分，或按逆序对数量给部分分 |
| `judgment` | ~12% | **二段式**：先选结论（会/不会/取决于），再选支撑要点；**结论错则本题 0 分** | 结论 × 要点 |
| `atomic` | ~8% | **单选 4 选 1**，不走 keyPoints 计分 | 对/错 |

**目标占比必须是配额，不是倡议。** §2 的配额表需按大类再声明各题型的目标条数，审核时按型收题——这是唯一能对抗上面那三条漂移力的机制。

**若只肯做一型，做 `sequence`。** 它是唯一一处产品**主动做错事**（不是覆盖不到，是打乱顺序把答案毁了），占 19.8%，而且最便宜：一个拖拽 UI + 一次排列比较，顺序本来就在要点里，无新增内容成本。

**每次出现重抽干扰项、重排顺序。** 间隔重复配固定选项有个经典毛病：用户记住"第 2、4、5 个是对的"，而不是记住内容。动态抽取直接免疫这个问题，顺带让同一道题每次重复都略有不同（这本身有利于记忆）。

> **`cardType = 'sequence'` 是本条的强制例外。** 对因果链/过程型的题（binlog 两阶段提交、类加载过程、SQL 执行顺序），**顺序就是答案**。打乱选项等于每次复习都在抹掉这道题要考的那个东西——用户可以永远拿满分，然后在面试里把 redo 和 binlog 说反。这一型改为排序题，选项按固定顺序呈现，考的是用户能不能排对。

#### 干扰项分层抽取（修正干扰项枯竭）

**不能只从同块抽。** 实算：一个块约 20 题 × 4.5 要点 = 90 条要点池；用户刷完该块一轮（20 题 × 约 6 次复习 × 3 个干扰项）要抽 **360 次**，平均每条要点被抽中 4 次，**用户会见过块内 98.2% 的要点**。刷到后半程，所有选项都眼熟，干扰性归零。

因此干扰项**分层抽取**，比例约 1 : 2：

| 层 | 来源 | 作用 |
|---|---|---|
| 约 1/3 | **同块**其他题的要点 | 最难辨别，维持区分度 |
| 约 2/3 | **同大类**其他块的要点 | 池子放大约 10 倍（90 → 900），解决枯竭 |

干扰项总数是 `9 − 正确要点数`，即 3-6 条；按上述比例向下取整分配，余数给跨块层。

**这也修正了 §12 ④ 的补救路径**：原来写的"缩窄抽取池""增加干扰项数量"两条，方向都是**加速**枯竭，必须作废。正确的难度调节是**调整分层比例**——掌握度越高，同块层占比越大，池子不变而辨别难度上升。

#### 干扰项在服务端抽，客户端只拿渲染好的选项

**客户端永远不持有未解锁内容的语料。** 取今日队列时（一天一次），服务端为队列里每张卡**预生成未来 K 次的选项集**：

```ts
type PreparedOptions = {
  cardId: string
  variants: Array<{           // K 份，对应该卡接下来 K 次复习
    optionTexts: string[]     // 9 条，已打乱
    correctIndices: number[]  // 判分用，客户端离线判分需要
    distractorKeyPointIds: string[]   // 只回传，不用于渲染
  }>
}
```

随队列一起下发并落 IndexedDB。四个目标同时达成：**离线成立**（今天的量已在本地）、**§4.3 的"每次重抽"成立**（取预生成序列的下一项）、**`review_log.distractorIds` 可复现**、**未解锁块的要点不进客户端语料**——只有被抽中的那几条以纯文本形式出现在已渲染的选项里。

#### 免费用户的跨块干扰项：公开要点池

免费用户只解锁 2 个块，但跨块层要从整个大类（约 900 条要点）抽。实算泄露量：40 题 × 6 次复习 × 2 条跨块 = **480 次抽取**，在 900 条池上期望见过 `900 × (1 − e^(−480/900)) ≈ 372` 条要点 ≈ **83 道题的完整答案**——是免费层本身（40 道）的 2.1 倍。用户走正常 UI、不碰开发者工具就能拿到。

**解法**：`KeyPoint` 增加 `public: boolean`。每道题标 1-2 条要点为公开（同时用于 §7 的 SEO 题目页 lead-in）。

| | 同块层 | 跨块层 | 泄露 |
|---|---|---|---|
| **免费用户** | 从已解锁的 2 个块抽 | 从本大类的**公开要点池**抽（约 200-400 条） | 零——本来就公开 |
| **付费用户** | 同块 | 整个大类（他买了） | 不适用 |

**不能让免费层退化成"全从同块抽"**：20 题的块只有 90 条要点池，360 次抽取——正是本节开头算出并否定的 98.2% 枯竭场景。而免费层恰恰是唯一必须演示"机制有用"的地方（§10.1），在那里让机制退化等于演示产品**不能**做什么。

**§6 屏② 的归属显示同步降级**：错勾了未解锁块的要点时，显示"属于本大类的另一道题（未解锁）"，而非具体题目。保住"你把两个概念搞混了"的一半信息价值，堵住 (要点 → 题) 归属关系的泄露，且天然是个转化点。

#### 抽取算法规格（`lib/options`）

§4.3 自称是"整套设计能成立的支点"，因此它必须可测。四条必须写死，否则实现者会各自发明：

```ts
drawDistractors(card, pools, count, rng): KeyPoint[]
```

1. **随机源是注入的确定性 PRNG**，不是 `Math.random()`。`seed = hash(userId, cardId, reviewIndex)`，用 xoshiro / sfc32 之类（十几行）。这一条同时解决三件事：可单测、`review_log.distractorIds` 真能**复现**而不只是记录、服务端能校验客户端结果。也是服务端预生成选项集的前提。
2. **池不足时的降级**：优先从同大类补足；同大类也不够时**从相邻大类抽**并记日志告警。**绝不允许少给干扰项**——那会让选项总数变化，直接泄露正确条数（见上文）。也不允许重复抽同一条。
3. **分层比例用分数表，不用小数**，与 §5.2 的起始档表同构：

   | 条件 | 同块 : 跨块 |
   |---|---|
   | `3·s < 1` | 1 : 2 |
   | `3·s < 2` | 1 : 1 |
   | `s < 1` | 2 : 1 |
   | `s = 1` | 3 : 0 |

   必须是分数比较。写成小数会原样重演 §5.2 记录在案的 `2/3 = 0.6667 < 0.67` 那个 bug。
4. **`excludeAsDistractorFor` 需要反向索引**。字段语义是"本要点对**这些题**也成立"，而抽取时要做的是反向查询：给定目标题 T，排除所有 `excludeAsDistractorFor` 含 T 的要点。内容同步时物化 `Map<cardId, Set<keyPointId>>`。

#### 互斥检查的真实工作量

**判断单位是"(某条要点, 另一道题)"，不是"(题, 题)"。** 早期文档按后者估成"20 题的块约 190 对"，低估 **9 倍**：

```
单块：20 题 × 4.5 要点 × 19 道其他题 ≈ 1,710 次判断
全库：70 块 × 1,710 ≈ 120,000 次判断
```

纯人工不可行。流程必须是**机器召回 + 人工确认**：

1. LLM 对块内全部 1,710 组合做**召回导向**的预筛（宁可多报不可漏报），标出疑似"这条对那题也成立"的组合
2. 人工只确认被标出的（预计 5-10%，即每块 85-170 条，约 10 秒/条）
3. 漏网的靠 §9 ④ 的用户报错闭环兜住

这里用 LLM 是**安全的**，与 §9.1 ③ 被否决的双模型预审不同：预筛的失败模式是假阴性，而假阴性有报错闭环兜底；双模型预审的失败模式是**把相关性错误系统性路由出人工队列**，没有任何东西兜底。

**成本：约 25-60 小时，且这笔钱不在 §9.1 的逐题审核里，必须单列。**

**跨块（第 2 层）不做全量互斥检查**，只做抽检——跨大类概念撞车的概率远低于同块，且报错闭环能覆盖。这是有意识的取舍，不是遗漏。

**三个副产品**：
1. 判分完全客观，用户无法自欺（对比原自评方案，见 §12 ③）
2. 错勾数据告诉我们**用户把哪些知识点搞混了**——比"漏了哪条"信息量更大，是内容迭代的直接依据
3. 某条要点若 80% 用户漏选，说明它写得太偏，不配当得分点

每条要点自带 `source` 和 `appliesTo`（§4.2）不是装饰。八股文最大的坑是版本差异（偏向锁在 JDK 15 后被废弃），标到要点级、且出处指向英文一手资料，用户才敢信（§9.1）。

### 4.4 掌握度计算

**卡状态**（存于 `card_state`，字段见 §8.1）：

- `phase`：`new`（从未刷过）| `learning` | `done`（本周期计划已走完）| `paused`（所属块被取消勾选，§5.5）
  `new` 是**独立状态，不是 `s = 0`**。从没见过的卡和见过但说不出的卡，需要的干预完全不同
  `paused` 的卡保留 `plan[]` 但不进 `todayQueue`，重新勾选块时按剩余窗口续上
- `s ∈ [0,1]`：最近 3 次得分的加权平均，权重 `3:2:1`（不足 3 次按已有次数归一）
- 单次得分**按 `cardType` 分派**，但一律归一化到 `[0,1]` 再喂给 §5.2 的起始档判断——**排期引擎一行不用改**：

  | `cardType` | 单次得分 |
  |---|---|
  | `enumeration` / `comparison` | `max(0, (勾对数 − 勾错数) / 正确要点总数)` |
  | `sequence` | `1 − 逆序对数 / 最大逆序对数`（全序正确得 1） |
  | `judgment` | 结论错 → `0`；结论对 → `结论分 0.5 + 0.5 × 要点得分` |
  | `atomic` | 对 `1` / 错 `0` |

  分母（或对应的归一化基数）随复习记录一起存（§8.1）。

枚举型公式里减去勾错数，是为了堵住**乱勾全选**这条路——不扣错的话，全选就能拿满分。下限取 0，避免负分传进 §5.2 的起始档判断。

**注意一个此前被忽略的精度问题**：要点条数是这个分母，而 §5.5 用"得分比例 `< 1/2`"触发重排。同样是"我答对了两个核心点"，3 要点卡（2/3）不重排、6 要点卡（2/6）重排。§5.2 花了整整一段修掉 `2/3 = 0.6667 < 0.67` 那个 **1/1296 的浮点误差**，却一直留着这个 **2 倍的粒度误差**。这是要点粒度标准必须写死的直接原因（§9.3）。

`s` 取加权平均而非"最近一次"：单次观测做估计量方差太大，连续五次满分的卡不该因为一次走神就把整条计划推倒重来。

**块掌握度** = 块内**当前计划内**卡片的 `s` 加权平均，权重按 `frequency`（high=3, mid=2, low=1）。

分母**只算计划内的卡**。被 §5.4 收窄排除的低频卡不进分母，UI 上单独标注"已排除 N 张低频"。否则会出现一个荒谬的死结：用户听产品建议只刷高频，把高频全刷到满分，块掌握度仍永远卡在 45%（3 张 high 满分 / 权重总和 20）——地图永远是红的，而唯一能让它变绿的动作，是去刷产品刚刚明确告诉他不要刷的低频卡。

`phase = new` 的卡不进分母；块内全为 `new` 时地图显示"未刷"而非 0%。

## 5. 排期引擎（核心）

> 本节经过一轮敌意评审后重写。评审报告见 `docs/superpowers/reviews/round1-scheduler-correctness.md`，其中的实测数字在下文中用于说明"为什么不能那样写"。

### 5.1 接口与不变量

```ts
schedule(
  cards: Card[], cardStates: CardState[],
  readyByDate: LocalDate, dailyCapacity: number, today: LocalDate,
  reservedLoad?: ReadonlyMap<number /* dayOffset */, number /* count */>
) → { todayQueue, plans, overloadWarning }
```

**`reservedLoad` 是必需的，不是可选优化。** `cards[]` 永远是用户选中块的子集（§5.6），而**不在 `cards[]` 里但已有计划的卡，仍然占用那些天的容量**。没有这个参数，§5.3 的装箱判断"当天已满"和 §5.4 的前缀和判据都只能看到局部负载。

失败场景：用户周三接到周五面试，按 §5.8 勾 MySQL + Redis（60 张卡）做临时加密。`schedule()` 只收到这 60 张，看到 day0、day1 各用了 0/45，判定装得下。但用户原有计划在这两天各有 40 张其他块的卡——**实际负载 70/45，超容量 56%，而 I5 被违反、§5.4 不告警**。产品在最该可靠的那一天（面试前一天）静默超载。

调用方负责从"不在 `cards[]` 里但有计划的卡"汇总出 `reservedLoad`。§5.3 装箱与 §5.4 前缀和都先减去它。`lib/scheduler` 仍是纯函数、零依赖、可完整单测。

**纯函数**：无 IO、无副作用、不读系统时钟。

**为什么是 `readyByDate` 而不是 `examDate`**：用户不知道自己哪天面试。真实求职是 1-3 个月的滚动过程——投简历、等回复、面试方提前 2-5 天约时间、一面二面各自独立约。于是"你哪天面试"这个问题，在用户最需要开始准备的那一刻**根本没有答案**；等他有答案时只剩 3-5 天，`R = 4` 的窗口铺出来是 `[0, 1, 3]`，产品最该发力的时候发不上力。而强制填写的结果是用户填假日期，之后每约到一场就改一次，每次改都触发重排（§5.5），§6 屏② 的圆点每次都变——正好踩中本文档自己的判词"用户感知到的东西是错的，比感知不到更糟"。

**"你希望哪天准备好"是人人都答得上来的问题**，且答案由用户自己掌控，不依赖面试方。引擎一行不用改，只是换了个语义更诚实的输入。过了就绪日自动转入 §5.7 的维持模式，正对应"准备好了在等面试"那段日子。真正约到面试时走 §5.8 的临时加密。

**时间类型钉死**：`today` 与 `readyByDate` 均为**本地日历日**（`YYYY-MM-DD`），日差按日历天数计算，**不用毫秒差除以 86400000**——DST 切换那天是 23 或 25 小时，除法会得到 `0.96` 或 `1.04`，取整就少一天。日界定在**本地时间 04:00**：刷题用户会熬夜，23:50 和次日 00:10 应算同一天。

**排序必须确定**：所有涉及卡片排序的地方，排序键末尾一律追加 `cardId`。否则同键时的顺序取决于数据库返回顺序或对象键顺序——那不在 `schedule()` 的参数里，"输入确定则输出确定"就是假的，§7 的单测和 §8 的重放一起落空。

**五条不变量**，每条对应 §11 的一组单测：

| # | 不变量 |
|---|---|
| I1 | 每张计划内的卡，末次复习落在 `[E - fw + 1, E]`，高频卡优先占 `E` |
| I2 | 计划内日期严格递增，同一张卡不在同一天出现两次 |
| I3 | `R ≥ 0` 且存在计划内卡片时，`todayQueue` 非空 |
| I4 | 计划生成后不再重算，除非触发 §5.5 的三种条件之一 |
| I5 | 任一天负载 ≤ `dailyCapacity`，唯一例外是 `E = 0`（就绪日就在明天），此时超载且必须告警 |

### 5.2 计划生成（plan-once）

**计划一次性生成并持久化，之后只消费不重算。**

这是对早期设计的根本修正。早期方案是每次提交后按剩余窗口重算，`d_1` 取剩余窗口的比例分数——那构成芝诺式递推，步长随窗口缩短而缩短，复习次数发散。实测一张「每次都通过、承诺复习 3 次」的卡，实际被复习 **12 次**，从第 11 天起变成每日复习，而 §6 屏② 那排圆点每刷一次就多画一个。**没有不动点的排期不能用。**

**① 窗口**

```
R = readyByDate - today                       // 日历天数
buffer = 1 (R < 30) | 2 (30 ≤ R < 50) | 3 (R ≥ 50)
E = R - buffer                             // 末次复习的目标日（相对今天的偏移）
```

`buffer` 是**查表不是公式**。早期写成 `clamp(round(R × 0.05), 1, 3)`，实测它在 `R ≤ 29` 恒为 1、`R ≥ 50` 恒为 3，只在 `R ∈ [30, 49]` 真正起作用——而产品主场景（1–3 周备考）全落在常数区。查表更诚实，也免掉 `round` 半值方向的歧义。

`R < 0`（就绪日已过）→ 视同未设日期，走 §5.7，并提示用户更新日期。这是必然发生的输入。

**② 绝对间隔阶梯**

```
INTERVALS = [1, 2, 4, 8, 16, 32, 64]       // 天，绝对值
```

起始档由掌握度决定，**用分数比较，不用小数阈值**：

| 条件 | 起始档 |
|---|---|
| `phase = new` 或 `3·s < 1` | 0 |
| `3·s < 2` | 1 |
| `s < 1` | 2 |
| `s = 1` | 3 |

必须用分数比较，且 **`s` 必须以精确有理数存储**（整数分子/分母），比较用交叉相乘，不用浮点。

理由：`s` 是最近 3 次得分的 `3:2:1` 加权平均（§4.4），单次得分是 `max(0, 勾对数 − 勾错数) / 正确要点总数`，分母 3–6。全是有理数，通分后分母不超过 `6 × 6³ = 1296`，整数运算完全够用。

早期写成 `s ≥ 0.67` 出过实际错误：`2/3 = 0.6667 < 0.67`，三要点卡答对两条会掉进下一档——同样是"大部分对了"，三要点卡的用户被平白多排一遍。若改用浮点算 `3·s`，`3 × (2/3)` 可能得到 `1.9999999999999998`，同一个 bug 换个地方复发。`s ≥ 0.9` 那档更糟：3–6 要点卡里 `1.0` 之下的最大值是 `5/6 ≈ 0.833`，那一档**实际只有满分可达**，`0.9` 是假精度。

**③ 铺阶梯，末端截断**

```
a = [offset]
idx = 起始档
while a.last < E' and idx < len(INTERVALS):
    a.append(a.last + INTERVALS[idx]); idx += 1
plan = [x for x in a if x < E'] + [E']      // E' = 该卡的末次目标日，见 ④
```

**复习次数是输出不是输入**——由窗口长度决定刷几遍，那张容易出错的 `n` 表就不需要了。

实测样例（`offset = 0`，新卡）：

```
E=20 → [0, 1, 3, 7, 15, 20]        E=6 → [0, 1, 3, 6]
E=4  → [0, 1, 3, 4]                E=2 → [0, 1, 2]        E=0 → [0]
```

全部严格递增、起于今天、止于 `E`，无退化。对照早期的比例缩放公式：`E=4` 时它算出 `[1,2,3,4]`，间隔 `[1,1,1,1]`——**一到两周备考时"递增间隔"完全退化成连着刷四天**，而这恰恰是它声称要利用的机制。更糟的是穷举 `n=1..5, E=n..199` 后发现**不存在任何 `d_i = 0`**：新用户走完激活流程，第一屏看到的是"今天没有要复习的题"。

**④ 首次曝光错峰 + 末端窗口**

早期公式里 `d` 只由 `(E, n)` 决定，不含任何卡片自身信息——**同一批新卡拿到逐字节相同的计划**，全堆在同几天。两处修正：

- **新卡配额**：`newPerDay = max(1, floor(dailyCapacity × 0.35))`。按 `(frequency 降序, cardId 升序)` 排位，第 `j` 张新卡的 `offset = min(j / newPerDay, E)`，剩余容量留给复习。不加配额的话，150 张新卡各自还带一次"+1 天"的复习，前端必然拥塞。
- **末端窗口**：所有卡的末次都想落在 `E`，那天必然爆。末次分散到 `[E - fw + 1, E]`，`fw` 从 `ceil(计划内卡数 / dailyCapacity)` 起，若仍有某天超容量则递增 `fw` 直到满足 I5。高频卡分配到最靠近 `E` 的日子。

第二条是**对早期设计的明确让步**：「末次严格落在面试前 buffer 天」降级为「落在末端窗口内」。早期把"末端对齐"和"超载只能往前挪"同时写成硬保证，而这两条在任何满载场景下互斥——实测 150 张卡 / `R=7` / 容量 30 时，`day0` 会拿到 **420 张**（超容量 14 倍），且 150 张里有 **120 张**的末端对齐被打破。互斥的保证必须明着选一个，不能两个都写。

### 5.3 容量装箱

不做事后均衡，容量是**生成时的硬约束**。按 `(frequency 降序, cardId 升序)` 逐卡装箱：

- **末次不可移动**，优先占位（由 §5.2 ④ 的末端窗口保证不超容）
- **中间次遇到当天已满 → 往后推一天**，最多推到末次的前一天；若该卡已占用目标日则继续后推（保证 I2）
- 推到无处可去 → **丢弃该次复习**，计入 `overloadWarning.dropped`

**往后推而非往前推。** 往前推会挤爆今天——今天没有"前一天"可以继续推，是唯一被豁免容量的日子；而且提前复习等于缩短间隔，对间隔重复没有价值。少刷一遍，好过把一遍刷在没用的位置上。

### 5.4 超载检测

判据是**前缀和**，不是总量：

```
for t in 0..E:
    if 累计需求(day 0..t) > (t + 1) × dailyCapacity:
        告警，报出最早违反的 t
```

总量判据（`Σ复习次数 > R × dailyCapacity`）不够用——它只检查了可行性条件里最松的那一项，而负载天然堆在前端，**卡死的永远是前缀**。实测：100 张卡 / `R=30` / 容量 30 时，总量 `400 ≤ 900` 不告警，`day0` 却仍然溢出到 40 张。

告警文案报**最早排不下的那一天**（"你前 3 天就已经排不下了"比"总量超了"可操作得多），并给出按 `(frequency 降序, cardId 升序)` 的收窄建议。收窄后**必须重跑一遍前缀和判据**确认真的可行：早期的收窄建议只满足总量判据，实测砍完之后 `day0` 仍是 66 张 / 容量 30——"补救成功"而问题原封不动。

**默认 `dailyCapacity = 45`**：一张新卡按阶梯约 6 次复习，45 × 21 天 = 945 次容量 ÷ 6 ≈ 157 张新卡。这个默认值定义了单用户在一个 3 周窗口内能刷透的题量上限。

**注意超载是常态而非异常**，见 §5.6。

`E = 0`（就绪日就在明天）是唯一允许突破容量的情况：所有卡排在今天并告警。此时没有更好的选择。

### 5.5 重新生成计划

计划只在四种情况下重生成，其余时候只消费：

1. **答错**：得分比例 `< 1/2` → 起始档退回 0，**从明天起**重新生成
2. `readyByDate` 变更
3. `dailyCapacity` 变更
4. **选中块集合变更**（地图上勾选/取消块）

**第 4 条是产品最高频的动作**（§10 的"块级选择"、§5.6 推论 1），早期文档漏了它，导致实现者无规格可依。三种情况分别定义：

- **加块**：只为**新增块**的卡生成计划，**已有卡的计划一律不动**。新增卡装箱时把已有计划的占用通过 `reservedLoad`（§5.1）算进去。末端窗口对新增卡单独算，可能与已有计划的末端窗口撞在同几天而轻微突破 I5——此时**必须走 §5.4 告警**，不得静默。
  不这么做的两条路都坏：完全不重排 → 新块的卡 `plan[] = []` 永不进队列，用户勾了块什么都没发生；全局重排 → `newPerDay` 排位和 `fw` 全部重算，**原有每张卡的末次都可能挪位、圆点整排重画**，正是 §6 判为"比感知不到更糟"的情形。
- **减块**：被取消块的卡置 `phase = paused`，`plan[]` **保留但不进 `todayQueue`**。重新勾选时按剩余窗口续上，不从头再来。
- **重生成的作用域一律是"新增/变更的卡"，不是整个选中集合。** 这条同时适用于第 1 条的答错重排：只重排那一张卡，把它的新阶梯装进现有占用图。

**§11 需补三条验收**：加块不动老计划；减块的卡不进队列；加→减→加往返后计划与只加一次一致。

答错重排从**明天**起，不是"当天稍后"。早期写的是当天稍后，它和"每次提交重跑 `schedule()`"叠加会构成**同日死循环**：`R ≤ 1` 时全部卡排今天 → 刷完重跑 → 还是今天 → 无限循环，而且发生在面试前一天这个产品最重要的日子。

**终止状态**：计划中已无 `> today` 的项 → `phase = done`，退出 `todayQueue`。早期文档没有任何终止条件，`schedule()` 在任何输入下都至少吐出一次未来复习。

> **v2 修订（2026-09-28，计划 6 常备模式）**：本条终止语义废除——「冲刺窗口收口」被误当「掌握」，实测出现「就绪日临近 + 得分全错 → 全部毕业永久退休」的缺陷（且 done 无任何复活路径）。新语义：**计划耗尽（答对消费完末项 / 答错且 E=0 重排得空 / 防御性空计划）自动转入 §5.7 维持滚动**——答错次日 +1 天再见（临阵磨枪；+1 不当天回队，不踩同日死循环红线），答对按当前档位拉长间隔。`phase=done` 不再自动产生，仅作 v1 存量兼容（保存设置时按解锁块复活为 learning）。同批修订：常备模式（maintenance）下设置变更不清空滚动计划（维持分支不生成计划，清空即黑洞）；常备模式新卡首曝按 `newPerDayOf` 限流（防全量洪水）。

**逾期卡**：计划日已过但没刷的卡，并入下次打开时的 `todayQueue`，且不改变计划中剩余的项；逾期卡排在当天新排卡之前。用户 day4 该刷没刷、day9 才打开，是常态而非异常。

### 5.6 题库规模与单用户可消化量（重要）

这两个数字相差一个数量级，必须分开对待：

| | 数量 |
|---|---|
| 题库总量（§2） | 1200-1600 题 |
| 一张新卡的复习次数 | 约 6 次 |
| 全库刷透所需复习次数 | **约 7200-9600 次** |
| 3 周 × 45 题/天的容量 | **945 次** |
| **单用户 3 周实际能刷透的新题** | **约 150-170 题** |

差 7.6 倍。**没有任何用户能刷完这个题库**——甚至选一个完整大类（200 题 × 6 = 1200 次）也超出 945。

这不是缺陷，是定位问题。题库规模的作用**不是让用户刷完，是让用户找得到他要的那块**。由此三条设计推论：

1. **排期只作用于用户选中的知识块**，不是全库。`schedule()` 的 `cards[]` 参数永远是选中子集，不是题库全集
2. **§5.4 的超载收窄是核心交互，不是异常兜底。** 它实际回答的是产品最有价值的那个问题——"从 1200 道里，我这三周该刷哪 157 道"。因此它的 UI 不能长得像错误提示，要长得像一个规划工具
3. **知识地图（§4.1）与超载收窄是一对。** 地图负责"你自己选哪块不熟"，收窄负责"选完之后按频度砍到刷得完"。两者合起来才兑现"哪块记不住就刷哪块"这个承诺

**因此 §5.4 的告警文案要改口径**：不是"你选多了，装不下"，而是"这三周你能刷透约 160 道，按面试频度我建议这些"。同一个算法，完全不同的产品语义。

### 5.7 维持模式（就绪日之后）

`readyByDate` 为空或已过期时走日常维持模式：

- 档位 `k` 存于 `card_state.phase_index`，新卡 `k = 0`
- 间隔表 `[1, 3, 7, 15, 30, 60, 120]` 天，到表尾后**停在 120 天不再增长**
- 得分比例 `≥ 1/2` → `k += 1`；`< 1/2` → `k = 0`
- `readyByDate` 从空变为有值时，按当前 `s` 走 §5.2 生成计划；`phase_index` 保留但不参与冲刺模式

**这不再只是兜底路径。** 改用就绪日之后，它承担了一个真实且高频的场景：用户准备好了，但面试还没来。求职过程持续 1-3 个月，这段"已就绪、等通知"的日子可能比冲刺期还长。维持模式的任务是让他**别在等待期把刚记住的东西忘掉**，每天只需要几分钟。

### 5.8 面试临时加密

用户真约到一场面试时（通常提前 2-5 天通知），输入面试日期与**这场面试相关的知识块**（例如投的是数据密集岗，勾 MySQL + Redis）。

- 对选中块里 `s` 最低的卡，在剩余 2-5 天内按 §5.2 重新铺一遍（`readyByDate` = 面试前一天）
- **不影响其他块的计划**——只重排选中块，其余照常
- 面试过后自动回到 §5.7 维持模式

> **v2 接线注记（2026-09-28，计划 6）**：cram 执行时将 `readyByDate` 置为面试前一天——这是 §5.5 条件 2「日期变更 → 全局重排」的**显式豁免**（只重排选中块，其余块计划逐字节不变）。效果：冲刺窗口内 mode=sprint、答错走 §5.5 重排；面试日一过 R<0 自动回落 §5.7，正是上一条「面试过后自动回到维持模式」的机制化实现。代价是覆盖常备用户的空就绪日（效果等价，UI 文案需提示「就绪日已过，已回到常备模式」）。

这条是就绪日模型的必要补充：就绪日解决"我什么时候准备好"，临时加密解决"这周四要面字节，临阵抱一下佛脚"。两者加起来才覆盖真实求职的完整时间结构。**它也是唯一需要用户填真实面试日期的地方，而此时用户确实知道那个日期。**

## 6. 刷题主循环

**一张卡两屏，全程点击，不需要出声，目标 15-20 秒。**

早期设计是三屏（题面 → 出声说 → 勾选"我刚才说到的"），已废弃：它与时间预算互斥，且自评勾选是一条激励对齐的作弊通道。推导见 §12 ④、§12 ③。

**① 题目 + 选项（同屏）**

顶部：知识块名、频度标签、今日进度（`12/45`）、常驻的"面试还剩 N 天"。
主体：题面 + 6-9 个选项（正确要点 3-6 条 + 干扰项 3 条，顺序随机，见 §4.3）。
提示语是"勾出所有属于这道题的要点"，**不显示正确条数**。

今日进度的分母 = 今天开始时 `todayQueue` 的长度（含逾期卡），**当天内不变**，存于 `daily_session`（§8.1）。答错重排到明天（§5.5），不往当天分母里追加，所以不会出现 `12/45 → 12/46` 这种自增。

**空勾选不允许提交。** 一条不勾 = 0 分 = 得分比例 `< 1/2` = 触发 §5.5 重新生成。在一个主打"碎片时间快速点击"的移动端产品上，误触提交是必然事件，而它的代价是整份计划被重排 + 弹出"计划已重排"。前端拦截空提交，或按"跳过本题"处理、不写 `review_log`。

不设"先在心里回忆"的停顿屏。这是一个明确取舍：停顿能保住主动回忆（间隔重复真正起效的动作），但每题多 3 秒、45 题多 2 分钟。取舍理由和它的风险见 §12 ④。

**② 即时判分 + 排期反馈**

- 得分 `4/5`，并标明**漏了几条、错勾了几条**
- 逐条染色：勾对（绿）、漏选（黄，附"68% 的人也漏了这条"）、错勾（红）
- 错勾的选项要显示**它实际属于哪道题**——这是本方案独有的信息，直接告诉用户"你把 A 和 B 搞混了"，比单纯说"你错了"有用得多
- **"下次 2 天后 · 面试前还会再过 2 遍"**，配一排圆点表示该卡在面试前的剩余复习节点，末尾红点为面试日
- `detail` / `followUps` / `sources` 默认折叠

第 ② 屏的排期反馈是刻意设计的：算法再聪明，用户感知不到就等于不存在。

### 6.1 不做口述模式

曾考虑把口述作为"模式二"（高掌握度卡解锁语音作答 + AI 判分），**已否决**。

理由不是工程量，是用户不要：口述费时间，而本产品的用户要的就是**短期、大量、快速刷题把知识点记住**。一个没人愿意用的模式，做出来只是增加维护面。

**这个否决顺带回答了 §12 ⑥（为什么不直接问 AI）。** 通用 AI 最强的恰恰是听你口述并批改——那是它的主场，正面打必输。但它做不了"整个题库按你的遗忘曲线排好、每天 15 分钟刷完、面试当天全在峰值"。砍掉口述等于主动退出跟 AI 重合的那块，守住它守不住的那块：**跨会话的排期状态 + 结构化题库**。

产品的价值主张因此收窄成一句话：**面试前有限的时间里，把该记的知识点按遗忘曲线刷到记住。** 不做理解辅导、不做模拟面试、不做口述训练。

代价见 §12 ④——迁移假设失去了后手，成为单点赌注。

**这屏的正确性依赖 §5.2 的计划持久化。** 圆点画的是已经落盘的计划，答对时它只会少一个，不会重画。早期的每次重算方案会让这排圆点每刷一次就变多——用户感知到的东西是错的，比感知不到更糟。答错触发重新生成（§5.5）时，UI 必须明说"计划已重排"，而不是默默换一排圆点。

## 7. 架构

**技术栈**：Next.js (App Router) + TypeScript + PostgreSQL。

选 Next 的实际理由是题目页面可 SSR 被搜索引擎收录——"AQS 是怎么实现独占锁的"这类长尾搜索是刷题产品最重要的免费获客渠道。认证用 GitHub OAuth（用户是程序员）+ 邮箱兜底。

**SEO 与付费墙的边界必须一次定死，不能含糊**：公开题目页 `q/[cardId]` 对**爬虫和用户渲染完全相同的内容**——题面 + `public` 要点（每题 1-2 条）+ 一个"完整 N 条要点在 App 内"的入口。**不做 cloaking**（给爬虫看全文、给用户看付费墙），那会被搜索引擎判罚。

代价说清楚：能被索引的只有题面和 1-2 条要点，长尾搜索的落地页内容比 JavaGuide 单薄——§12 ⑤ 已记录获客是未解问题，这里只是确保**不因为技术手段把它变得更糟**。收益是这批 `public` 要点一份内容三用：SEO 落地页、免费用户的跨块干扰项池（§4.3）、以及付费转化的展示面。

**内容进 Git，不进 CMS**：题卡源文件是仓库里的 Markdown/YAML。审核流程直接用 PR，版本历史和 diff 白送，省掉一整个编辑后台子系统。

**内容同步是独立 job，不挂在应用部署上**。早期写的是"构建时同步进库"——数据量上没问题（1400 行、亚秒级），但它把内容发布和应用部署耦在一条流水线：改一个错别字要重新部署整个应用，而内容轨要持续编辑 4-9 个月；更糟的是**两者的回滚语义不同**，应用回滚回滚不掉已写进 DB 的内容。改为 `content/**` 变更触发独立 job 直连 DB 做 upsert，应用运行时从 DB 读内容而非从构建产物读（否则 DB 与 bundle 会漂移，`keyPointsTotal` 对不上）。

**内容 id 的稳定性必须有守卫，且要在写第一道题之前就位**。`id` 一动，`review_log.distractorIds`、`excludeAsDistractorFor`、`card_state` 全部变成悬空引用——而 §9.1 那 25-60 小时的人工互斥登记就挂在这些 id 上，**一次目录重构就能静默报废一部分，没有任何东西会报错**。四条：

- **id 由脚手架生成，不由人手写**：`pnpm content:new <block>` 铸一个 ULID 写进 frontmatter。文件名与 id 解耦，文件可随意改名
- **CI 跨提交守卫**：上一次 `main` 的全量 id 集合作为 `content/.ids.lock` 提交；id 消失或改变即构建失败，除非同 PR 显式写了 `movedFrom` / `retiredAt`
- **校验必须是全库一次性，不是 per-card**：`KeyPoint.id` 块内唯一（两个作者在同块不同文件各加一条 `kp-7`，Git 不会冲突，只有全库校验能发现）、外键指向存在的 id、每块干扰项池容量达阈值
- **删除用 tombstone**：`retiredAt` 标记，不真删——`review_log` append-only 且引用 `cardId`

```
content/                      # Git 管理的内容源（非代码）
  concurrency/
    aqs-and-locks/
      001-aqs-exclusive-lock.md

src/
  lib/scheduler/              # ★ 纯函数、零依赖、可完整单测
    plan.ts                   #   计划生成：阶梯 + 错峰 + 末端窗口 (§5.2)
    capacity.ts               #   容量装箱 + 前缀和超载检测 (§5.3, §5.4)
    regenerate.ts             #   重生成条件与终止状态 (§5.5, §5.7)
    schedule.ts               #   主入口
    types.ts
  lib/content/
    parse.ts                  #   源文件 → Card
    validate.ts               #   schema 校验
  lib/mastery/                # 掌握度计算 (§4.4)，纯函数
  lib/options/                # ★ 干扰项分层抽取 + 选项集预生成 (§4.3)，纯函数
  lib/entitlement/            # ★ 权限：用户解锁了哪些块 (§10.1)
  server/
    sync/                     #   离线队列回传、幂等、localDate 判定 (§8.3)
    queue/                    #   今日队列 + 预生成选项集下发
  app/
    (drill)/                  # 刷题主循环
    map/                      # 知识地图
    q/[cardId]/               # ★ 公开题目页（SEO），只渲染 public 要点

                              #   独立于生产应用，本地运行，直接读写 content/
```

依赖严格单向：`app → server → lib`。`lib/scheduler`、`lib/options`、`lib/mastery` 均为纯函数、零依赖。

**三个模块是第 4 轮评审补的，早期架构图里没有它们的位置**：

- **`lib/options`**：干扰项抽取此前完全没有算法归属，而它同时涉及分层比例、互斥过滤、付费墙边界和可复现随机源。必须是纯函数才能测——随机源由参数注入（`seed`），不读全局。
- **`lib/entitlement`**：权限逻辑此前无归属层。它决定 `schedule()` 的 `cards[]` 里能放哪些块、以及 `lib/options` 的跨块层从哪个池抽。放在 `lib` 而非 `server`，因为筛选逻辑要被单测覆盖（§11）。
- **`tools/review`**：§9.1 要求的审核工具（12 万次互斥检查的机器召回 + 人工确认界面）此前只在"做"清单里，架构里不存在。它**独立于生产应用**：本地运行、直接读写 `content/` 目录、产出 PR，不部署、不接触生产库。

## 8. 数据流与错误处理

### 8.1 存储结构

`review_log`（append-only，永不更新）——每条记录必须自带当时的上下文，否则日志无法解释：

| 字段 | 为什么必须存 |
|---|---|
| `cardId`, `userId`, `reviewedAt` | — |
| `correctChecked`, `wrongChecked` | 勾对数、勾错数。两个都要存——勾错数据告诉我们用户把哪些知识点搞混了（§4.3 副产品 2） |
| `distractorIds` | 本次实际抽中的干扰项。干扰项是动态抽的，不存就无法复现这一次到底考了什么 |
| `keyPointsTotal` | **复习当时的要点总数**。内容在 Git 里会改，某张卡要点从 4 条变 6 条后，历史记录里"勾了 3 条"的含义会从 `0.75` 静默变成 `0.5` |
| `predictedCount` | §4.3 的元认知偏差 |
| `readyByDateAtReview`, `dailyCapacityAtReview` | 排期的输入，不存就无法解释当时为什么排在那天 |
| `submissionId` | 客户端生成的 ULID / UUIDv7，**唯一索引**。离线重试的幂等键（§8.3） |
| `localDate` | 该次复习归属的本地日历日，**由服务端判定**（§8.3） |
| `distractorIds` | 本次抽中的干扰项要点 id，用于复现该次到底考了什么 |
| `algoVersion` | §5 必然迭代，不记版本就分不清"算法变了"和"数据坏了" |

`card_state`：`phase`、`s`、`plan[]`（已生成的计划）、`phaseIndex`（§5.7 用）、`reviewCount`、`planGeneratedAt`、**`algoVersion`**。

`algoVersion` 必须存在 `card_state` 上而不只是 `review_log` 上：§8.2 已承认排期不可重放，所以**算法一改，存量用户的 `plan[]` 就是旧形状且无法重建**。上线三周后修一个装箱 bug 时，窗口里的用户怎么办？新代码消费旧计划（语义可能已变）还是重新生成（圆点全部重画，且这不是 §5.5 的任何触发条件）？有了这个字段，新算法只对**新生成的计划**生效，旧计划跑完当前窗口（≤ 3 周）自然退场。

`daily_session(userId, localDate, queueSize, startedAt)`：§6 规定"今日进度的分母 = 今天开始时 `todayQueue` 的长度，当天内不变"，而这是 per-(用户, 本地日) 的状态，`card_state`（per-card）和 `review_log`（per-review）都放不下。不单独存，刷新页面或换设备分母就变了。

**刷一张卡**：
```
提交勾选 → 写 review_log → 更新 card_state（消费计划中的当前项）
         → 仅在 §5.5 三种条件下才重新生成计划
         → 返回 { 新掌握度, 下次复习日, 面试前剩余遍数 }
```

注意这里**不是**每次提交都重跑 `schedule()`——那正是造成复习次数发散的原因（§5.2）。

### 8.2 重放能力的边界

`review_log` 足以**重算掌握度 `s`**，因为每条记录自带 `keyPointsTotal`。

`review_log` **不足以重放排期**。排期还依赖 `readyByDate` 与 `dailyCapacity` 的**变更历史**——用户在第 5 天把面试从 10-06 改到 10-20，用当前值重放得到的历史与真实发生过的完全不同。要支持排期重放，得再加一条 `user_settings_log` 事件流。

**第一版只承诺前者**，不做 `user_settings_log`。这意味着：拿历史日志回测新算法（可以做），`card_state` 写坏后完整恢复排期（做不到，只能按当前设置重新生成计划）。早期文档写的"所有排期状态都能从日志重放"是一张空头支票，这里明确兑现范围。

### 8.3 离线

**核心规则：客户端只消费计划，永不生成计划。服务端是 `plan[]` 的唯一写者。**

早期写法是"排期引擎是纯函数，客户端可同构运行，断网也能刷完当天的量"。那句话把 `plan[]` 变成了**多写者字段**——而 §8.2 已经声明它**不可重建**（`review_log` 只够重算 `s`，重算不出计划）。这是全文唯一一处"数据坏了没有恢复路径"。

失败序列：用户断网刷 40 张卡，第 7 张答错触发 §5.5 重排 → 客户端跑 `schedule()` 写本地 `plan[]`；中午他在公司电脑上也刷过、也重排过。联网回传时服务端无论**接受客户端结果**（静默覆盖另一台设备的计划，且 §6 要求的"计划已重排"提示不会弹）还是**服务端重放**（要求两端逐字节同结果，且要按正确顺序重放多次重排，因为 §5.3 的装箱依赖当时的占用状态），坏掉之后都没有恢复手段。

**修法（几乎零成本）**：

- 断网时客户端**只读已落盘的计划**，答错不重排，只把提交入队，UI 显示"计划将在联网后更新"
- 联网后由服务端按队列顺序逐条重放 §5.5

这不违反"断网也能刷完当天的量"——**当天的量本来就来自已落盘的计划**；且 §5.5 规定答错是"从明天起"重排，当天本就不会再见到这张卡。

同构运行仍然有用，但用在 §11 的一致性测试上（同一输入在 Node 与 headless 浏览器跑出同一份 JSON），**不用在生产写路径上**。

**三条必须配套的机制**：

- **幂等键**：回传队列每条带客户端生成的 `submissionId`（ULID / UUIDv7），`review_log` 上建唯一索引。早期文档写 `review_log` append-only"天然无冲突"——**append-only 消除的是写冲突，不是重复提交**，两件事被混为一谈。超时重试 = 重复日志 = "最近 3 次"里塞进两条同一次提交 = `s` 错 = 起始档错 = 计划错。
- **顺序**：`s` 是 `3:2:1` 加权，顺序敏感。服务端按 `reviewedAt` 排序后重算；对异常时钟（早于上一条、或晚于服务端 now 超过阈值）做钳制并记录。
- **日界唯一判定方**：`localDate` **只由服务端算**，用用户设置里的 IANA 时区 + **锁定版本的 tz 库**（不用 `Intl`——JS 引擎的时区数据来自各自打包的 ICU 快照，版本会漂移）。客户端离线期间可用自己的判断临时排队，同步时由服务端重新归属。

**多设备冲突**：`review_log` append-only + `submissionId` 幂等；`card_state.s` 由服务端按序重算；`plan[]` 只有服务端写，不存在冲突。

`reviewedAt` 记 UTC 瞬时值仅用于排序，"属于哪一天"由上面的 `localDate` 规则单独判定，两者不混用。

**内容校验失败**：CI 上跑 `lib/content/validate`，缺 `sources` 的卡直接构建失败，坏内容进不了生产。

**最少要点数按 `cardType` 分派，不是统一的 3 条**：

| `cardType` | 最少要点 |
|---|---|
| `enumeration` / `comparison` | 3 |
| `sequence` | 4，且每条要点自带 `order` |
| `judgment` | 2（结论 + 支撑） |
| `atomic` | 1 |

早期写的是统一"少于 3 条构建失败"。那条规则会**自动挡掉 17.5% 的真实高频题**——单点事实型（9.9%，一句话就答完）和情景推演型（7.6%，答案是"会/不会"加一条推理）根本凑不满 3 条，作者要么注水凑数，要么换一道题写。这是 §4.3 那三条漂移力里最硬的一条。

## 9. 内容生产管线

题目来源与答案来源是两回事。

**① 题目来源：专家标注冷启动 + 用户回流校准**

> 原方案是"从牛客 / 小红书采集面经，题目是客观事实不受版权保护"。**第 3 轮评审推翻了这个论证——它答错了题。** 约束根本不在著作权：平台用户协议是**合同**约束，与内容是否受版权保护无关；小红书 robots.txt 对 `User-agent: *` 是 `Disallow: /` 加登录墙，构成"技术管理措施"；而 2025-10-15 施行的新《反不正当竞争法》第十三条禁止"以……避开或者破坏技术管理措施等不正当方式，获取、使用其他经营者合法持有的数据"，罚则 10-100 万、情节严重 100-500 万。**收费同时补齐了"经营者"主体资格与"竞争关系"两个要件**（牛客、面试鸭卖的是同一批用户），风险等级因此上升。此处为风险判断而非法律意见，商业化前应由执业律师复核。

**方案：题目从知识体系反推，`frequency` 由专家标注。**

对着官方文档、源码、RFC 梳理出每个知识块该考什么，由懂行的人按经验把 `frequency` 标为高/中/低。不采集任何第三方平台数据。

**不做用户回流采集**（曾考虑让用户面试后回来勾选"这几道我被问到了"，以校准 `frequency` 并自动产出验收数据）。否决理由：那个机制服务的是产品的数据需求，不是用户的使用需求。本产品的主张是"短期大量快速刷题记住知识点"（§6.1），用户来这里不是为了贡献数据。用"顺带提升留存"来论证它也不成立——留存不是本产品追求的目标（§12 ⑤ 已确认这是正常的一次性工具形态）。

**因此接受两个代价，明确记录**：

1. **`frequency` 永远是专家判断，没有自我校准机制。** 而它驱动着 §5.4 的超载收窄——现在的核心交互（§5.6）。**标注质量直接决定产品质量**，这是内容审核之外第二项吃专业判断的工作，不能外包
2. **§11 的命中率验收拿不到自动数据**，须靠人工访谈那 5-10 个种子用户。第一版规模下够用，但这条路不随用户增长而变省

`frequency` 直接决定超载时先砍谁（§5.4）、以及末次复习谁最贴近就绪日（§5.2 ④）。

**② 答案对着一手资料生成**，不依赖模型记忆。输入：官方文档对应章节、JDK 源码片段、RFC 原文。输出：3-6 条要点，每条标出处和适用版本。**无出处的断言一律剔除**。这是把"AI 幻觉"约束成"AI 摘录"。

**③ 人工审核走 PR**，清单六条：
1. 每条要点能否在 `sources` 里逐条验证
2. 版本适用性是否标对
3. 要点粒度是否符合 **KP1-KP6**（§9.3）——原来只写"是否齐整"，没有可判据
4. 题面是否是面试官的真实问法
5. **`cardType` 标注是否正确**——标错会让出题形式和计分方式一起错（§4.3）
6. **干扰项互斥性**（§4.3）：本题的要点对同知识块的其他题是否也成立？若成立须标 `excludeAsDistractorFor`。这是选择题方案唯一新增的审核负担，但它是块内 N² 量级的检查——**审核工具必须自动把同块要点两两列出来给人看**，纯靠人脑记不住 18 张卡之间的交叉关系

**④ 上线后的质量闭环**：

| 信号 | 说明什么 | 动作 |
|---|---|---|
| 某要点 80% 用户漏 | 要点太偏或太细 | 标记复核 |
| 某题人人秒过 | 太简单 | 降频或删除 |
| 用户点"报错" | 可能确有错误 | 自动开 issue |

### 9.1 成本与压缩（本项目最大的一笔投入）

**审核是瓶颈，不是生成。** 按朴素做法，1200-1600 题 × 10 分钟/题 = **200-270 小时**，且必须是懂行的人做，外包不了。这是全项目的主要成本，也是唯一真正的进度约束——工程轨（§5-§8）的工作量在它面前可以忽略。

> **本节经第 3 轮评审重写。** 原来列了四条压缩手段、结论 70-80 小时——其中一条是幻想、一条与 §4.3 自相矛盾，且漏算了两笔开销。修正后的结论是 **145-220 小时**。原估算是错的，以此为前提做过的范围决策（§2 的 8 大类）应当据此重新审视。

**压缩手段，逐条核实后只剩两条半**：

| 手段 | 判定 |
|---|---|
| **按知识块批量审** | ✅ **真实，约省 25-30%**。跨块切换要换一整套一手资料、术语和版本坐标系，同块 15-25 题共享这些。但省的只是上下文加载，不是逐条核对源码那段——若 10 分钟里 3 分钟是上下文、7 分钟是验证，上限就是 30%。反向力：同块连审 20 道题极其单调，第 15 道后判断质量下降，而这正是最吃判断力的活 |
| **报错闭环兜底** | ✅ **真实**。前置审核的目标是"没有系统性错误"，不是"零错误"（§9 ④） |
| ~~**要点级复用**~~ | ❌ **删除——与 §4.3 是同一个事实的两面**。"同一条要点在多题中复现"翻译成 §4.3 的语言就是"A 题的要点对 B 题也成立"，**每一次省下审核时间的复用，恰好是一条必须登记的 `excludeAsDistractorFor`**。省下的时间要用互斥登记还回去，而且每登记一条，干扰项池就少一个可用项。复用率越高净收益越负。原文档在一处记成收益、另一处记成成本，等于凭空多算了一次 |
| ~~**双模型交叉预审**~~ | ❌ **删除——"独立"这个前提被实证推翻，而且它是逆向筛选**。见下 |

#### 为什么双模型交叉预审必须删掉

原设计是"两个模型独立生成，**只有不一致处进人工队列**"，理由写的是"两模型独立出错且错到一处的概率很低"。

[ICML 2025 *Correlated Errors in Large Language Models*](https://arxiv.org/abs/2506.07962)（Kim, Garg, Peng & Garg，350+ 模型实测）直接否定了这个前提：**两个模型都答错时，错到同一个答案的概率在两个数据集上分别是 42.3% 和 60%**，而随机基线是 0.127 和 0.333——实测是独立假设的 1.8 到 3.3 倍。论文摘要原文：*"larger and more accurate models have highly correlated errors, even with distinct architectures and providers."* **换厂商、换架构都不解决，而且模型越强越相关。**

比"无效"更糟的是它的方向：**该设计把"两模型一致"当成免检通道，而一致恰恰是共有错误认知的藏身处**。中文八股是这个问题最密集的领域——大量以讹传讹的结论在各家模型的训练语料里是同一批博客。这套流程会系统性地把最危险的那类错误筛出人工队列。

**替代方案**（保留多模型，但反转筛选逻辑）：

1. **不一致 → 必进人工**。这仍是高精度的错误信号，该用
2. **一致 → 按比例随机抽检**（建议 10-15%）。一致不是正确的证据，只是"没有独立证据"
3. **真正的防线是一手资料，不是模型投票**：要点的 `source` 必须指向**英文一手资料**（官方文档、源码、RFC），**中文技术博客不得作为 source**。这才是对"中文圈流传的错误结论"的有效防御——错误认知集中在中文二手资料里，而一手资料里没有

#### 修正后的估算

| 项 | 工时 |
|---|---|
| 逐题审核 1400 题 × 7-12 分钟（批量审后） | **165-280 小时** → 取中位 **145-220 小时** |
| §4.3 块内互斥检查（机器召回 + 人工确认） | **25-60 小时** |
| 审核工具开发 | 单列，属工程轨 |

朴素基线 10 分钟/题本身偏低：§9 ③ 要求"每条要点在 `sources` 里**逐条**验证"，而逐条验证一条 JDK 源码级要点的真实动作是定位类和方法 → 确认该行为在声明版本里成立 → 确认它至今未变。按 2-3 分钟/要点 × 4.5 条，光验证就 9-13 分钟。

**这是全项目的关键路径，也是唯一的真约束。**

**必须先建工具，再开始审**：`excludeAsDistractorFor` 的互斥检查是块内 N² 量级——20 题的块有约 190 对要点组合，1200 题全库人脑记不住任何跨题关系。审核工具必须自动把同块要点两两列出、标出疑似互斥对给人确认。**这个工具的开发应排在内容生产之前**，否则会审到一半推倒重来。

### 9.2 版本衰减与增量维护

八股内容会过期。`appliesTo` 字段的存在本身就是证据——"偏向锁默认开启"在 JDK 15 之后就是错的。JDK 每半年一个版本，Spring / Redis / MySQL 各有节奏，维护成本不会停（§12 ⑤）。

**但它不该线性累积。** 关键在于内容按稳定性天然分两类：

| 类型 | 占比（估） | 例子 | 维护 |
|---|---|---|---|
| **稳定内容** | 约 85% | TCP 三次握手、B+ 树结构、进程与线程的区别、CAP | 几乎不变，一次审核长期有效 |
| **版本敏感内容** | 约 15% | 偏向锁默认值、G1 参数、Redis 新数据结构、Spring 默认行为 | 跟版本走，需要复核 |

**增量复核靠 `KeyPoint.appliesTo` + `verifiedAt` 两个字段驱动**（这是 §4.2 把它们下沉到要点级的第二个理由）：

1. 订阅 JDK / Spring / Redis / MySQL 的 release notes
2. 新版本发布时，按 `appliesTo` 圈出**可能受影响的要点**——不是受影响的卡，是要点。粒度差 3-6 倍
3. 只复核被圈中的那些，复核后更新 `verifiedAt`
4. `verifiedAt` 超过 18 个月未更新的要点进入抽检队列，防止"没人报错就假设还对"

**因此维护成本随时间下降而非累积**：稳定内容审过一次就不再进队列；版本敏感内容虽然反复进，但基数只有 15%，且每次只复核受影响的要点而非整张卡。粗估年维护量是初始审核的 10-15%，即每年 20-35 小时。

**用户报错闭环（§9 ④）是这套机制的兜底**，不是替代——报错只能发现已经错了的，圈定复核能在用户撞上之前发现。

### 9.3 要点粒度标准 KP1-KP6

§9 ③ 的审核清单原来只写"要点粒度是否齐整"，没有定义什么叫齐整——而粒度直接决定 §4.4 的得分分母和 §5.5 的重排阈值（2 倍误差）。六条判据，审核时能照着判：

- **KP1 · 独立可说出**——一条要点是候选人能用一句话（15-25 字）说出、且说出后面试官会点头的最小单位。判据：**"他只说了这一条，面试官会不会认为答到了点上？"**
- **KP2 · 单一信息核**——只含一个可被独立追问的事实。判据：**能不能对这条要点提出两个互不相干的追问？能，就该拆成两条。**
- **KP3 · 同卡同类型**——一张卡的要点全是结构、或全是流程、或全是权衡，不混。混了说明这张卡问了两个问题。（这是 `cardType` 的审核形态）
- **KP4 · 等价可失**——漏掉任意一条的后果大致相当。判据：按"面试官会不会因为漏这条扣分"排序，若首尾落差明显（一条致命、一条无所谓），最后那条降为 `detail`。**六条里唯一有排期后果的**，它直接保护 §5.5 的 1/2 阈值。
- **KP5 · 不含承载词**——不得出现「等」「多种」「一系列」「若干」「之类」「诸如」。它们把多个事实折叠进一个词，是"把不可枚举硬塞进枚举"的语法标志。
- **KP6 · 与题面同粒度**——抽象层级与 `question` 一致，既不下沉到实现细节，也不上浮到定义。

**正例**（AQS 那道题按标准重写，全流程型、每条一个信息核）：

```
1. state 是 volatile int，表示同步状态，独占锁下 0 表示空闲
2. 获取锁是对 state 做 CAS，成功即持有
3. CAS 失败则把线程包装成 Node，入等待队列尾部
4. 排队线程用 LockSupport.park 阻塞，不自旋空转
5. 释放时改 state，再 unpark 后继节点
```

CLH 血统、队列为什么双向、`waitStatus` 取值下沉到 `detail`；"为什么是双向不是单向"提升为 `followUp`——那本来就是面试官的真实追问。

**审核应直接打回的写法**：

| 反例 | 违反 |
|---|---|
| `AQS 是 AbstractQueuedSynchronizer 的缩写，是 JUC 的基础框架` | KP1——背景不是得分点，面试官不会点头 |
| `AQS 支持独占和共享两种模式，ReentrantLock、Semaphore 等都基于它` | KP5 + KP6——「等」折叠了未知数量的事实，且层级高于题面 |
| `Node 的 waitStatus 有 CANCELLED(1)、SIGNAL(-1)…四个值` | KP6——下沉到实现细节，该进 `detail` |
| `AQS 用 CLH 变体的双向 FIFO 队列管理等待线程，入队用 CAS 保证安全` | KP2——三个信息核，能提出三个不相干的追问 |

**三条机器校验规则**（进 `lib/content/validate.ts`，CI 跑，成本为零）：

1. 要点长度上界 **30 个汉字**——超过几乎必然违反 KP2。是 KP2 的廉价代理，不替代人工判断
2. 承载词黑名单：`等|多种|一系列|若干|之类|诸如|各种` 命中即失败
3. 块名黑名单：`基础|进阶|高级|其他|常见问题|高频` 命中即失败

这三条跑在约 6000 条要点上，覆盖的正是 §9.1 自己承认的那个薄弱点——"同块连审 20 道题极其单调，第 15 道后判断质量下降"。

> **⚠️ 必须在第一周启动、不占工程人力但卡日历**：境内收款的前置资质链条——营业执照 → ICP 备案 → 公安备案 → 微信支付/支付宝商户号——需要 **4-8 周日历时间**，且步骤间严格串行。它不是一个工程 bullet，是一条与全部开发并行的独立轨道。放到开发后期才启动，会让写完的产品干等着上不了线。

**明确不做**：社区贡献 / UGC、编辑后台、推送提醒、排行榜 / 打卡分享。

### 10.1 免费与付费边界

**原则：排期免费，题量付费。**

| | 免费 | 付费 |
|---|---|---|
| 可刷题量 | **用户任选 2 个知识块**，约 30-50 题 | 全量 1200-1600 道 |
| 知识地图 | ✓ 完整可见（含未解锁块的题数） | ✓ |
| 排期引擎（§5 全部） | ✓ 完整 | ✓ |
| 维持模式、临时加密 | ✓ | ✓ |
| 多设备同步 | ✓ | ✓ |

**免费层是"完整的 2 个块"，不是"分散的 300 道高频"。** 后者是早期设计，第 3 轮评审指出它与文档自身两处硬冲突：

- 300 道摊到 64-96 个块 = **每块 3-5 题**，直接违反 §2 自己的判词"块不完善，核心动作就不成立"。用户点进任何一块都是残缺的，恰好演示了产品**不能**做什么
- 300 道超过 §5.6 算出的单用户 157 道容量上限，免费用户第一天就撞上超载收窄——最糟的第一印象

**"任选 2 个块"让用户用自己最在意的那块来判断产品**，说服力最强；30-50 题也远低于容量上限，能完整走完一个排期周期（含末端窗口和维持模式），真正体验到机制而不只是看到题。

锁题量不锁功能，三个理由：

1. **排期是产品体验的核心，锁掉它用户感受不到任何价值**，试用就变成走过场
2. 题库价值本来就随题量线性增长（§5.6：题库的作用是让用户"找得到"），按量收费最自然
3. 免费层要证明的不是"内容够多"——那一仗打不赢 JavaGuide 和小林 coding，它们免费且体系完整。免费层要证明的是**"按遗忘曲线刷题这套机制对我有用"**，而这恰恰需要一个完整的块才演示得出来

**转化点设计**：知识地图上，未解锁的块显示真实题数但不可进入——"MySQL 索引 · 23 题"。用户刷完免费的 2 个块、感受到机制有用之后，地图上那些数字自然构成升级动机。**产品内不应有第二处付费提示，尤其不要在刷题过程中打断。**

**定价**：一次性买断，对标面试鸭永久会员（129 元起）。选买断而非订阅，是因为用户使用周期与求职周期一致——集中用几周，然后两三年后下次找工作再回来。订阅制在这种使用形态下只会逼用户在拿到 offer 当天退订，徒增摩擦。具体价格上线前再定。

> **v3 修订（2026-10-02，付费模型）**：本条「一次性买断」废除，改为 **¥29 / 30 天通行证**（不自动续费，可叠加续期）。原反对订阅的理由是「逼用户在拿到 offer 当天退订，徒增摩擦」——该理由针对的是**自动续费**；单次期限通行证没有退订这个动作，摩擦不成立，而本条自己指出的使用形态（「集中用几周」）恰恰支持期限定价。
>
> **同时新增宽限语义**：到期不立即切断，冲刺模式跑到在期排期最后一天、常备模式 +14 天。因为本产品的排期是跨周铺开的，「到期即断」会让用户看到自己买过的排期从中间消失。宽限期内只跑**已有计划**的卡、不新排，且 AI 配额仍按付费档——宽限是「让没刷完的刷完」，不是「再送两周」。
>
> 免费层仍为 2 个块。到期结算必须把勾选收敛到 ≤2：付费期勾选通常几十块，直接当免费层会触发 `makeFreeEntitlement` 的 ≤2 抛错，令首页/地图/学习页全 500（比「掉到 0 块」更糟）。存量付费用户在迁移时统一转为「执行时刻 + 30 天」（2026-10-02 用户拍板，不做 grandfather）。

**永久不做**：口述 / 语音作答模式（§6.1）。这不是"以后再说"，是方向性排除——它与产品的核心主张（短期大量快速刷题）冲突，且是通用 AI 的主场。

**两条并行轨道**，且**内容轨是关键路径**：
- **工程轨**：§5-§8，可用少量样例题（10-20 道）全程开发，不阻塞于内容
- **内容轨**：§9，1200-1600 题的采集、生成、审核，**145-220 小时**，外加互斥检查 25-60 小时，是日历时间上的绝对长项

实现计划必须把两轨分开排期，只在验收（§11）处汇合。工程轨做完会长时间空等内容轨——这是既定事实，不是排期失误，**实现计划不应为了"让工程有事做"而扩大工程范围**。

**内容轨内部的顺序不能错**：审核工具（§9.1）→ 单块试点（选一个块走完全流程，校准单题实际耗时）→ 按块批量生产。跳过试点直接批量，会在 1200 题的规模上放大流程缺陷。

## 11. 验收标准

1. **端到端跑通**：设就绪日 → 在地图上选若干知识块 → 超载收窄给出可行方案 → 刷完该方案的排期 → 所有题在就绪日前收口
2. **排期正确性**：`lib/scheduler` 单测全绿。§5.1 的五条不变量 I1–I5 各自成组，外加这些边界：

   | 边界 | 期望 |
   |---|---|
   | `R = 0 / 1 / 2 / 3` | 不崩、不空队列、末次落在 `E` |
   | `R < 0`（就绪日已过） | 走 §5.7 退化路径并提示更新 |
   | 用户选中 1200 题 / 3 周 / 容量 45 | 前缀和判据告警，收窄建议落在约 157 题 |
   | 用户只选 1 个块（20 题） | 不告警，正常排满窗口 |
   | 收窄建议执行后 | 重跑判据确认真的可行 |
   | 一张卡连续通过到面试 | 复习次数 = 计划长度，**不发散** |
   | 答错 | 重排从明天起，当天不再出现同一张卡 |
   | 逾期 5 天后打开 | 逾期卡并入队首，剩余计划不变 |
   | 无就绪日 / 就绪日已过 | §5.7 维持模式档位进退正确，到 120 天封顶 |
   | §5.8 临时加密 | 其余块 `plan[]` 逐字节不变，**且**重排后每天总负载（含 `reservedLoad`）仍 ≤ 容量 |
   | 加块 | 已有卡计划逐字节不变；新卡进队列；撞容量时告警不静默 |
   | 减块 | 该块的卡 `phase = paused`，不进 `todayQueue`，`plan[]` 保留 |
   | 加→减→加 往返 | 计划与只加一次的结果一致 |

3. **§5 以外的模块也必须有测试**——早期文档只列了 scheduler 的单测，而下面这些恰恰是最容易出错的部分：

   | 模块 | 必测 |
   |---|---|
   | `lib/options`（§4.3） | 选项总数恒为 9；分层比例正确；互斥项永不被抽中；同一 `seed` 输出可复现；池不足时的降级行为。**每种 `cardType` 各一组**；`sequence` 型必须断言选项**未被打乱** |
   | `lib/content/validate`（§9.3） | 三条正则：要点 ≤ 30 汉字、承载词黑名单、块名黑名单；`minKeyPoints` 按 `cardType` 分派 |
   | `lib/mastery`（§4.4） | 四种 `cardType` 的得分公式各自正确，且一律归一化到 `[0,1]` |
   | `lib/entitlement`（§10.1） | 免费用户的跨块干扰项只来自 `public` 要点池；未解锁块的要点不出现在下发语料里 |
   | `server/sync`（§8.3） | 重复 `submissionId` 幂等；乱序回传按 `reviewedAt` 重算 `s` 正确；异常时钟被钳制；离线跨日界的 `localDate` 由服务端判定 |
   | 同构一致性 | 同一输入在 Node 与 headless 浏览器跑出逐字节相同的 JSON |
   | DST 切换日 / 跨时区 | 日差按日历天计算，不偏移 |

4. **内容质量**：全部 1200-1600 题通过 schema 校验 + 人工审核签字；`excludeAsDistractorFor` 的块内互斥检查全覆盖（§9.1）
5. **产品有效性**：找 5-10 个真要面试的程序员用两周，面试后问**两个**问题：
   - **命中率**："你被问到的题里，有多少在这刷到过？"（测选题准不准）
   - **迁移率**："刷到过的那些题，你当场说得出来吗？"（测 §12 ④ 的再认→回忆假设）**必须按 `cardType` 分组统计**——不分组的话这个指标无法证伪（§12 ④）

阈值：**命中率 ≥ 50%**。全类覆盖后这个数才有意义——早期版本只做并发一个大类时，并发在一场面试里只占 0-3 道题，即使 150 道全命中，覆盖率上限也就 10-20%，50% 在数学上不可达。

**但覆盖面对齐还不够，题型面也要对齐。** 第 5 轮指出这是同一类错误的第二个维度：如果题库 80% 是列举题而真实面试 66% 不是，那么即使选题的**主题**完全命中，**题型**不匹配的那部分也没有对应的卡，50% 阈值在数学上仍然吃紧。§4.3 的题型配额（列举 ≤ 45%）是这条阈值能成立的前提。

**但必须按"用户实际刷过的块"归因**，不能按全库算。用户只刷了 MySQL 和网络，被问到 Redis 却没答上来，那不是选题失败，是他自己没选那块。统计口径：
```
命中率 = 被问到且属于用户已刷块的题数 / 被问到且属于用户已刷块的题数 + 漏掉的
```
另外单独记一个**块选择准确率**：用户选的块，和他实际被问到的块，重合多少。这测的是知识地图引导得好不好——如果用户总是选错块，问题在地图不在题库。

**两问必须分开统计**。只问命中率会漏掉本产品最大的未验证假设：用户可能"刷得挺好但面试说不出来"，那是形态问题不是选题问题，修法完全不同。

命中率低 → 选题跑偏（修 §9 的题目来源）。块选择准确率低 → 知识地图引导有问题。迁移率低 → 按 §12 ④ 的三条框架内加固路径处理。

## 12. 风险

> 第 2 轮评审重排了本节。原 ① 的**诊断**是错的，原 ③ 被**低估**，并新增 ④⑤⑥。详见 `reviews/round2-product-value.md`。

**④ 再认能否迁移成回忆**（原"时间预算互斥"已解决，替换为改版后的新赌注）

原问题：口述一个 3-6 要点的答案要 30-60 秒，而单卡预算是 15-25 秒。按设计出声则每天 45-70 分钟（承诺的 3-4 倍）；不出声则勾选退化成"这条我知道吗"，正是 §3 要消灭的偏差。两条路都通向失效。

**解法：改为多选题 + 客观判分**（§6），不再要求出声。时间预算和判分客观性同时解决。

**代价，也是本产品现在最大的未验证假设**：选择题练的是**再认**，面试要的是**回忆**。记忆研究里这两者差别明确，再认显著更容易。

支持这个赌注的理由有两条：
1. 我们的选项**不是编造的干扰项，就是答案要点本身**。用户反复接触的是一道题的完整要点结构，这种结构性曝光向口述的迁移，强于普通选择题。
2. 更重要的是比较基准：理想的口述形态**从来不会发生**（时间预算装不下），而实际会发生的那个自评翻卡**同样是再认，还是用户自己打分的再认**。所以正确的对比不是"选择题 vs 理想口述"，而是"客观判分的再认 vs 虚高自评的再认"——后者严格更差。

**证伪方式**（并入 §11）：验收访谈时必须分开问两件事——"被问到的题有多少在这刷到过"和"刷到过的题里，你当场说得出来吗"。第二个问题才测这个假设。

> **⚠️ 第 5 轮发现这个赌注原本无法被证伪，必须靠题型配额才能真正检验。**
>
> 本赌注在**列举型**题上最可能成立（结构就是一个清单，背清单确实能迁移成说清单），在**因果链/权衡型**上最不可能成立（结构是一个顺序或一组条件，而 9 个复选框承载不了）。
>
> 而 §4.3 记录的三条漂移力会把题库推向 70-85% 列举题。于是：**题库向列举题漂移 → 验收访谈问到的多是列举题 → 迁移率数字好看 → 本赌注被"验证"。** 内容漂移方向与赌注的偏向是同一个，所以 §11 会确认 §12 ④，**无论它是不是真的**。这是最坏的一种失败：不会被证伪。
>
> **因此 §4.3 的题型配额不是内容质量问题，是验收有效性问题。** 只有当题库的题型分布接近真实分布（列举 ≤ 45%）时，迁移率这个指标才真正在测东西。验收时**必须按 `cardType` 分组统计迁移率**——如果列举型迁移率高而 `sequence` / `judgment` 型低，那才是这个赌注的真实答案。

**这是一个单点赌注，没有后手。** §6.1 已否决口述模式，所以不存在"赌输了就上模式二"的退路。这是有意识的选择：口述费时间、没人愿意用，且是通用 AI 的主场。

**迁移率偏低时的补救路径**（全部在选择题框架内，不引入口述、不增加单卡耗时）：

1. **提高干扰项相似度**——随掌握度上升，从"同知识块"缩窄到"同一道题的相邻概念"抽干扰项。辨别越难，越接近真正的理解
2. **增加干扰项数量**——`s` 高的卡从 8 选 5 升到 12 选 5。选项多了，扫一眼做排除法就不管用了
3. **要点乱序 + 相似表述**——同一条要点用两种措辞出现，其中一种是错的（例如"CAS 失败则入队"vs"入队失败则 CAS"）

三条都只改出题逻辑，不改形态、不加时间。这是本产品在"快速点击"这个硬约束内能把难度推到的上限。

真正会推翻整个形态的只有一种结果：**命中率高、迁移率低，且上述三条加固后迁移率仍不动**。那才说明"认出来"这条路根本不通向"说出来"，那时要改的是产品定位，不是出题参数。

**⑤ 零收入对上持续的内容维护成本**（✅ 已由 §10.1 的付费设计解决）

原问题：不做付费，却定位为"做产品给别人用"。成本端是持续的——145-220 小时只是初始审核，而 `appliesTo` 字段的存在本身就证明八股内容有**版本衰减**（JDK 每半年一版），维护成本不会停。这是结构性亏损，亏的是最稀缺的资源（懂行的人的时间）。

**已修**：§10.1 定下"排期免费、题量付费"，一次性买断对标面试鸭 129 元。依据是同品类的一次性工具全都收钱且活得好（面试鸭 129 元起、牛客 119.9 元/年、LeetCode Premium 明确按短期订阅定位）——"面试完就流失"不是问题，"流失前没向他收过任何东西"才是。

**残留风险**：付费转化率完全未知，且本产品**没有留存可言**（面试完即走），意味着收入完全依赖**持续获新**。而 §7 押的 SSR 长尾搜索获客，要和 JavaGuide（156K star、8 年外链）争同一批关键词——这是所有获客渠道里最不可能奏效的一条。**获客问题目前没有答案**，应在第一版验收后单列评估。

**⑥ "为什么不直接问 AI"**（本轮新增，✅ 已由 §6.1 的定位收窄回答）

原问题：ChatGPT Study Mode 用户一句话就能得到本产品主循环的全部输出，且它**真的听你说并指出你漏了什么**——当时的文档在自己声称的核心洞察（口述）上被完整超越，还把竞品的现有能力写成了自己的第二版。

**回答**：不跟 AI 抢口述那块，主动退出。产品收窄为"整个题库按你的遗忘曲线排好，每天 15 分钟刷完，面试当天全在峰值"——这需要**跨会话的持久状态 + 结构化题库 + 排期引擎**，是对话式 AI 结构上不做的事。用户问 ChatGPT 能得到十道题和批改，但得不到"这是你第三次做错这道题，它排在你面试前两天"。

**残留缺口，仍未解决**：护城河的另一半是"明天主动提醒你"，而 §10 明确不做推送提醒。没有推送，用户想不起来打开，排期再准也不发生。这条应在第一版验收后重新评估——**推送可能是唯一不该砍的"增长功能"，因为它不是增长功能，是排期机制的组成部分。**

**① 面试日期不可预测**（✅ 已由 §5.1 改问就绪日 + §5.8 临时加密解决）
原诊断"用户嫌麻烦不设、做进激活流程即可"是错的。真实求职里"什么时候面试"不是一个日期，是持续 1-3 个月的滚动过程：面试方提前 2-5 天约时间，每场独立约。于是——用户开始准备那天**根本没有日期可填**；等他有了日期，`R≈4`，§5.2 的阶梯退化成 `[0,1,3]`，**产品最需要排期的时候排不了，能排的时候用户没有日期**。这是时间结构不匹配，不是 UI 摩擦。
强制激活的实际后果是用户填**假日期**，而假日期比没日期更糟：`readyByDate` 变更是 §5.5 的重排触发条件，每约到一场面试就改一次 → 每次重排 → §6 屏② 的圆点每次都变，正好踩中文档自己写的判词"用户感知到的东西是错的，比感知不到更糟"。
**已修**：不再问"你哪天面试"（用户不知道），改问"你希望哪天准备好"（用户自己说了算）。三段式覆盖真实求职的时间结构——冲刺期（§5.2）→ 就绪后的维持期（§5.7）→ 约到面试时的临时加密（§5.8）。引擎逻辑一行未改，只换了输入的语义。

**残留**：用户仍可能把就绪日设得过于乐观（"我三天就能准备好"）。这时 §5.4 的前缀和判据会告警并给出收窄建议——超载收窄在这里第二次证明了它是核心交互而非异常兜底（§5.6）。

**② 审核工时**（数量级已随范围扩大而上调）
1200-1600 题，朴素做法 200-270 小时，压缩后 145-220 小时 + 互斥检查 25-60 小时（§9.1）。无技术解法能绕开，只能靠压缩手段和分块并行。这是全项目的关键路径。

**③ 勾选虚高**（✅ 已由 §6 改版解决，保留记录以说明为何不能回到自评方案）

多选题客观判分后，勾错就是错，下面描述的作弊通道已关闭。保留本条是因为它解释了一个设计约束：**任何"让用户自己判断对错"的方案都会重新打开这条通道**，包括将来可能诱人的"太简单了，让我自己标记已掌握"这类功能。

以下为原分析——
系统把"少干活"的奖励直接绑在"多勾"上：勾得多 → 起始档更高 → 间隔更长 → 以后少见几次 → 每天队列更短；同时块掌握度更高 → 地图变绿 → 即时情绪奖励。两条奖励同向，没有任何反向的力。这不是"用户有动机自欺"，是产品**付钱请他自欺**。
原缓解措施"预测环节能侧面暴露高估者"**无效**：预测值也是用户自己填的，想省事的用户会同时压低预测、抬高勾选，系统看到的反而是一条漂亮的"元认知正在改善"曲线。两个信号由同一个有动机的人产生，互相验证不了。
连带污染：§4.3 的"某要点 80% 用户漏"和 §9 ④ 的质量闭环——勾选若系统性虚高，漏点统计就系统性偏低，内容迭代会把**难的要点误判为好要点**，方向是反的。

## 13. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 目标用户 | 做产品给别人用 | 求职是软件里付费意愿最高的窗口之一；同品类（面试鸭、牛客、LeetCode Premium）均已验证可收费 |
| 商业模式 | 部分免费 + 付费解锁，一次性买断 | 排期免费、题量付费：锁功能会让试用变成走过场，锁题量则与真实价值对齐（§10.1） |
| 免费层 | **任选 2 个完整知识块**，非分散的 300 道高频 | 分散 300 道 = 每块 3-5 题，违反 §2"块不完善核心动作不成立"，且超出 §5.6 的 157 容量上限 |
| 题目来源 | 知识体系反推 + 专家标注 `frequency` | 原"从面经采集"的法律论证答错了题：约束是平台合同与新《反不正当竞争法》第十三条，不是著作权；收费补齐了要件 |
| 用户回流采集 | **不做** | 它服务的是产品的数据需求而非用户的使用需求；"顺带提升留存"也不成立，留存本就不是本产品的目标。代价：`frequency` 无自我校准 |
| 离线的写权限 | **客户端只消费计划，永不生成计划** | `plan[]` 是不可重建字段（§8.2），多写者 = 静默数据损坏且无恢复路径。服务端唯一写者 + 幂等键 + 服务端判定 `localDate`（§8.3） |
| 干扰项抽取位置 | **服务端预生成选项集下发** | 客户端持有全大类语料就等于付费墙失效；预生成同时满足离线、每次重抽、可复现三个要求（§4.3） |
| 选项总数 | **固定 9 个** | 干扰项固定 3 条会让"选项数 − 3 = 答案数"，用户数一遍就破解，与该规则自身的设计目标直接冲突（§4.3） |
| SEO 与付费墙 | 公开页对爬虫和用户渲染**相同内容** | 不做 cloaking。代价是落地页只有题面 + 1-2 条 `public` 要点，但这批要点一份三用（§7） |
| 内容范围 | 后端八股文（Java 方向） | 正是"看了就忘"的知识类型，与频度记忆天然契合；知识点天然成块 |
| 内容生产 | AI 生成 + 人工审核 | 质量、速度、版权三方平衡 |
| 作答方式 | ~~翻卡自评~~ → **多选题 + 客观判分** | 自评方案与时间预算互斥（出声要 30-60 秒），且自评是激励对齐的作弊通道。改为选择题后两者同时解决 |
| 干扰项来源 | 同知识块其他题的要点，动态抽取 | 内容成本为零，且天然真实、似是而非；每次重抽可防止用户记住选项位置而非内容 |
| 回忆停顿 | 不留 | 用户判断：先认出来、熟悉知识点，自然说得出来。这是显式赌注，证伪方式见 §12 ④ |
| 口述形态 | **永久否决** | 口述费时间、用户不愿意用；且它是通用 AI 的主场，正面打必输。砍掉它等于守住 AI 守不住的那块：跨会话排期状态 + 结构化题库（§6.1） |
| 产品主张 | 短期、大量、快速刷题，把该记的知识点记住 | 不做理解辅导、不做模拟面试、不做口述训练。边界清晰才守得住 |
| 大类配额 | **11 类 / 78 块 / 1345 题，按真实分布倾斜** | 均分配额会让 JVM 注水、分布式/框架残缺（实测真实分布 4-8 倍倾斜）。总预算不变，只是放对地方（§2） |
| 题型 | **五种 `cardType`，配额化** | `keyPoints` 只覆盖 33.6% 的真实八股；CI 硬拒 + 审核经济学 + 互斥登记惩罚三条力同向，会把题库推到 70-85% 列举题（§4.3） |
| 顺序题 | `sequence` 型**强制不打乱选项** | 对因果链型题顺序就是答案，打乱等于每次复习都抹掉要考的东西。这是产品唯一一处**主动做错事**（§4.3） |
| 迁移率统计 | **必须按 `cardType` 分组** | 不分组则内容漂移与赌注偏向同向，§11 会确认 §12 ④ 而无论它是否为真——不可证伪（§12 ④） |
| 第一版范围 | 全部大类**完善覆盖**（第 5 轮后为 11 类 1345 题） | 核心动作是"哪块记不住刷哪块"，块不完善这个动作就不成立。用户判断：每个类别必须完善，否则没意义。**第 3 轮把工时从 70-80 修正到 170-280 小时后，该决策已重新确认**——理由不变，接受约半年的内容投入 |
| 题库 vs 可消化量 | 题库 1200+，单用户 3 周约 157 题 | 题库的作用是让用户**找得到**，不是让他刷完。超载收窄因此从异常兜底升级为核心交互（§5.6） |
| 内容轨定位 | 关键路径，145-220 小时 + 互斥检查 25-60 小时 | 工程轨做完会长时间空等内容轨。这是既定事实，不应为填满工程时间而扩大工程范围 |
| 日期输入 | `examDate` → **`readyByDate`（就绪日）** | 用户不知道哪天面试（求职是 1-3 个月滚动过程），但知道自己想哪天准备好。引擎不变，输入语义变诚实 |
| 时间结构 | 冲刺期 → 维持期 → 临时加密 | 分别对应 §5.2 / §5.7 / §5.8。维持期不再是兜底，它覆盖"已就绪、等通知"这段真实且漫长的日子 |
| 知识分块 | 两层树 + 掌握度地图 | 一屏看出哪块红了，导航浅、决策快 |
| 排期算法 | 考试驱动倒计时 | ~~唯一为面试当天优化的方案，也是 Anki 类产品结构上做不到的~~ **理由已作废**（第 2 轮查证：RemNote/Quizlet 已内置，Anki 官方 FAQ 教手算）。保留该算法是因为它对本场景确实正确，但它是实现质量而非差异化来源 |
| 平台 | 移动端优先 Web + PWA | 上线最快、无需审核、链接可分享、SSR 可获长尾搜索流量 |
| 建设路径 | 内容先行，产品做薄 | 成败在内容质量而非工程；先用最小工程量跑通主链路 |
| 预测环节 | ~~保留~~ → **已随自评方案一起废弃** | 它服务于"预测 vs 实际说到"的对比，而"实际说到"这一步已不存在。且预测值也由用户自填，本就无法验证 |
| 计划重算时机 | plan-once，只在三种条件下重生成 | 每次提交重算构成芝诺递推，实测承诺 3 遍的卡实际刷 12 遍 |
| 间隔形式 | 绝对间隔阶梯，非比例缩放 | 比例缩放在 `E ≤ 12`（主场景）退化成连续日，递增间隔名存实亡 |
| 末端对齐强度 | 末端**窗口**对齐，非单日 | 单日对齐与容量约束在满载时互斥，两者不能都写成硬保证 |
| 重放承诺 | 只承诺重算掌握度，不承诺重放排期 | 排期还依赖 readyByDate/capacity 变更历史，第一版不做设置变更事件流 |
