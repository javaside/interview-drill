# 面试刷题产品 · 设计文档

- 日期：2026-09-15
- 状态：已确认，待编写实现计划

## 1. 背景与目标

程序员准备面试时，八股文知识"看了就忘"：复习过的内容在面试当天想不起来。现有方案各有缺口——面试题仓库（JavaGuide 等）只解决"内容从哪来"，不解决"怎么记住"；通用记忆软件（Anki）有记忆算法但没内容，且算法目标与面试场景错位。

本产品把两者合起来：**按知识块组织的面试题库 + 为面试当天优化的复习排期**。

用户旅程：设定面试日期 → 在知识地图上看到哪块"红了" → 刷那块 → 面试当天所有题处于记忆峰值。

## 2. 范围

- **目标用户**：准备后端面试的程序员（第一版聚焦 Java 方向）
- **形态**：移动端优先的响应式 Web + PWA
- **第一版内容范围**：后端八股文 → 并发一个大类

## 3. 核心洞察

**间隔重复算法为"终身记忆"优化，而面试复习是"短期冲刺"。**

标准 SM-2/FSRS 的间隔无上界：答对就翻倍，1→3→7→15→30→60 天。用户 3 周后面试，一道 D11 答对的卡会被排到 D26 复习——落在面试之后。用户在面试当天的记忆强度，恰恰是这类算法从未优化过的目标。

本产品的差异化即在此：**排期目标是面试当天的记忆强度最大化**，而非长期留存。这是 Anki 类产品结构上做不到的事（它们没有"考试日"这个概念）。

第二个洞察：**八股面试是口述的**。翻卡自评存在"熟悉感 ≠ 能说出来"的系统性偏差——用户看到答案觉得"我知道"，真让他说却说不利索。本产品用**要点勾选计分**把自评从主观感觉变成可数的客观量（见 §4）。

## 4. 内容模型

### 4.1 层级

```
大类 (category)  →  知识块 (block)  →  题卡 (card)
并发              AQS 与锁           "AQS 是怎么实现独占锁的？"
```

题卡**单一归属**于一个知识块。跨领域的题（如"Redis 分布式锁"）通过 `relatedBlocks` 软链接指向其他块，不做多归属——否则块掌握度会被重复统计，知识地图失真。

### 4.2 题卡结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定标识。间隔重复要求同一道题在整个复习周期内 ID 不变 |
| `blockId` | string | 唯一归属的知识块 |
| `relatedBlocks` | string[] | 软链接，不参与掌握度统计 |
| `question` | string | 面试官口吻的问法，非教科书标题 |
| `keyPoints` | string[] | **3-6 条可得分要点**，自评的计分单位 |
| `detail` | markdown | 展开讲解，可折叠，不参与计分 |
| `followUps` | string[] | 1-2 个追问，模拟面试官深挖 |
| `sources` | Source[] | 权威出处（官方文档 / 源码 / RFC），每条要点可验证 |
| `appliesTo` | string | 版本适用范围，如 `JDK 8+` |
| `frequency` | `high`\|`mid`\|`low` | 面试出现频度，由面经统计得出（§9） |

### 4.3 keyPoints 是设计枢纽

刷题流程中：翻面**前**用户预测能说出几个要点 → 翻面后要点逐条展开 → 用户勾选**实际说到**的条目 → 系统以 `勾选数 / 要点总数` 计分。

三个作用：
1. 自评从"我觉得我会"变成可数的客观量
2. 预测值与实际勾选的差距，量化用户的元认知偏差（长期高估者值得单独提醒）
3. 勾选数据沉淀为内容迭代依据——某条要点如果 80% 用户都漏，说明它写得太偏，不配当得分点

`sources` 和 `appliesTo` 不是装饰。八股文最大的坑是版本差异（偏向锁在 JDK 15 后被废弃），标了出处用户才敢信。

### 4.4 掌握度计算

**卡状态**（存于 `card_state`，字段见 §8.1）：

- `phase`：`new`（从未刷过）| `learning` | `done`（本周期计划已走完）
  `new` 是**独立状态，不是 `s = 0`**。从没见过的卡和见过但说不出的卡，需要的干预完全不同
- `s ∈ [0,1]`：最近 3 次得分的加权平均，权重 `3:2:1`（不足 3 次按已有次数归一）
- 单次得分 `= 勾选数 / 该次复习时的要点总数`，分母随复习记录一起存（§8.1）

`s` 取加权平均而非"最近一次"：单次观测做估计量方差太大，连续五次满分的卡不该因为一次走神就把整条计划推倒重来。

**块掌握度** = 块内**当前计划内**卡片的 `s` 加权平均，权重按 `frequency`（high=3, mid=2, low=1）。

分母**只算计划内的卡**。被 §5.4 收窄排除的低频卡不进分母，UI 上单独标注"已排除 N 张低频"。否则会出现一个荒谬的死结：用户听产品建议只刷高频，把高频全刷到满分，块掌握度仍永远卡在 45%（3 张 high 满分 / 权重总和 20）——地图永远是红的，而唯一能让它变绿的动作，是去刷产品刚刚明确告诉他不要刷的低频卡。

`phase = new` 的卡不进分母；块内全为 `new` 时地图显示"未刷"而非 0%。

## 5. 排期引擎（核心）

> 本节经过一轮敌意评审后重写。评审报告见 `docs/superpowers/reviews/round1-scheduler-correctness.md`，其中的实测数字在下文中用于说明"为什么不能那样写"。

### 5.1 接口与不变量

```
schedule(cards[], cardStates[], examDate, dailyCapacity, today)
  → { todayQueue, plans, overloadWarning }
```

**纯函数**：无 IO、无副作用、不读系统时钟。

**时间类型钉死**：`today` 与 `examDate` 均为**本地日历日**（`YYYY-MM-DD`），日差按日历天数计算，**不用毫秒差除以 86400000**——DST 切换那天是 23 或 25 小时，除法会得到 `0.96` 或 `1.04`，取整就少一天。日界定在**本地时间 04:00**：刷题用户会熬夜，23:50 和次日 00:10 应算同一天。

**排序必须确定**：所有涉及卡片排序的地方，排序键末尾一律追加 `cardId`。否则同键时的顺序取决于数据库返回顺序或对象键顺序——那不在 `schedule()` 的参数里，"输入确定则输出确定"就是假的，§7 的单测和 §8 的重放一起落空。

**五条不变量**，每条对应 §11 的一组单测：

| # | 不变量 |
|---|---|
| I1 | 每张计划内的卡，末次复习落在 `[E - fw + 1, E]`，高频卡优先占 `E` |
| I2 | 计划内日期严格递增，同一张卡不在同一天出现两次 |
| I3 | `R ≥ 0` 且存在计划内卡片时，`todayQueue` 非空 |
| I4 | 计划生成后不再重算，除非触发 §5.5 的三种条件之一 |
| I5 | 任一天负载 ≤ `dailyCapacity`，唯一例外是 `E = 0`（明天面试），此时超载且必须告警 |

### 5.2 计划生成（plan-once）

**计划一次性生成并持久化，之后只消费不重算。**

这是对早期设计的根本修正。早期方案是每次提交后按剩余窗口重算，`d_1` 取剩余窗口的比例分数——那构成芝诺式递推，步长随窗口缩短而缩短，复习次数发散。实测一张「每次都通过、承诺复习 3 次」的卡，实际被复习 **12 次**，从第 11 天起变成每日复习，而 §6 屏③ 那排圆点每刷一次就多画一个。**没有不动点的排期不能用。**

**① 窗口**

```
R = examDate - today                       // 日历天数
buffer = 1 (R < 30) | 2 (30 ≤ R < 50) | 3 (R ≥ 50)
E = R - buffer                             // 末次复习的目标日（相对今天的偏移）
```

`buffer` 是**查表不是公式**。早期写成 `clamp(round(R × 0.05), 1, 3)`，实测它在 `R ≤ 29` 恒为 1、`R ≥ 50` 恒为 3，只在 `R ∈ [30, 49]` 真正起作用——而产品主场景（1–3 周备考）全落在常数区。查表更诚实，也免掉 `round` 半值方向的歧义。

`R < 0`（面试日已过）→ 视同未设日期，走 §5.6，并提示用户更新日期。这是必然发生的输入。

**② 绝对间隔阶梯**

```
INTERVALS = [1, 2, 4, 8, 16, 32, 64]       // 天，绝对值
```

起始档由掌握度决定，**用分数比较，不用小数阈值**：

| 条件 | 起始档 |
|---|---|
| `phase = new` 或 `3 × 勾选数 < 要点总数` | 0 |
| `3 × 勾选数 < 2 × 要点总数` | 1 |
| 未满分 | 2 |
| 满分 | 3 |

必须用分数。早期写的是 `s ≥ 0.67`，而 `2/3 = 0.6667 < 0.67`——三要点卡答对两条会掉进下一档。同样是"大部分说对了"，三要点卡的用户被平白多排一遍。`s ≥ 0.9` 那档更糟：3–6 要点卡里 `1.0` 之下的最大值是 `5/6 ≈ 0.833`，那一档**实际只有满分可达**，`0.9` 是假精度，会误导实现者以为存在一个 0.83–1.0 的区间。

**③ 铺阶梯，末端截断**

```
a = [offset]
idx = 起始档
while a.last < E' and idx < len(INTERVALS):
    a.append(a.last + INTERVALS[idx]); idx += 1
plan = [x for x in a if x < E'] + [E']      // E' = 该卡的末次目标日，见 ④
```

**复习次数是输出不是输入**——由窗口长度决定刷几遍，那张容易出错的 `n` 表就不需要了。

实测样例（`offset = 0`，新卡）：

```
E=20 → [0, 1, 3, 7, 15, 20]        E=6 → [0, 1, 3, 6]
E=4  → [0, 1, 3, 4]                E=2 → [0, 1, 2]        E=0 → [0]
```

全部严格递增、起于今天、止于 `E`，无退化。对照早期的比例缩放公式：`E=4` 时它算出 `[1,2,3,4]`，间隔 `[1,1,1,1]`——**一到两周备考时"递增间隔"完全退化成连着刷四天**，而这恰恰是它声称要利用的机制。更糟的是穷举 `n=1..5, E=n..199` 后发现**不存在任何 `d_i = 0`**：新用户走完激活流程，第一屏看到的是"今天没有要复习的题"。

**④ 首次曝光错峰 + 末端窗口**

早期公式里 `d` 只由 `(E, n)` 决定，不含任何卡片自身信息——**同一批新卡拿到逐字节相同的计划**，全堆在同几天。两处修正：

- **新卡配额**：`newPerDay = max(1, floor(dailyCapacity × 0.35))`。按 `(frequency 降序, cardId 升序)` 排位，第 `j` 张新卡的 `offset = min(j / newPerDay, E)`，剩余容量留给复习。不加配额的话，150 张新卡各自还带一次"+1 天"的复习，前端必然拥塞。
- **末端窗口**：所有卡的末次都想落在 `E`，那天必然爆。末次分散到 `[E - fw + 1, E]`，`fw` 从 `ceil(计划内卡数 / dailyCapacity)` 起，若仍有某天超容量则递增 `fw` 直到满足 I5。高频卡分配到最靠近 `E` 的日子。

第二条是**对早期设计的明确让步**：「末次严格落在面试前 buffer 天」降级为「落在末端窗口内」。早期把"末端对齐"和"超载只能往前挪"同时写成硬保证，而这两条在任何满载场景下互斥——实测 150 张卡 / `R=7` / 容量 30 时，`day0` 会拿到 **420 张**（超容量 14 倍），且 150 张里有 **120 张**的末端对齐被打破。互斥的保证必须明着选一个，不能两个都写。

### 5.3 容量装箱

不做事后均衡，容量是**生成时的硬约束**。按 `(frequency 降序, cardId 升序)` 逐卡装箱：

- **末次不可移动**，优先占位（由 §5.2 ④ 的末端窗口保证不超容）
- **中间次遇到当天已满 → 往后推一天**，最多推到末次的前一天；若该卡已占用目标日则继续后推（保证 I2）
- 推到无处可去 → **丢弃该次复习**，计入 `overloadWarning.dropped`

**往后推而非往前推。** 往前推会挤爆今天——今天没有"前一天"可以继续推，是唯一被豁免容量的日子；而且提前复习等于缩短间隔，对间隔重复没有价值。少刷一遍，好过把一遍刷在没用的位置上。

### 5.4 超载检测

判据是**前缀和**，不是总量：

```
for t in 0..E:
    if 累计需求(day 0..t) > (t + 1) × dailyCapacity:
        告警，报出最早违反的 t
```

总量判据（`Σ复习次数 > R × dailyCapacity`）不够用——它只检查了可行性条件里最松的那一项，而负载天然堆在前端，**卡死的永远是前缀**。实测：100 张卡 / `R=30` / 容量 30 时，总量 `400 ≤ 900` 不告警，`day0` 却仍然溢出到 40 张。

告警文案报**最早排不下的那一天**（"你前 3 天就已经排不下了"比"总量超了"可操作得多），并给出按 `(frequency 降序, cardId 升序)` 的收窄建议。收窄后**必须重跑一遍前缀和判据**确认真的可行：早期的收窄建议只满足总量判据，实测砍完之后 `day0` 仍是 66 张 / 容量 30——"补救成功"而问题原封不动。

**已知的容量缺口**：§10 的第一版范围在默认容量下装不下。150 张新卡各约 6 次复习 ≈ 900 次需求，而 3 周 × 30 题 = 630 容量，实测从第 11 天起告警。因此**默认 `dailyCapacity` 定为 45**（900 / 21 ≈ 43），§10 同步记录这个约束。

`E = 0`（明天面试）是唯一允许突破容量的情况：所有卡排在今天并告警。此时没有更好的选择。

### 5.5 重新生成计划

计划只在三种情况下重生成，其余时候只消费：

1. **答错**：勾选比例 `< 1/2` → 起始档退回 0，**从明天起**重新生成
2. `examDate` 变更
3. `dailyCapacity` 变更

答错重排从**明天**起，不是"当天稍后"。早期写的是当天稍后，它和"每次提交重跑 `schedule()`"叠加会构成**同日死循环**：`R ≤ 1` 时全部卡排今天 → 刷完重跑 → 还是今天 → 无限循环，而且发生在面试前一天这个产品最重要的日子。

**终止状态**：计划中已无 `> today` 的项 → `phase = done`，退出 `todayQueue`。早期文档没有任何终止条件，`schedule()` 在任何输入下都至少吐出一次未来复习。

**逾期卡**：计划日已过但没刷的卡，并入下次打开时的 `todayQueue`，且不改变计划中剩余的项；逾期卡排在当天新排卡之前。用户 day4 该刷没刷、day9 才打开，是常态而非异常。

### 5.6 无面试日期时的退化

`examDate` 为空或已过期时走日常维持模式：

- 档位 `k` 存于 `card_state.phase_index`，新卡 `k = 0`
- 间隔表 `[1, 3, 7, 15, 30, 60, 120]` 天，到表尾后**停在 120 天不再增长**
- 勾选比例 `≥ 1/2` → `k += 1`；`< 1/2` → `k = 0`
- `examDate` 从空变为有值时，按当前 `s` 走 §5.2 生成计划；`phase_index` 保留但不参与考试模式

**注意**：此路径是兜底，不是主路径。产品设计上要引导用户设定日期（见 §12 风险 ①）。

## 6. 刷题主循环

一张卡三屏，目标 15-25 秒。

**① 题面**
显示知识块名、频度标签、今日进度（`12/30`）、常驻的"面试还剩 N 天"。

今日进度的分母 = 今天开始时 `todayQueue` 的长度（含逾期卡），**当天内不变**。答错重排到明天（§5.5），不会往当天分母里追加，所以进度条不会出现 `12/30 → 12/31` 这种自增。
提示"先出声说一遍"，然后**预测能说出几个要点**（按钮为 `0 .. keyPoints.length`，随卡片要点数动态生成，不是固定 6 个）→ 翻面。

预测环节保留，理由是它制造"预测—打脸"的落差，那是记忆最容易被巩固的时刻；同时产出元认知偏差数据。代价是每张卡多一次点击，接受。

**② 要点勾选**
要点逐条列出，用户勾选"刚才真的说到"的条目。底部显示 `3 / 5` 及与预测值的比对。
`detail` / `followUps` / `sources` 默认折叠。

**③ 排期反馈**
- 掌握度环（`3/5 = 60%`）
- **漏了哪几条** + "这两条 68% 的人也漏了"（§4.3 的勾选数据在这里变成用户可感知的价值）
- **"下次 2 天后 · 面试前还会再过 2 遍"**，配一排圆点表示该卡在面试前的剩余复习节点，末尾红点为面试日

第 ③ 屏的排期反馈是刻意设计的：算法再聪明，用户感知不到就等于不存在。

**这屏的正确性依赖 §5.2 的计划持久化。** 圆点画的是已经落盘的计划，答对时它只会少一个，不会重画。早期的每次重算方案会让这排圆点每刷一次就变多——用户感知到的东西是错的，比感知不到更糟。答错触发重新生成（§5.5）时，UI 必须明说"计划已重排"，而不是默默换一排圆点。

## 7. 架构

**技术栈**：Next.js (App Router) + TypeScript + PostgreSQL。

选 Next 的实际理由是题目页面可 SSR 被搜索引擎收录——"AQS 是怎么实现独占锁的"这类长尾搜索是刷题产品最重要的免费获客渠道。认证用 GitHub OAuth（用户是程序员）+ 邮箱兜底。

**内容进 Git，不进 CMS**：题卡源文件是仓库里的 Markdown/YAML，构建时同步进库。审核流程直接用 PR，版本历史和 diff 白送，省掉一整个编辑后台子系统。

```
content/                      # Git 管理的内容源（非代码）
  concurrency/
    aqs-and-locks/
      001-aqs-exclusive-lock.md

src/
  lib/scheduler/              # ★ 纯函数、零依赖、可完整单测
    plan.ts                   #   计划生成：阶梯 + 错峰 + 末端窗口 (§5.2)
    capacity.ts               #   容量装箱 + 前缀和超载检测 (§5.3, §5.4)
    regenerate.ts             #   重生成条件与终止状态 (§5.5, §5.6)
    schedule.ts               #   主入口
    types.ts
  lib/content/
    parse.ts                  #   源文件 → Card
    validate.ts               #   schema 校验
  lib/mastery/                # 掌握度计算 (§4.4)，纯函数
  server/                     # DB 访问、API handlers
  app/
    (drill)/                  # 刷题主循环
    map/                      # 知识地图
```

依赖严格单向：`app → server → lib`。`lib/scheduler` 不依赖任何模块。

## 8. 数据流与错误处理

### 8.1 存储结构

`review_log`（append-only，永不更新）——每条记录必须自带当时的上下文，否则日志无法解释：

| 字段 | 为什么必须存 |
|---|---|
| `cardId`, `userId`, `reviewedAt` | — |
| `checkedCount` | 勾选数 |
| `keyPointsTotal` | **复习当时的要点总数**。内容在 Git 里会改，某张卡要点从 4 条变 6 条后，历史记录里"勾了 3 条"的含义会从 `0.75` 静默变成 `0.5` |
| `predictedCount` | §4.3 的元认知偏差 |
| `examDateAtReview`, `dailyCapacityAtReview` | 排期的输入，不存就无法解释当时为什么排在那天 |
| `algoVersion` | §5 必然迭代，不记版本就分不清"算法变了"和"数据坏了" |

`card_state`：`phase`、`s`、`plan[]`（已生成的计划）、`phaseIndex`（§5.6 用）、`reviewCount`、`planGeneratedAt`。

**刷一张卡**：
```
提交勾选 → 写 review_log → 更新 card_state（消费计划中的当前项）
         → 仅在 §5.5 三种条件下才重新生成计划
         → 返回 { 新掌握度, 下次复习日, 面试前剩余遍数 }
```

注意这里**不是**每次提交都重跑 `schedule()`——那正是造成复习次数发散的原因（§5.2）。

### 8.2 重放能力的边界

`review_log` 足以**重算掌握度 `s`**，因为每条记录自带 `keyPointsTotal`。

`review_log` **不足以重放排期**。排期还依赖 `examDate` 与 `dailyCapacity` 的**变更历史**——用户在第 5 天把面试从 10-06 改到 10-20，用当前值重放得到的历史与真实发生过的完全不同。要支持排期重放，得再加一条 `user_settings_log` 事件流。

**第一版只承诺前者**，不做 `user_settings_log`。这意味着：拿历史日志回测新算法（可以做），`card_state` 写坏后完整恢复排期（做不到，只能按当前设置重新生成计划）。早期文档写的"所有排期状态都能从日志重放"是一张空头支票，这里明确兑现范围。

### 8.3 其他

**断网**：地铁刷题必然断网。提交先落 IndexedDB 本地队列，联网后按序回传。排期引擎是纯函数，客户端可同构运行，断网也能刷完当天的量。

**多设备冲突**：`review_log` append-only 天然无冲突。`card_state` 按 `reviewedAt` 重算 `s`——但时间戳由客户端时钟产生，跨设备有偏差。因此 `reviewedAt` 记 UTC 瞬时值用于排序，而"属于哪一天"按 §5.1 的本地日界单独判定，两者不混用。`card_state` 只能重算 `s`，重算不出计划（见 §8.2）。

**内容校验失败**：CI 上跑 `lib/content/validate`，要点少于 3 条或缺 `sources` 的卡直接构建失败，坏内容进不了生产。

## 9. 内容生产管线

题目来源与答案来源是两回事。

**① 题目从面经来**（牛客 / V2EX / 小红书的面试记录 + 岗位 JD）。被问到的问题是客观事实，不受版权保护；抄答案才有版权问题。此步骤同时产出**出现频度统计**，即 `frequency` 字段——它不是拍脑袋填的，而是数出来的，且直接决定超载时先砍谁（§5.4）、以及末次复习谁最贴近面试日（§5.2 ④）。

**② 答案对着一手资料生成**，不依赖模型记忆。输入：官方文档对应章节、JDK 源码片段、RFC 原文。输出：3-6 条要点，每条标出处和适用版本。**无出处的断言一律剔除**。这是把"AI 幻觉"约束成"AI 摘录"。

**③ 人工审核走 PR**，清单四条：
1. 每条要点能否在 `sources` 里逐条验证
2. 版本适用性是否标对
3. 要点粒度是否齐整
4. 题面是否是面试官的真实问法

**④ 上线后的质量闭环**：

| 信号 | 说明什么 | 动作 |
|---|---|---|
| 某要点 80% 用户漏 | 要点太偏或太细 | 标记复核 |
| 某题人人秒过 | 太简单 | 降频或删除 |
| 用户点"报错" | 可能确有错误 | 自动开 issue |

**成本**：审核是瓶颈，不是生成。150 题按每题 10 分钟审是 25 小时实打实的工作量，且需要懂行的人做，外包不了。这是本方案的主要成本项。

## 10. 第一版边界

**做**：
- 并发一个大类，8-10 个知识块，150 道精品题
- 知识地图（两层 + 掌握度环）
- 三屏刷题主循环
- 考试驱动排期（含无日期退化）
- GitHub 登录 + 云端同步
- 断网可刷

**容量约束**（由 §5.4 的实测推出）：150 张新卡在 3 周窗口内约需 900 次复习，因此**默认 `dailyCapacity = 45`**，而非最初设想的 30。若产品上线后发现每天 45 题（约 15-20 分钟）超出用户耐受，应优先砍题量到约 100 题，而不是降容量——降容量会让几乎每个新用户在激活当天就撞上超载收窄流程，那是最糟的第一印象。

**明确不做**（验证后再议）：其他大类、AI 口述判分、社区贡献 / UGC、付费、编辑后台、推送提醒、排行榜 / 打卡分享。

**两条并行轨道**：本文档同时覆盖软件实现和内容生产，二者依赖关系弱，应并行推进——
- **工程轨**：§5-§8，可用少量样例题（10-20 道）全程开发，不阻塞于内容
- **内容轨**：§9，150 题的采集、生成、审核，是日历时间上的长项

实现计划需把两轨分开排期，只在验收（§11）处汇合。若按串行推进，工程会空等内容。

## 11. 验收标准

1. **端到端跑通**：设面试日期 → 刷完 150 题的排期 → 所有题在面试日前收口
2. **排期正确性**：`lib/scheduler` 单测全绿。§5.1 的五条不变量 I1–I5 各自成组，外加这些边界：

   | 边界 | 期望 |
   |---|---|
   | `R = 0 / 1 / 2 / 3` | 不崩、不空队列、末次落在 `E` |
   | `R < 0`（面试日已过） | 走 §5.6 退化路径并提示更新 |
   | 150 题 / 3 周 / 容量 30 | 前缀和判据告警，报出最早违反日 |
   | 收窄建议执行后 | 重跑判据确认真的可行 |
   | 一张卡连续通过到面试 | 复习次数 = 计划长度，**不发散** |
   | 答错 | 重排从明天起，当天不再出现同一张卡 |
   | 逾期 5 天后打开 | 逾期卡并入队首，剩余计划不变 |
   | 无面试日期 | §5.6 档位进退正确，到 120 天封顶 |
   | DST 切换日 / 跨时区 | 日差按日历天计算，不偏移 |

3. **内容质量**：150 题全部通过 schema 校验 + 人工审核签字
4. **产品有效性**：找 5-10 个真要面试的程序员用两周，面试后询问"你被问到的题里，有多少在这刷到过"

第 4 条是真正的验收。覆盖率低于 50% 说明选题跑偏，工程质量再高也救不回来。

## 12. 风险

**① 用户不设面试日期**（最致命）
倒计时是全部差异化的地基。用户嫌麻烦不设，产品立刻退化成题库更窄的 Anki。
缓解：把设定日期做进**首次激活流程**，而非藏在设置里的可选项。进来第一句就问"你什么时候面试"，没日期就没有个性化排期。

**② 审核工时 25 小时**
无技术解法，只能砍范围。扛不住就从 150 题砍到 80 题，宁可少而精。

**③ 勾选仍可能虚高**
用户可以勾他其实没说到的条目。预测环节和漏点统计能侧面暴露长期高估者，但根治不了。根治需要 AI 口述判分，属第二版。第一版接受这个精度损失。

## 13. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 目标用户 | 做产品给别人用 | — |
| 内容范围 | 后端八股文（Java 方向） | 正是"看了就忘"的知识类型，与频度记忆天然契合；知识点天然成块 |
| 内容生产 | AI 生成 + 人工审核 | 质量、速度、版权三方平衡 |
| 作答方式 | 翻卡自评（要点勾选计分） | 单卡 15-25 秒，满足"快速刷题"；勾选计分修正自评虚高 |
| 知识分块 | 两层树 + 掌握度地图 | 一屏看出哪块红了，导航浅、决策快 |
| 排期算法 | 考试驱动倒计时 | 唯一为面试当天优化的方案，也是 Anki 类产品结构上做不到的 |
| 平台 | 移动端优先 Web + PWA | 上线最快、无需审核、链接可分享、SSR 可获长尾搜索流量 |
| 建设路径 | 内容先行，产品做薄 | 成败在内容质量而非工程；先用最小工程量跑通主链路 |
| 预测环节 | 保留 | 制造"预测—打脸"的记忆巩固时刻，并产出元认知偏差数据 |
| 计划重算时机 | plan-once，只在三种条件下重生成 | 每次提交重算构成芝诺递推，实测承诺 3 遍的卡实际刷 12 遍 |
| 间隔形式 | 绝对间隔阶梯，非比例缩放 | 比例缩放在 `E ≤ 12`（主场景）退化成连续日，递增间隔名存实亡 |
| 末端对齐强度 | 末端**窗口**对齐，非单日 | 单日对齐与容量约束在满载时互斥，两者不能都写成硬保证 |
| 重放承诺 | 只承诺重算掌握度，不承诺重放排期 | 排期还依赖 examDate/capacity 变更历史，第一版不做设置变更事件流 |
