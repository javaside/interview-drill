## 项目为什么分三条轨道

spec §10 把工作明确切成三条**并行**轨道，只在验收（§11）处汇合。这不是排期失误，是刻意设计——理解这三条轨道是理解整个排序的前提：

| 轨道 | 内容 | 性质 | 关键约束 |
|---|---|---|---|
| **工程轨** | §5–§8：排期引擎、出题引擎、掌握度、权限、同步、应用层 | 纯开发，可用 10-20 道样例题全程推进 | 不阻塞于内容；做完会长时间空等内容轨 |
| **内容轨** | §9：题卡的采集、生成、审核（spec 原定 78 块 / 1345 题，实际收敛为 81 块 / 404 卡，见「一句话现状」） | 人力密集，**145-220 小时** + 互斥检查 25-60 小时 | **关键路径**——日历时间的绝对长项 |
| **资质轨** | 境内收款的前置资质链条 | 零工程人力，纯日历等待 | **4-8 周串行**，必须第一周启动 |

**三条轨道的排序逻辑是"谁卡日历谁先启动"**，而不是"谁重要谁先做"：

- 资质轨和内容轨都是**日历长项**，晚启动一周，上线就晚一周，与工程进度无关。
- 工程轨是**可压缩项**，人力到位就能快速推进，且能用样例题独立开发。

## 计划 1 已交付什么（已完成）

**8 个纯函数模块 + 6 个 CLI 工具 + 单块试点 + CI 接线**，94 个单测全绿、`typecheck` 无错。

- **`src/lib/content`**（零 IO 纯函数，可完整内存单测）
  - `types.ts` — 领域类型 `Card`/`KeyPoint`/`Source`，并定死 spec 未定义的 `Source`
  - `schema.ts` — zod 校验，最少要点数**按 `cardType` 分派**（不是统一 3 条）
  - `rules.ts` — 三条机器校验正则（要点 ≤30 汉字、承载词黑名单、块名黑名单）
  - `parse.ts` + `yaml.ts` — 源文件解析，钉 `JSON_SCHEMA` 防 `verifiedAt` 被解析成 Date
  - `audit.ts` — 全库审计：id 唯一性、外键、干扰项池容量、跨提交 id 守卫
  - `block.ts` — 块元数据 + B5 块名校验
- **`tools/`**（本地 CLI，直接读写 `content/`，不部署）
  - `content-new/` — 脚手架，id 由 ULID 铸造（防序号派生 id 触发重编号）
  - `review/` — 互斥检查的组合生成、召回预筛、人工确认写回
  - `audit-cli.ts` — 唯一的读盘处，接 CI
- **单块试点**：MySQL「MVCC 与 Undo Log」，五种 `cardType` 各一张、共 17 条要点，`status: ready` 下审计通过
- **校准笔记**：实测均值约 12.8 分钟/题（`docs/superpowers/notes/2026-09-18-pilot-calibration.md`）
- **CI**：`.github/workflows/content.yml`，lockfile 从 `origin/main` 取

**端到端验证过的验收项**：占位符回归拦截、跨提交 id 守卫（改 id 无 `movedFrom` → 红，补上 → 绿）、互斥回路（答"是/否"分别写回，重跑不再问）。

**唯一未勾的验收项**：CI 真跑一次并转绿——需开 PR 在 GitHub Actions 上实跑，无法本地验证。

## 计划 4a 已交付什么（已完成）

**`src/server` 服务层**：把三个纯函数库（scheduler / options / mastery / entitlement）接到持久化与 HTTP 上。纯核单测 + pglite 进程内集成测试，全库 280 单测全绿、`typecheck` 无错、`next build` 成功。HTTP 路由是薄壳，逻辑全在可单测的纯核里。

- **基座**：Next.js（App Router）+ drizzle schema/迁移，pglite 用于进程内集成测试
- **日界与时钟**：服务端日界判定 + 客户端时钟钳制（防提前/回拨刷时间）
- **判分核**：确定性变体重算（服务端按种子重放出题）+ 四型判分 + 卡状态迁移，纯函数可单测
- **同步回放**：幂等、乱序重放、时钟钳制、服务端日界——离线提交回放到服务端的核心
- **唯一池装配**：`buildDistractorPools` 统一入口（同块池 + 跨块池 + 相邻大类池三层）
- **今日队列**：`buildDailyPayload` 装配今日队列（entitledCards 过滤 → schedule → 逐卡出题）
- **刷卡流程**：刷一张卡的完整服务端流程（取题→判分→更新 s→回写）
- **设置/块集变更**：§5.5 条件 2/3/4 的变更入口（重生成、维持模式切换等）
- **GitHub OAuth** 接线 + **内容 upsert job**（把 `content/` 灌进库）

**对 4b 的接口**：`/api/queue`（今日队列）· `/api/review`（提交判分）· `/api/sync`（离线回放）。UI 层只消费这三个端点。

## 整体排序建议

> 以下与「依赖关系图」是 2026-09 工程启动期的排序决策记录（谁卡日历谁先启动），保留作回顾；当前状态见顶部「一句话现状」与「下一步」。

按"谁卡日历谁先启动"的原则，**三件事应当同时启动**，而不是串行：

### 立即启动（并行三路）

1. **资质轨（计划 5 的资质部分）** — 零工程人力，但 4-8 周串行日历时间。**这是最该现在就动的**：它不占开发资源，却决定上线下限。放到工程做完再启动，等于让写好的产品干等 1-2 个月才能收款。
2. **内容批量生产** — 关键路径，用计划 1 的工具链按块推进。试点已校准工时，可开始铺量。这是人力长项，越早开始越好。
3. **工程轨 · 计划 2（排期引擎）** — 见下。

### 工程轨内部顺序（严格）

依赖是单向的 `app → server → lib`，所以工程计划必须自底向上：

```
计划 2（lib/scheduler）  ──┐
                           ├──→ 计划 4a（server）✅ ──→ 计划 4b（app UI）──→ 验收 §11
计划 3（lib/options 等）  ──┘
```

- **先做计划 2（排期引擎）**，理由三条：
  1. 它是产品的**核心机制**（§3：面试当天记忆强度最大化），差异化就在这里
  2. **零上游依赖**、纯函数、可立即开工，不等任何东西
  3. §11 验收标准里排期正确性权重最重（I1–I5 五条不变量 + 十余个边界用例），风险最高，越早暴露越好
- **再做计划 3（出题与掌握度）**，它依赖计划 1 的类型（已就绪），同样是纯函数，可紧接计划 2 或与之并行（若有第二个人）
- **计划 4 拆两步**：先 **4a（服务层）**——它依赖 2+3 全部，是三条工程计划的汇合点，已完成；再 **4b（UI 层）**，只消费 4a 的三个端点

### 为什么不先做应用层

应用层看得见、最有成就感，但它依赖排期和出题两个纯函数库。先搭 UI 会让核心逻辑塞进组件里、无法单测——而 §11 明确要求这些模块**必须有独立测试**。自底向上是这套架构的硬约束。

## 已知文档债务（2026-10-01 审计）

审了全库文档与代码的一致性，发现的**尚未解决**的偏差记录在此，避免下次又当成新发现：

1. **内容范围变了但没有拍板记录。** spec §2 定的是 11 大类 / 78 块 / 1345 题（含独立 `redis` 类），实际内容是 12 大类 / 81 块 / 404 卡（无 `redis` 类，新增 `agent`、`architecture`）。代码与数据是权威，但**这次收敛是何时、由谁、基于什么决定，Git 与文档里都查不到**。要么补一条决策记录，要么把 spec §2 的配额表标注作废——现在两处并存，读的人会以为内容只做了三分之一。
2. **spec 全文数字已过时**（11 类 / 78 块 / 1345 题散见 §2、§11、§12）。spec 是 2026-09-15 的设计存档，`AGENTS.md` 已声明「部分决策已被推翻，以本文件与 git log 为准」，但它自己身上没有这条提示——建议在标题下加一行状态横幅。
3. **内容真的写错了一处**：8 张卡的进阶分隔符写成 `<!--advanced>>`（少一横），进阶内容静默混进入门版。已修复，但 `content:audit` **不检查分隔符拼写**（只校验 `**`/反引号配对），同类错误下次仍会漏过——审计规则里补一条是独立待办。
4. **`src/server/deps.ts:26` 注释是过期描述**：写「paid 空集 = 全部，兜底由 buildDailyPayload 统一做」，但 `buildDailyPayload` 只有「勾选集过滤、空即空」，**没有 paid 兜底**。注释与代码相反，容易误导。
5. **`/upgrade` 一句话与实现不符**：`UpgradeView.tsx:61` 对已解锁用户写「保留原勾选（不默认全选）」，但兑换/履约会把 `free_block_ids` 置空，**原勾选实际被清掉**，用户得回设置重勾。UI 的下一步引导是对的，这句描述不对。
